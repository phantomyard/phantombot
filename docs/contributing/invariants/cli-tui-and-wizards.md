# CLI, TUI and wizards — contributor invariants

Part of the phantombot contributor guide: the Ink app, the TTY gate, settings/brain/voice wizards, model pickers. The index of every invariant is in [`/AGENTS.md`](../../../AGENTS.md). Numbers are stable identifiers — code comments and tests cite them — so a new rule takes the next free number and nothing is renumbered or reused (the one-time renumbering into 71–73 and 77 is recorded in AGENTS.md). Only the `### N.` headings below, each with its `inv-N` anchor, are numbered invariants; a numbered list in an intro section is prose, so never cite its item numbers. Each rule records a real incident; a deliberate, documented trade-off is not a defect.

### 35. The TUI is TTY-GATED and strictly additive — the CLI does not change (issue #471).

`phantombot` with no arguments, attached to a terminal on BOTH stdin and stdout, opens a full-screen Ink app: chat with the default phantom, or the setup wizard when it is not configured. Everything else is untouched. Three things are load-bearing and each has a silent failure mode. **The gate is a SECOND question after `isReadOnlyInvocation`, not a redefinition of it** (`lib/tuiGate.ts`). A bare call is still read-only whenever nobody is watching, because CI uses bare/`--help` as "does the binary run?" smoke tests and every shell `<TAB>` shells through the same entrypoint; an argv-based gate writes to disk on a runner and hangs `phantombot | head` forever on a renderer nobody can see. Both directions are pinned in `tests/lib-tui-gate.test.ts`. **A screen must call the SAME function the subcommand calls.** The TUI reuses `applyEmbeddingConfig`, `applyVoiceConfig`, `runMemoryIndex`, `runMemorySearch`, `runDoctor`, `writeAutostartPersonas` and `applyPersona`; where logic lived inline in a command handler it was EXTRACTED (the autostart ordering out of the `persona` picker, `runPersonaNew` out of `create-persona`), never copied. Two implementations of one write is how the CLI quietly becomes the untested surface. **Changing a setting is an ACTION, not a write** (`tui/actions.ts`). `phantombot embedding` finishes by PRINTING `phantombot memory index --reembed` for the user to run; miss that line and the vector-space fingerprint no longer matches the index, every stored vector goes invisible (queries are space-scoped) and recall silently degrades to lexical with nothing looking broken. So every editable field declares its consequence (`describe*Change`), performs it, and shows it finishing — with `onProgress` threaded through `runEmbedJob`/`runTurnEmbedJob` so the bar is real. The one asymmetry to preserve: the DOCUMENT prefix is part of the space fingerprint and the QUERY prefix is not, so a query-prefix change must never offer a re-embed. Three smaller rules that are easy to erode: **no code in the TUI may know the terminal width** — borders come from `borderStyle` on a flex box and widths from `flexGrow`/percentages, because hand-drawn box characters encode a column count and shear on any resize, emoji or CJK glyph; `stdout.columns` appears only in `App.tsx`'s resize listener. **Ink reads a TAPPED stdin** (`tui/stdinTap.ts`) — the tap is installed BEFORE `render()`, because it must exist before Ink attaches to its stdin, and its `setForwarding` is the single switch that detaches the TUI from the keyboard while another program borrows the terminal and re-attaches it afterwards. Re-attaching RESUMES the real stdin: closing a `readline` interface pauses it, and a paused stdin brings the app back drawing perfectly but deaf to every keystroke. The tap is released on every exit path. #508 removed mouse support together with `tui/mouse.ts`, the filtered stdin that carried it; the tap is what that filter became. **Chat turns are `trusted: true`** — the speaker is a human at a local TTY in the account that owns the persona directory, who can already read `identity.json` and therefore already holds the vault key, so screening adds nothing while getting it wrong the other way HOLDS the owner's own messages and locks them out of their own phantom. This widens nothing else: `phantombot ask` stays untrusted, a pipe is not a TTY, and the chat path is reachable only through the TTY gate. **It is a FULL-SCREEN app, and that is four separate mechanisms** (`tui/terminal.ts`). `render()` alone draws INLINE — a frame the height of its content, left in the shell's scrollback under whatever was there before — so the entrypoint enters the alternate screen buffer (`?1049h`, restored on every exit path including a crash), the root box is given `height={rows}`, the transcript is CLIPPED to the window before layout (`tui/transcript.ts`, newest kept, at least one message always), and the size is measured in ONE place and passed down by context. That last point is the width rule restated, not an exception to it: the root may measure, a component may ask how many ROWS it has, and nothing anywhere does column arithmetic to draw. Skip the clip and a long thread pushes the bottom border off the screen and the alternate buffer scrolls — the deformation this all exists to prevent. **Logs are captured while the TUI runs, never printed** (`lib/logSink.ts` → `tui/logBuffer.ts`, shown on `^l`). The logger writes JSON lines to stderr, which is the same terminal the app draws on, so unredirected they land on top of the frame and tear it wherever one wraps. Two writers, not one: the logger is redirected globally AND `openChat` takes a `stderr` sink, because a harness subprocess writes to whatever stream it was handed. Capturing without a pane would be hiding a failure rather than fixing a layout, so the pane is part of the fix. Every non-TUI entrypoint keeps writing to stderr byte-for-byte as before. **Ink asks the questions too** — a value to type, a choice to make and a confirmation to give are screens inside the app (`screens/Ask.tsx`, `screens/Choose.tsx`, `screens/Confirm.tsx`), with its header, footer and `esc`. Ink cannot be paused, so the entrypoints install a host (`setPromptHost` in `tui/prompts.ts`) that BRACKETS any borrower that is not Ink: writes gated off (`gateStdout`), keystrokes no longer forwarded (the tap's `setForwarding(false)`), alternate screen left; on the way back the alternate screen is re-entered, forwarding restored (which restores raw mode and resumes stdin) and the frame repainted in full with `forceRepaint` — not `clear()`, which re-syncs Ink to the frame it just erased — because Ink diffs against a frame that is no longer on screen. Nothing borrows today — the `$EDITOR` hand-over became `screens/FileEditor.tsx` and the `@clack` flows became screen flows (#508) — but the bracket stays installed (`tui/index.tsx`, `tui/standalone.tsx`) and pinned by `tests/tui-prompts.test.ts`. A cancelled question resolves `undefined`/`false` and MUST change nothing. **A working turn has to look like one.** The activity line animates (spinner + the current step + a climbing seconds counter, `components/Spinner.tsx`); a static `thinking…` was reported as not noticed at all, and it makes a twenty-second turn and a hung process render identically. Assertions on it must test MOTION, not the presence of a word. **`^s` and `^p` are different questions.** `^s` opens the settings of the phantom you are talking to; `^p` opens the host-wide table. Wiring both to the dashboard (the first cut) answered a question the user did not ask, and `esc` must return to whichever screen the settings were entered from. **A screen taller than the window renders FEWER BLOCKS, not smaller ones** (`tui/scroll.ts`). Yoga does not clip overflow, it compresses: two readings print on the same line and the bottom border comes out as `╰─ ─ ─✚─Doctor─`. `Frame` clips its body as a backstop and every growable screen windows its own content and says what it hid. **A text field reads its live value from a REF, never from the render closure** (`tui/textInput.ts`): several stdin chunks can arrive before React commits, and a chunk can carry its own newline (a paste, or batched keystrokes) which Ink does not report as `key.return` — that combination created a persona named `"alice\n"` and, in the other direction, dropped every letter but the last. Documented in [First run](../../../docs/getting-started/first-run.md); if you change the gate, the key map or the consequence table, update it.

### 36. The chat screen dispatches slash commands AHEAD of the harness, and renders replies as markdown (issues #480, #481).

`src/tui/slash.ts` decides only what the terminal ADVERTISES — the list is derived from `TELEGRAM_BOT_COMMANDS`, never retyped — and `chatSession.command()` delegates to the same `handleSlashCommand` Telegram, phantomchat and ACP call, so persona gating on `/update` and `/restart` comes free and three surfaces cannot drift. Three things are load-bearing. **Ahead of the harness is the whole point:** `/stop` exists to kill the turn that is currently blocking everything, so it is not gated on `busy` and neither is typing — a keyboard that stops accepting characters exactly when a turn hangs cannot be used to stop it. The session therefore owns its OWN `AbortController` and forwards the screen's `^c` signal into it; an `AbortSignal` cannot be aborted by whoever merely holds it, so without that `/stop` would have nothing to abort. **Command-SHAPED is not the same as ours:** `/wat` is answered in-app with the list, while `/usr/bin/env`, `/etc/hosts` and `/^ab+c$/` must reach the phantom untouched — the parse is a head of `[A-Za-z][\w-]*` and nothing else, and both directions are pinned in `tests/tui-slash.test.ts`. **Messages are patched by IDENTITY, not by "the last message"** — a command typed mid-turn appends a second bubble, and index-based patching then writes the streaming reply into it. For markdown, `src/tui/markdown.ts` is a pure `(text, width) -> rows` function emitting SPANS, never ANSI: escape sequences are not glyphs, so a decorated string would be measured wrong and the transcript's "a row of scroll is a row on screen" arithmetic — the thing that keeps clipping ahead of layout — would break. Yoga compresses rather than clips, so every block states its own policy: prose, lists and quotes WRAP; code rows and table cells TRUNCATE with an ellipsis (a re-flowed command line looks copy-pasteable and is not), and table columns are shrunk widest-first to a floor of three. Purity is what makes the width-drop `forceRepaint` path safe — there is no cached layout to invalidate. Only ASSISTANT text is rendered: an error is shown verbatim (a stack trace full of `*` would come out half-eaten) and so is the user's own line. The type-ahead pays for its rows out of the transcript in the same render, so a `/` keystroke can never grow the column and tear the frame.

### 43. System observability is platform-neutral and failure-tolerant (issue #478).

The TUI's former Logs destination is the `^l` System workspace: Overview distinguishes daemon, heartbeat, and tick using the existing service probe, timer fire markers, and persona task history; Logs READS THE HOST'S REAL SINKS, it does not display only what this process captured. That distinction is the whole issue: the original pane was fed exclusively by a 100-line process-local ring (`tui/logBuffer.ts`) filled by the TUI's own logger and, once a chat was open, harness stderr — so a TUI opened over SSH purely to look at logs showed `0/0` BY CONSTRUCTION, because the daemon that answers Telegram is a different process logging to journald. `tui/logSources.ts` therefore enumerates five sources — `session` (the live ring), `service` (the daemon, via the SAME `logsSpec` argv `phantombot logs` uses, so there is one definition of "the service log"), `audit` (`<persona-dir>/audit/<day>.log`), `state` (`state-audit.log`) and `tasks` (`task_runs`) — cycled with `s`. Three rules are load-bearing. **Every source reports its `location` and a copy-pasteable `command`, and the pane renders both above the lines**; the question that motivated the issue was literally "where do I find the audit logs?", and a viewer that cannot answer it has failed even when it shows lines. **A source that cannot be read stays LISTED, marked `available: false` with a reason, and its `read` returns an explaining ROW rather than `[]`** — an empty pane and a quiet host must remain distinguishable, which is exactly the failure mode being fixed, so returning `[]` on an empty audit trail is a regression the tests pin. **The time filter defaults to `all`, not `1h`**: the sources are now durable files where the interesting line is usually older than the window, and a 1h default silently reproduces the original symptom. Two smaller points: the log sink is installed as the FIRST statement of `startTui()`, ahead of `hostSnapshot()`, because snapshotting is the noisiest part of startup and every one of those lines used to be lost to stderr; and the ring defaults to 5000 lines (`PHANTOMBOT_TUI_LOG_LINES`) rather than 100. Reads are bounded and never throw — journalctl absent in a container is a row, not a crash. Missing markers, old task schemas, unreadable databases, or an unavailable service probe render as `unavailable` and must never block or crash the TUI. History charts are Unicode summaries inside flex layout, not hand-measured terminal-width drawings. Tests: `tests/tui-system.test.ts`, `tests/tui-navigation.test.tsx`, `tests/tui-log-sources.test.ts`, `tests/tui-log-pane.test.tsx`.

### 47. A long-lived chat session resolves its harness chain ONCE at open, so any write that can change that chain must REBUILD IT IN PLACE.

`ChatSession` deliberately outlives screen switches (`ctrl+s` into Settings and back must not lose the transcript), which means it keeps talking to the chain that existed when it opened. Configure the brain mid-session and, without `reloadHarnesses()`, chat keeps driving the pre-config chain — on a fresh host that is the default `claude`, which is not installed, so every turn fails. Reopening the session would fix the chain and wipe the conversation, so the wizard (`brainOnboarding`) and the Configure > Brain row both call `reloadHarnesses()` instead. Pinned at the CALL SITES in `tests/tui-brain-reload.test.tsx`, not just on the helper.

### 49. Model pickers are filled from the PROVIDER'S OWN `/models` endpoint, never from a catalogue baked into the binary.

`pi --list-models` only enumerates providers Pi has already keyed, so the model list is empty for the key the user just pasted — the exact moment they need it. `src/lib/providerModelCatalog.ts` fetches live, reusing `providerKeyProbe`'s endpoint table as the single source of truth (OpenRouter's is public: no key, ~430 models). A hardcoded model list rots inside one release cycle and is not an acceptable fallback; the fallback is free-text entry. **The decision-model picker asks the DECISIONS catalogue, not the chat catalogue (phantomops parity)**: `fetchDecisionModels` (`src/lib/decisionModel.ts`) pins `https://openrouter.ai/api/v1/models?output_modalities=decisions` for OpenRouter — the same modality split the voice picker makes for transcription/speech ([invariant 65](#inv-65)) — because the decisions catalog is a DIFFERENT list from the chat catalog, verified live 2026-10-02: the unfiltered `/models` carries 460+ chat models and NONE of the decide models (`liquid/d1`, `togethercomputer/tev1-4b-experimental`, `inception/mercury-decide:free`, `upstage/solar-decide`, `respan/span-01`, `jaredpalmer/kev-4b`, `~typesafe/jev-latest` — 10 ids that day). The pre-fix code fetched the chat catalogue and heuristically promoted "typesafe"/"jev"/"decision"-ish ids, which offered hundreds of chat models that would all fail the `/api/alpha/decisions` endpoint while showing none of the decide models the operator came for. The query param is the ONLY filter — no client-side heuristic can reconstruct the list, so none is attempted; the default model stays pinned first and the rest of the catalog sorts deterministically behind it. **A choice question carries a vendor FLOOR of 2 options**, enforced client-side by `questionsError` (`DECISION_MODEL_MIN_CHOICES`): the decisions gateway 422s a single-option choice ("A Choice needs at least 2 options", verified live 2026-10-02 when the wizard's own validation ping — a 1-option `pong` — failed against every OpenRouter decide model while the live judge payload, `allow`/`hold`, was always compliant). The wizard's `validateDecisionModelKey` probe therefore sends a two-option pong, and the client-side floor catches the whole bug family before the wire so no future call site can ship a one-option choice. Tests: `tests/lib-decisionModel.test.ts` (pinned URL + catalog shape + degrade-to-default + the min-2 floor), `tests/cli-jev.test.ts` (the ping's wire shape); the flow tests inject `fetchModels`.

<a id="inv-52"></a>
### 52. A wizard that WRITES AS IT GOES must be able to roll back, and its notices must match what is actually on disk.

The brain interview persists every answer as it is given — provider and model slots through `applyRouting`, the API key into the vault AND into Pi's `auth.json` — but only asks "apply?" after the live test. Withholding `applyChain` on discard is therefore not "changing nothing": it leaves the new provider, models and key committed under a notice that says the brain is unchanged (PR #539 review). `runBrainOnboarding` snapshots all three stores before the first `configureNative` pass and restores them on every non-applying exit: cancel, esc mid-interview, failed test, explicit discard. Two rules make the rollback correct. **Snapshot the routing sub-table VERBATIM, per slot** (`snapshotPiRouting` / `restorePiRouting`): a key-by-key restore drops the `use_local_config` tombstone, and a persona that no longer states its routing silently inherits the HOST's. **Restore Pi's `auth.json` byte for byte** (`snapshotPiAuth` / `restorePiAuth`, 0600, tempfile+rename): it is shared user state holding OAuth entries we must not re-serialise, and the only file we may delete is one the wizard itself created. When the restore fails, the notice degrades to "brain partly saved" — never claim an intact brain you did not verify. Tests: `tests/brain-onboarding.test.ts` (flow-level, proven by mutation), `tests/cli-harness-routing.test.ts` and `tests/lib-piAuthStore.test.ts` (store round-trips).

### 54. Every ask/choose/search overlay request mounts a FRESH screen — keyed per request, never reused.

`askValue` resolves, clears its state and the caller's next `askValue` sets new state in the same React batch, so without a key the `AskScreen` never unmounts and the second question inherits the first one's `useState` — the OpenClaw import's "Persona name" box opened holding the directory path just typed, and Enter submitted the path as the name ("import failed: use lowercase letters…"). `App.tsx` stamps each request with `requestSeq` and renders the overlay with `key={request.seq}`; the same applies to `ChooseScreen` (a stale cursor would pre-select the previous pick's row) and `SearchListScreen`. Test: `tests/tui-app-first-run.test.tsx` (the import test asserts the name box does not contain the path; proven by removing the key).

### 58. OpenAI voice-list probing is a compatibility helper, not the provider contract.

`fetchOpenAIVoiceOptions` can still parse OpenAI’s model-scoped validation response for callers that want a menu, but OpenAI-compatible setup accepts provider-specific model and voice strings because another endpoint may expose different names. ### 62. A seeded prompt is trusted ONLY because a human is watching it run, so a launch with no terminal is refused, never rerouted.

`phantombot --prompt "…"` (issue #575, for Omarchy's default-agent integration) opens the TUI and sends the prompt as the first turn, exactly as if typed — the same shape as `pi "$prompt"` / `claude -- "$prompt"`. Trust comes from the interactive process the user launched, so `lib/tuiGate.ts` REFUSES (exit 2, pointing at `phantombot ask`) whenever that premise fails: no TTY on stdin or stdout, `--no-tui`, a missing/empty value, a repeated flag, or a `--persona` that is not a valid persona-directory name. Refusal happens in `src/index.ts` BEFORE the credential bootstrap, so an unattended caller provisions nothing on its way to being turned away, and it never silently falls back to `ask` — that would convert a refused unattended prompt into an accepted one. WHICH PHANTOM a launch is for is resolved ONCE, from the same chain the rest of the CLI uses with the flag added in front — `--persona`, then the harness-injected `PHANTOMBOT_PERSONA`, then the configured default (`resolveLaunchPersona` → `launchOpeningTarget`, consumed by `src/index.ts` for the vault and by `resolveLaunchOpening` for the opening screen). Resolving the vault from the full chain but the screen from the FLAG ALONE pairs one phantom's decrypted secrets with another phantom's conversation (`PHANTOMBOT_PERSONA=lena` + default `robbie` decrypted Lena's vault and seeded Robbie's chat). A named phantom that does not exist is refused (exit 2) whether the name came from the flag or the env var — the entrypoint already resolved the vault from it, so continuing would open another phantom's chat with no secrets at all — and it is never a reason to open the wizard; a resolved DEFAULT that does not exist is NOT refused, because that is the broken-default case `resolveOpeningScreen` heals. The prompt is dropped with an on-screen notice when the app opens anywhere but a ready chat (`seedForOpening`) — holding it across onboarding would fire a turn minutes after the user stopped expecting it — and it is delivered ONCE, only to the persona the launch named (`App` holds it in a ref and the chat screen reports consumption on mount, so `^s`/`esc` never replays it). A seeded slash command dispatches as a command, like a typed one. Related: interactive launches now run turns in the LAUNCH CWD (`lib/launchCwd.ts`), falling back to `$HOME` when it is gone or unlistable — `ask` and every channel deliberately stay on `$HOME`. Tests: `tests/lib-tui-gate.test.ts`, `tests/tui-launch-prompt.test.tsx` (real `App` + real `ChatScreen`), `tests/tui-launch-persona.test.ts` (the real launch decision path against personas on disk, env ≠ default), `tests/lib-launch-cwd.test.ts` (including a real subprocess proving the headless refusal writes nothing); 23 mutations proven.

### 65. OpenAI-compatible audio is one endpoint-scoped full loop, not an OpenAI-only TTS special case (issues #618, #622).

`[voice] provider = "openai-compatible"` selects `[voice.openai_compatible]` with `base_url`, `key_env`, independent `stt_model`/`tts_model`, `voice` and `speed`; `audio.ts` appends `/audio/transcriptions` and `/audio/speech` to the already-versioned base URL. **OpenRouter splits CATALOGUES, not providers**: the wizard asks `/models?output_modalities=transcription` and `=speech`, requires each row to declare the requested modality (an endpoint that ignores the query must not expose its whole text catalogue as audio), and offers separate model menus with a typed **Other** escape. A speech row's `supported_voices` is authoritative for that model and drives the voice picker directly (for example Grok's `eve`/`ara`/`rex`/`sal`/`leo`); only missing metadata falls through to the rejected-request parser and then the OpenAI fallback list. Switching endpoints never carries OpenAI's model defaults into OpenRouter. OpenAI-compatible TTS prefers `mp3`, then retries without `response_format` when the endpoint explicitly rejects that encoding; voice discovery and proof make the same retry because a format rejection says nothing about a voice. Provider-selected `audio/pcm` is signed 16-bit little-endian, wrapped in WAV before it reaches a transport, and Telegram uses `sendAudio` for that WAV because `sendVoice` accepts MP3/M4A/OGG only. Other response MIME types propagate unchanged; transports must never relabel bytes as OGG. OpenRouter's unquoted `Supported voices:` response is a valid enumeration shape. A network failure or HTTP 401/403/429/5xx during voice proof is INCONCLUSIVE, not a bad voice; only a response that actually rejects the model/voice blocks saving, and rejection UI must not prefix non-key failures with `key rejected`. The pre-#618 `provider = "openai"` block loads into this runtime shape for upgrade compatibility, while every writer emits only the new block and removes retired OpenAI/Azure blocks on save. Azure Edge is retired: it is absent from both wizards, writes are refused, and a legacy config yields a migration error instead of a half-working TTS-only phantom. Credential discovery is endpoint-aware and persona-scoped through `getPersonaSecretStrict`; it may offer a matching audio/embeddings/OpenAI/OpenRouter vault row without rendering the value, and it must never inspect another persona. Declining an offered shared credential writes the replacement to `PHANTOMBOT_VOICE_OPENAI_COMPATIBLE_API_KEY`; it must never overwrite the routing or embeddings slot the operator declined. Audio examples are OpenAI and OpenRouter only; the embeddings flow may additionally show Ollama because OpenAI-compatible embeddings do not imply audio support. Tests: `tests/lib-audio.test.ts`, `tests/lib-voice.test.ts`, `tests/cli-voice-voice-check.test.ts`, `tests/cli-voice.test.ts`, `tests/tui-voiceFlow.test.ts`, `tests/config.test.ts`, `tests/channels-statusProbes.test.ts`.

### 77. ↑↓ in the chat prompt walk the rows AS DRAWN, and only the edge rows scroll (issue #667).

`promptBox.ts` `cursorUp`/`cursorDown` move by VISUAL row — wrapped rows count, not just `\n` — keep a goal column (display columns, so an emoji is 2 and the cursor never lands inside one), and return `undefined` on the first/last row, which is `Chat.tsx`'s cue to scroll the transcript; shift+↑↓ and PgUp/PgDn always scroll. Two things are load-bearing. **There is ONE layout** (`layoutLine`), read by both `promptRows` and the vertical moves through the same `rowOf`/`colOf` map — a second model of wrapping would send ↓ to a row you cannot see. **The layout ignores the cursor** (issue #677): the cursor is drawn ON a cell in inverse video, never as a cell of its own, and the text gets `width - 1` columns so the last column is free for the solid cursor cell at the end of a line or on whitespace that hangs past the edge. Moving the cursor therefore never re-wraps or shifts the text. Do not bring back a caret glyph (the old `▌`) inside the wrap stream: it made the row count depend on the cursor position and needed a per-row restart scheme just to keep ↓ fast on a long paste. `tests/tui-prompt-vertical.test.ts` pins the moves against an exhaustive oracle (every cursor position rendered by `promptRows`) on fixed and seeded-random texts; `tests/tui-prompt-box.test.ts` pins the drawing.

<a id="inv-78"></a>
### 78. The chat prompt's Emacs keys are matched on what Ink reports, never on the characters macOS types for Option (issue #677).

`Chat.tsx` binds ^b/^f (character), Alt-b/f and Alt-←/→ (word, via `cursorWordLeft`/`cursorWordRight`), ^a/^e (line, then whole input, via `cursorLineStart`/`cursorLineEnd`) and ^p/^n (the same path as ↑↓, so rule 77 applies). Alt is recognised only as Ink's `key.meta` — an Esc prefix or a modified arrow. **Never map `∫`/`ƒ` (or any other Option-layer character) to a word move**: they are what macOS sends when the terminal does NOT treat Option as Meta, they differ per keyboard layout, and catching them makes them impossible to type. The fix for "Option-b types ∫" is the terminal setting, documented in [TUI keys](../../reference/tui-keys.md). The word-move branch sits ABOVE plain ←→, because Ink reports Alt-← as `leftArrow` with `meta` and the plain branch would take it as a single step. Home/End stay transcript scrolling, which is why line start/end live on ^a/^e. A word is a run of letters, digits and combining marks; everything else — including `\n` and emoji — separates words, so word moves cross lines without a special case. `tests/tui-prompt-emacs.test.ts` pins the moves; a new binding updates that test, [TUI keys](../../reference/tui-keys.md), and this rule.
