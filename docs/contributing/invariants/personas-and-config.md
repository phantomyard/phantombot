# Personas, config and credentials — contributor invariants

Part of the phantombot contributor guide: the many-personas-one-process model, the two config layers, the vault and the retired `.env`. The index of every invariant is in [`/AGENTS.md`](../../../AGENTS.md). Numbers are stable identifiers — code comments and tests cite them — so a new rule takes the next free number and nothing is renumbered or reused (the one-time renumbering into 71–73 and 77 is recorded in AGENTS.md). Each rule records a real incident; a deliberate, documented trade-off is not a defect.

## Persona model — many personas, one process

**One process serves every persona this host starts** (phantombot#439). The persona "library" on disk (under `~/.local/share/phantombot/personas/`) can hold many directories; which of them run is an explicit choice, never inferred from what happens to be on disk:

- `default_persona` — a CONVENIENCE, not an owner (phantombot#519). It always starts and it is what a persona-less caller (the chat TUI, a bare CLI invocation) falls back to — nothing derives AUTHORITY from it. The lifecycle commands `/update` and `/restart` are answered for ANY served persona: they bounce the shared process, so the real constraint is a single-flight lock (`src/lib/lifecycleLock.ts`) plus a heads-up to every other persona (`src/lib/lifecycleBroadcast.ts`), never a designated owner. That heads-up is channel-neutral: Telegram accounts fan out through bot tokens and PhantomChat through each persona's own phantomchat.json identity (nsec + relays + allowlist) via the shared one-shot send path (`src/channels/phantomchat/oneShotSend.ts`). **Notification sources fan out independently to every configured channel**: a persona reachable on BOTH Telegram and PhantomChat is notified on both, and one channel failing never suppresses the other. Recipients come from the account map the daemon builds off the resolved listener plan, never inferred from the calling listener's own persona-resolved config (on a non-default listener `channels.telegram` is that CALLER's bot). Gating on the record instead stranded a host whose `default_persona` named a persona that did not exist — every persona was told to ask a ghost, and only SSH could recover it. `/stop` is per-chat and ungated by persona — but like every slash command it is still answered only for an authenticated principal ([invariant 24](security-perimeter.md#inv-24)).
- `autostart_personas` — the explicit roster of ADDITIONAL personas to start. Absent means "exactly what this host did before the key existed"; present (even empty) is the whole truth, and a persona outside it is not started even if it has a `phantomchat.json` or a legacy `[channels.telegram.personas.<name>]` entry.

`runRun` builds one Telegram listener per persona-with-a-bot and one PhantomChat listener per persona-with-an-identity, all inside the single `phantombot run` process. The `runLock` (`src/lib/runLock.ts`) still prevents two `phantombot run` processes on one box — the multiplexing is inside the process, not across processes. There is no supervisor, no subprocess per persona, and adding one is a rejected design (crash isolation is not worth a supervisor, backoff, orphan handling on update, and the cgroup trap of #415).

Telegram account parsing is deliberately permissive: an account without a token resolves to no `TelegramAccount`. `Config.channels.telegramStated` and `telegramPersonasStated` preserve whether TOML nevertheless stated that account, so `planListeners` can warn and `doctor` can fail without making startup fatal. Do not infer intent from `channels.telegram === undefined`: that shape also describes a valid PhantomChat-only persona. A broken Telegram account disables only that listener; sibling Telegram listeners and PhantomChat must keep running.

**Config is two layers** (`src/lib/personaConfig.ts`, `loadConfig(persona)`):

| File | Holds |
|---|---|
| `<config-home>/phantombot/config.toml` | HOST globals: `default_persona`, `autostart_personas`, `update_channel`, `personas_dir`, `memory_db`, harness bin paths |
| `<personas-root>/<persona>/config.toml` | that persona's own settings: its Telegram bot, `[voice]`, `chattiness`, `[retrieval]`, its `[harnesses].chain` |

Resolution is a per-key deep merge, persona wins, env still wins over both. A key the persona file omits falls back to the GLOBAL FILE, never to a constant. Host-only keys are stripped from the persona layer, so a persona cannot elect itself default or relocate the root.

Two rules that follow from this, and that new code keeps breaking:

1. **Resolve the persona BEFORE loading config.** Any persona-aware entry point (`notify`, `ask`, `nightly`, `heartbeat`, `tick`, `voice`, `telegram`, `harness`) must call `loadConfigForPersona(name)` / `loadConfig(name)` rather than loading the default layer and picking a persona out of it afterwards. Loading first silently runs one persona on another's settings.
2. **Write where the read path looks.** A per-persona setting is written through `resolvePersonaWriteTarget()`: the persona's own file once it exists, the global file (in its historical shape) until then. A writer that ignores this "saves" successfully and changes nothing.

Migration from the old single-file layout is copy-only (never delete, so a rollback still boots), additive (fills only the keys the persona file omits, so a hand edit always wins) and runs on every daemon start, which is what makes `/update` order-independent from any older version.

The [Personas guide](../../../docs/how-to/personas.md) is the user-facing explanation;
if you change this model, update that guide and this invariant together.

## Credentials

Credentials live in the per-persona encrypted vault. The agent NEVER appends
secrets to `.env` or puts literal secret values in command arguments. It uses
`printf '%s' "$VALUE" | phantombot vault set NAME`; the positional
`phantombot vault set NAME "value"` form also remains available for backward
compatibility. Empty stdin is rejected unless `--allow-empty` is explicit, so a
failed pipe cannot silently erase an existing credential. The full credential
discovery + hygiene rules are baked into every persona's system prompt via
`CREDENTIALS_SECTION` in `src/persona/builder.ts`. If you change those rules, update both
`CREDENTIALS_SECTION` and [Secrets](../../../docs/how-to/secrets.md)
section.

## Invariants

<a id="inv-7"></a>
### 7. Creating/importing/restoring a persona on a fresh box without setting it as default

— the built-in fallback `default_persona = "phantom"` doesn't have a directory; `phantombot run` would fail with "persona 'phantom' not found." Every persona-producing path (`runImportPersona`, `runImportFromPath`, `runRestoreArchive`, `applyPersona`) calls `adoptAsDefaultIfMissing` from `src/lib/personaDefault.ts` so the new persona becomes default when there's no working default. If you add another persona-producing path, call it too — and add a `state.json` isolation `beforeEach` to its tests so they don't pollute the real `~/.local/share/phantombot/state.json`.

<a id="inv-18"></a>
### 18. The default-persona switch is gated on confirmation and agent-scoped switches are refused (PR #383 / issue #371).

`phantombot persona <name>` persists `state.default_persona` **only after** an explicit confirmation: interactive TTYs get a @clack confirm, non-TTY contexts require `--yes` (exit 2 otherwise), and tests inject a `confirm`/`isInteractive` into `runSwitchPersona`. A persona agent (harness sets `PHANTOMBOT_PERSONA`) can't re-point the daemon-wide default — that's the #371 ghost-switch bug — so the scope check refuses with exit 2 regardless of `--yes`. After confirmation the state is **re-loaded** (not the pre-confirm snapshot) to avoid clobbering a concurrent writer (e.g. `harness_bins` discovery), and the persona dir is re-validated right before the commit (TOCTOU). Any new user-facing CLI flag needs documentation in the relevant page under `docs/` and in AGENTS.md when it carries a contributor invariant; `--yes` is documented in [Personas](../../../docs/how-to/personas.md).

<a id="inv-27"></a>
### 27. Per-persona config has three rules, and each has already been broken once (issue #439).

One process serves every persona, and each persona's settings live in `<personas-root>/<persona>/config.toml` layered over the host's global file. **(a) Resolve the persona BEFORE loading config.** Every persona-aware entry point — `notify`, `ask`, `nightly`, `heartbeat`, `tick`, `voice`, `telegram`, `harness` — must call `loadConfigForPersona(name)` (or `loadConfig(name)`) instead of loading the default layer and picking a target out of it afterwards; the old shape silently runs one persona on another's bot, chain, voice and retrieval policy, and it fails *quietly*, which is why it needs a rule rather than a code review. The CLI resolves its target through the shared `resolvePersona(explicit, config)` helper in `config.ts` — explicit `--persona` flag, then the harness-injected `PHANTOMBOT_PERSONA` env var, then the configured default persona — and every persona-aware command (memory, task, vault, mcp, ask, notify, voice, heartbeat, nightly, doctor) routes through it (issue #473, PR #474): falling back straight to `defaultPersona` makes a non-default persona's harness silently operate on ANOTHER persona's data. `doctor` diagnoses and repairs with the RESOLVED persona's layer for persona-scoped checks (embeddings, harness chain, Pi routing) and keeps the host config for host-wide roster/account data (autostart roster, memory db path, update channel). Host-level harness BINS are carried over from the host layer by `withHostHarnessBins` — a `bin` names something installed on this machine and a stale persona copy must not shadow what `doctor` just probed. **(b) Write where the read path looks.** `resolvePersonaWriteTarget()` is the single write resolver: the persona's own file once it exists, the global file in its historical shape until then. A writer that hard-codes the legacy `[channels.telegram.personas.<name>]` / `[harnesses.personas.<name>]` tables reports "saved" and changes nothing on any migrated host, because the persona file outranks it on read. For the same reason `loadConfig(persona)` drops that persona's OWN legacy entry when its file states a chain, and a NON-default persona never inherits the global `[channels.telegram]` block — that bot belongs to the default persona, and handing it to a second listener trips the duplicate-token guard and takes Telegram down for everyone. **(c) Existing on disk never starts a persona.** The boot roster is `default_persona` + `autostart_personas`, applied to PhantomChat as well as Telegram (`selectPhantomchatPersonas`) — `listPhantomchatPersonas` scans directories, which is the right answer to "who is configured" and the wrong answer to "who talks to the world"; an imported, restored or archived-and-recreated identity must not start answering strangers because its folder exists. The gate is opt-in: `autostart_personas` ABSENT keeps exactly the pre-#439 behaviour, so an upgrade never silently loses a channel. Migration is copy-only (a rollback must still boot), ADDITIVE per key (a persona file holding only `[voice]`, which `phantombot voice --persona` will happily create before the first restart, must still get its Telegram translation) and runs on every daemon start, which is what makes `/update` order-independent from any version.

<a id="inv-28"></a>
### 28. A persona's brain is persona-scoped, and "cleared" must be SPELLED, not implied (issue #441).

The whole `[harnesses]` block — chain, Claude/Codex model, Pi provider and capability routing — resolves per persona: suffixed env (`PHANTOMBOT_PRIMARY_MODEL_LENA`) > that persona's `config.toml` > the host's unsuffixed env > the global `config.toml` > the default. Three things follow and each has already bitten. **(a) Every harness writer uses `resolveHarnessWriteTarget()`.** Not just the wizard — `/model` writes models too, and a write that lands in the global file is not "the host default", it is *every other persona's* value under the per-key merge. The resolver lives in `src/lib/harnessWriteTarget.ts` precisely so a non-TUI writer can share it. **(b) Deleting a key does not clear it.** Absence means "inherit", so removing a persona's routing hands it the host's routing and re-enables the host's ambient env var for that key. A cleared state needs its own on-disk spelling: `[harnesses.pi.routing] use_local_config = true` for "use Pi's own config" (it also withholds the api-key, which is read from the ambient env and would otherwise be the HOST's credential), and `model = ""` for a cleared codex pin. Any future persona-scoped opt-out needs the same treatment. That tombstone is only ever written into a PERSONA file — in the global file it would be inherited by every persona that has not stated its own, turning one persona's opt-out into the host's. **(c) A per-persona file must not fall back to another persona's file.** The managed pi extension directory is stamped once per host, so the harness names this persona's routing in `PHANTOMBOT_ROUTING_JSON`; when that var is STATED the extension reads only it, and a missing/invalid file registers nothing rather than falling through to the host-stamped sibling. A fallback across an isolation boundary is the leak, not the safety net.

<a id="inv-32"></a>
### 32. `.env` is a ONE-WAY LEGACY IMPORT — no runtime read, no write, and the file is kept rather than deleted (issue #452).

Phantombot sold the vault as canonical while `~/.env` and `~/.config/phantombot/.env` were still live on both sides: the units sourced them, `lib/envBootstrap.ts` re-sourced them before every spawn, and the model/voice/harness/importer wizards wrote to them — so the startup migration deleted files a later wizard run promptly recreated, and docs and reality disagreed about where a secret lived. All of it is gone in one direction: `vaultMigrate.ts` imports each plaintext file into the per-persona vaults exactly once and NOTHING reads one afterwards (`envFile.ts` is a read-only parser with `vaultMigrate` as its only importer, guarded by a test that enumerates the importers). Wizards write secrets through `lib/vaultSecrets.ts` into the persona's vault; non-secret model/routing settings write to `config.toml` only, and the old `PHANTOMBOT_*_MODEL` env mirror is deleted — a mirror nothing reads can only drift. Three things are load-bearing. **The plaintext file is NOT deleted.** An operator has to be able to roll back to an older phantombot that still sources it, so the migration keeps the bytes; what changes is that they stop mattering. **Therefore the migration needs a STAMP, not an absence.** `<file>.migrated-to-vault` is what makes the import happen once; without it a retained file would be re-imported on every startup and would silently stomp any `phantombot vault set` rotation made since — the file's absence used to carry that state, and keeping the file removed the signal. The stamp is written only after every key read back through the decrypt path, and a failure to write it means the whole file is retried next startup (verified-but-unstamped is reported as NOT imported, never as done). **Deprecation must be LOUD and repeated.** A surviving `.env`, and any retired key still present in the host `config.toml` (`DEPRECATED_CONFIG_KEYS` in `src/config.ts`), warns on EVERY startup rather than once per process: the failure mode is silent — an operator edits a setting and nothing changes — and a daemon that started before they opened the file would otherwise have already spent its one chance to say so. Rollback for the units is manual and documented: re-add the two `EnvironmentFile=-%h/...` lines, or install an older build; the files are still there. **The vault is a SECRETS store, so the import DROPS the settings that config.toml now owns.** A pre-#452 `~/.env` also carries the `PHANTOMBOT_*_MODEL` / `_BIN` / `_CHAIN` mirrors the old wizards wrote, and importing those would not preserve them, it would PROMOTE them: a vaulted key is injected into `process.env` at every startup and `harnessEnv(...) ?? asString(toml…)` resolves env FIRST, so a dead mirror would become a permanent override of the only store `/model` still writes — `/model claude sonnet` appears to work, then reverts on the next spawn, forever, with the stamp preventing the old re-import loop from ever healing it (the `_<PERSONA>` variants are worse: they outrank even the persona's own file). `CONFIG_OWNED_ENV_MIRRORS` / `isConfigOwnedEnvMirror` (`src/config.ts`) name them and `vaultMigrate.importableEntries` drops them at import, loudly; a file of nothing but mirrors is still stamped so it is not retried forever. **The drop-list must be enforced where the vault is READ, not only where it is written (issue #465).** Wiring it to the import path alone fixed hosts that migrated after #454 and left every host that had already vaulted its `.env` under #254 broken forever: the mirror rows were already resident, nothing sweeps a key that is merely present, and the predicted failure duly happened on the whole fleet — `phantombot harness` wrote `config.toml` correctly and the run kept using the stale model, on six personas at once. So `readAllVaultValues` (`lib/vault.ts`) withholds any mirror from the values it returns, and evicts the row as it goes — but ONLY when `configOwnedEnvMirrorSetting` finds the `[harnesses]` key it was retired into actually stated in a config file. Withholding is the load-bearing half — it is what makes the override inert, it covers every persona and every per-turn `reloadVaultForPersona`, and it holds even if the eviction throws; the eviction is hygiene, so `vault list` stops advertising a dead setting and a downgrade cannot resurrect the override. That is the one write on an otherwise pure read path, and it stays legal only because it is bounded to names the vault should never have held, idempotent, and self-extinguishing. The condition matters because eviction is the only IRREVERSIBLE step here and the mirror is not always a duplicate: `phantombot env set PHANTOMBOT_PRIMARY_MODEL …` was a supported way to set the value without touching `config.toml`, so on such a host the row is the last copy and deleting it would drop the persona to a built-in default with nothing left to recover from — those rows are kept, inert and named, and the startup warning says plainly that a DEFAULT now applies rather than claiming a config file is in charge that never mentioned the key. Nothing puts a mirror back either: `runVaultSet` (and therefore the deprecated `phantombot env set` alias) refuses the name outright with a pointer to `phantombot harness`, because otherwise the CLI would print `saved NAME to the vault` and the daemon would delete it on the next read — the same silent failure, at the one moment there is an operator present to be told instead. Note the scope: env-over-config precedence is NOT reverted, so a real shell `export` is still a working escape hatch — what is removed is the vault fabricating that export behind the operator's back, which is why the guard keys on the vault row and not on the env var. **A secret read for a persona that is not the startup persona must come from THAT persona's vault.** One daemon serves several personas but `loadVaultIntoEnv()` only ever injected the startup one's secrets into the shared `process.env`, so in-process consumers that used to read a single shared plaintext file now have to resolve per persona or they silently get the wrong persona's key or none: the audio path (`voiceApiKey` in `lib/audio.ts`, which is why `sttSupport`/`ttsSupport`/`synthesize`/`transcribe` are async) and tick's `--secret` env (`buildCommandEnv`, per `task.persona`). Two rules there: never write a resolved key back into `process.env` (two persona listeners can be mid-turn at once), and when falling back to the ambient env, exclude names this process injected FROM a vault (`isVaultInjectedEnvKey`) — an ambient shell/systemd export is host-wide and safe, another persona's vault value standing in is a cross-persona credential leak. That exclusion is scoped to the leak it exists for: a key injected from THIS persona's own vault is still honoured (`ambientEnvKeyAllowed` in `lib/vaultSecrets.ts`, the one gate both resolvers share), because `loadVaultIntoEnv` deliberately leaves injected secrets in place when the SAME persona's vault fails to open transiently — refusing them there would mute a persona over its own credential, and would have the two paths disagree about what a transient blip means. Vault READS are open-existing-only (`getPersonaSecretStrict` guards on the vault file, same rule as `readAllVaultValues`, #262): a pure read must never mint an identity + nsec for a persona nobody provisioned. **Deprecation warnings cover the PERSONA layer too**, not just the host file (`DEPRECATED_CONFIG_KEYS` / `warnDeprecatedConfigKeys`, checked before `stripHostOnlyKeys`) — since #441 a persona `config.toml` sets the same keys, and that is exactly where a silent edit hides. Note "retired" is not "ignored": `turn_timeout_s` is still honoured as an alias, and each entry's `advice` says which it is. Out of scope and still open: Telegram tokens and Gemini embedding keys living in `config.toml`.

### 38. A persona-scoped job must CARRY its persona, and the host default must be observable (issue #505).

Email triage stopped for ~200 consecutive scheduled fires while `task_runs` recorded `exit=0 ok` for every one of them, because three separate things were each individually defensible. **(a) `buildCommandEnv` (`cli/tick.ts`) sets `PHANTOMBOT_PERSONA` to the task's owning persona.** Command tasks get a deliberately minimal environment, and that env was missing the one variable the documented contract depends on: the shipped pattern tells a poller to shell back into `phantombot` (`ask`, `notify`, `mcp call`, `memory`), and every one of those resolves through `resolvePersona` — `--persona`, then `PHANTOMBOT_PERSONA`, then the HOST DEFAULT. With the variable absent, one tick process running tasks for every persona sent all of them at the default persona's vault, memory and MCP registry. That is the same cross-persona class as #452's secret leak, arriving through the env instead of the vault, and it fails QUIETLY: reading the wrong persona succeeds. It is set AFTER the allowlist copy so the tick process's own ambient value can never outrank the task's owner. **(b) `defaultPersonaDefect` (`lib/personaDefault.ts`) is the shared "is this default usable" predicate, and it is deliberately WEAKER than `personaCompleteness`.** `existsSync(personaDir)` was the whole test, so a create that died after `mkdir`, or a migration that moved the contents out, left a husk that heal read as healthy. The predicate now also requires at least ONE marker (`identity.json`, `config.toml`, `vault.sqlite`, `mcp.json`, `IDENTITY.md`, `SOUL.md`, `MEMORY.md`, `BOOT.md`, `memory/`, `kb/`) — a union, not an intersection, and NOT the completeness check the TUI launch gate uses. Heal rewrites `state.json` unprompted, so its trigger may never be something that can be transiently false: `identity.json` is created LAZILY on the first vault open (a persona created seconds ago has none) and the completeness brain probe reads the current PATH. Keying heal on either would let a fresh install repoint its brand-new default at some older persona, which is worse than the bug being fixed. `adoptAsDefaultIfMissing` uses the same predicate so the two writers cannot disagree, and heal prefers a candidate that is itself usable over the alphabetically-first name, or a host with two husks heals into another husk. **Scope, stated so nobody expects more:** a persona migrated to another HOST but leaving its files behind is indistinguishable from a working one and this will NOT catch it — that is (c)'s job, because reporting is safe and silently rewriting the host default on a guess is not. **(c) `doctor` reports the default persona on its first line: resolved name, provenance, usability, served-ness, MCP server count.** Provenance is load-bearing rather than decorative: resolution is `PHANTOMBOT_DEFAULT_PERSONA` > `state.json` > `config.toml` > built-in `phantom`, so the layer an operator edits first is the one that loses, and the human line says so explicitly when the answer came from state. Exit-code policy is deliberately split — a missing persona dir or an unparseable `mcp.json` FAILS (every `--persona`-less command is aimed at it), while an empty-but-loadable registry only WARNS, because a host that registers no MCP servers at all is normal and a health check that cries wolf is one nobody reads. The warn fires only when the default's registry is empty *while another persona's is not*, which is the exact shape of the outage. **The broader lesson, which is not enforceable in code but is why this issue exists:** a poller whose "skip quietly" path is indistinguishable from "nothing new" is an invisible outage. Every early exit in a command-backed task should log its reason. Tests: `tests/cli-tick.test.ts`, `tests/lib-personaDefault.test.ts`, `tests/cli-doctor.test.ts`.

<a id="inv-40"></a>
### 40. Persona names are case-sensitive keys even where paths are not (PR #475).

Resolve a configured default through `canonicalPersonaName`, using the exact spelling from the persona-directory listing before it reaches memory, vault, journal, or task namespaces. A unique case-only match is repaired and persisted; multiple case-insensitive matches are ambiguous and must never be guessed. Canonicalisation composes with `defaultPersonaDefect`: a case-matched husk is still defective and must not outrank a usable persona.

<a id="inv-55"></a>
### 55. An import writes for the persona it IMPORTED, never for `config.defaultPersona`.

`runImportPersona` loads `config` before `adoptAsDefaultIfMissing` runs, so on a fresh host `config.defaultPersona` names a persona that does not exist — and because opening a vault provisions on demand, the OpenClaw voice key minted a stray `personas/<default>/` with its own `identity.json` and vault while the imported phantom never got its key. Anything per-persona the importer writes takes `result.name` explicitly. Import is OpenClaw-only in the TUI (first-run wizard's opening pick, Configure → New persona): a phantombot persona's identity, vault and `memory.sqlite` rows are not markdown, so the menu does not promise it. Tests: `tests/cli-import-persona.test.ts` (proven by mutation).
