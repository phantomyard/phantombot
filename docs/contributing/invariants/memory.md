# Memory — contributor invariants

Part of the phantombot contributor guide: drawers, the journal, daily recall, drawer import/export, embeddings, the nightly. The index of every invariant is in [`/AGENTS.md`](../../../AGENTS.md). Numbers are stable identifiers — code comments and tests cite them — so a new rule takes the next free number and nothing is renumbered or reused (the one-time renumbering into 71–73 and 77 is recorded in AGENTS.md). Only the `### N.` headings below, each with its `inv-N` anchor, are numbered invariants; a numbered list in an intro section is prose, so never cite its item numbers. Each rule records a real incident; a deliberate, documented trade-off is not a defect.

## Invariants

### 21. Drawer entries are rows now, and only THREE of the five drawers decay (issue #410).

`src/memory/drawers.ts` gives every drawer entry a content-derived id (`sha256(persona, kind, normalizeFact(content))[..16]`) behind `UNIQUE (persona, kind, content_norm)`, so re-filing the same entry REAFFIRMS one row instead of appending a duplicate — the dedupe that step 2 of the nightly asked a model to do by reading a 663 KB file, which is why one live persona reached 64 exact duplicate decisions. Three invariants that look like tidy-up candidates and are not. **`BELIEF_KINDS` is exactly `decisions`, `lessons`, `norms`, and `commitments`/`people` must never be added to it.** Decay is `weight · 2^(-ageDays / halfLifeDays)` off `last_reaffirmed_at`, which is right for a claim about how the world works and catastrophic for an obligation: age makes a commitment MORE urgent, so decaying it silently buries the one thing that needed surfacing, and a person fact ("date of birth") is not less true for going a year unmentioned. Both move by `status` alone, `sweepDormant()` refuses to walk them, and there is a test asserting the membership of the list — if you extend it, you are changing what the system forgets. **Nothing is ever deleted.** `superseded`, `dormant`, `discharged` and `expired` rows stay queryable forever and merely stop being injected; retirement is a ranking decision, never a `DELETE`, the same rule the compaction stage runs on. **Re-filing does not revive a `superseded` entry** (a dormant one it does revive, since a restated belief is live by definition) — otherwise a third-party tool that re-files its old norm on every startup resurrects it over whatever replaced it, and supersession stops meaning anything. Conversely, superseding an id that was never filed is a deliberate no-op, not an error: on a fresh persona the old entry never existed and that must not fail the write of the entry replacing it. `src/memory/drawerIngest.ts` migrates the markdown and **never rewrites or deletes it** — it parses both wild shapes (`###` blocks and the heartbeat's flat `- - [tag] …` bullets), dates each entry from its `## YYYY-MM-DD` section header, and is idempotent, so it is safe to re-run while both representations coexist. Third-party tools file and correct norms through this API, so any change to the contract needs `docs/concepts/memory-lifecycle.md` updated with it. **The rows are WIRED, and since #417 they ARE the source of truth** (the paragraph below was written when the markdown was — read [invariant 23](#inv-23) with it). `src/memory/drawerSync.ts` is the only bridge: `syncDrawers()` runs in the heartbeat right after tagged lines are promoted (so a line captured this cycle is a row by the end of the same cycle), and `orchestrator/screen.ts` briefs the threat judge from RANKED rows instead of the first 16 KiB of a file. Do not invert that direction — nothing in the row path may write markdown, because the files are what the nightly writes, what the owner edits and what phantomtools merges into, and a table that can rewrite them turns a rebuildable projection into a second, authoritative copy. Three details that look incidental: the sync skips a drawer on an unchanged **content hash** (not mtime+size — the compaction stage rewrites drawers wholesale, and a same-length rewrite in the same millisecond is exactly when a skipped sync strands the rows on stale text), the sync marker is written only AFTER a successful ingest (a crash re-runs the drawer rather than marking stale text done), and the briefing's file fallback is **per drawer, not per briefing** — a persona mid-first-sync can legitimately have rows for `decisions` and none for `norms`, and failing open to "no norms at all" is precisely what makes the judge cry wolf on routine operations. The 16 KiB briefing cap is now shared out by `packBriefing` and trims on entry boundaries: before this, a 663 KB `decisions.md` consumed the whole budget and `norms` never reached the prompt, and the cut landed mid-entry so the judge read half a ruling as the whole one. **Any new drawer code needs a caller in the same PR** — stages two and three of #410 shipped a correct schema and a correct parser that nothing imported, which reads exactly like a finished feature in review and was live nowhere.

### 22. Which daily journals reach the prompt is decided in CODE and must stay there (issue #410).

`src/lib/dailyRecall.ts` runs on the prompt path of every turn (`orchestrator/turn.ts`, just before `buildSystemPrompt`): TODAY'S journal always — the day is still open, so nothing has been distilled out of it and if it is not in the prompt it is not in the turn — and YESTERDAY'S **only** when the `.nightly-state.json` ledger has no `ok`-with-every-stage record for that date. This lived in persona `AGENTS.md` prose before, which failed in both directions: an agent could simply not do it, and anything able to write the persona directory could edit the rule out. Load-bearing choices, each with a failure mode if "simplified": **no config switch and no caller hook** — this is not `retrieve`/`pullFacts`, no channel, config file or persona gets a say, because a persona that switches it off loses a whole day of memory the first time a sweep fails and has no way to notice; **no lookback past yesterday** — a second undistilled day is a nightly bug to fix (the sweep retries unprocessed dates by itself), not a reason to grow every prompt forever; **the exclusion is the healthy case, not an omission** — a swept day already lives deduplicated and weighted in the drawers, `MEMORY.md` and `kb/`, so re-injecting the raw file only adds a staler second copy, and the raw journal is a FALLBACK for failed distillation; **an unreadable or missing ledger counts as NOT distilled**, erring toward including the file, which is the safe direction; **the byte cap keeps the TAIL** (a journal is append-ordered, so the newest entries are the ones a turn needs and the oldest are the ones distillation reached first) and is `DAILY_RECALL_CEILING_BYTES` (32 KB per file) plus `DAILY_RECALL_COMBINED_CEILING_BYTES` (48 KB for today and yesterday TOGETHER) — deliberately plain constants rather than the persona's daily compaction budget (`resolveDailyBudgetBytes`, deleted with the daily compaction kind in #472 — do not reintroduce a shared knob), because those two numbers measure different things (how large a CLOSED, fully-distilled day may stay on disk versus how much of an OPEN day a turn is allowed to see) and pinning them together silently clipped the morning off heavy days, 26 KB of 34 KB in one observed case, losing exactly the tagged captures on their way to the drawers. The cap was 256 KB per file until #426, set from the largest daily ever observed on the fleet on the reasoning that a runaway `memory capture` writer was the only thing it needed to stop. That was evidence about the past dressed up as a bound: a persona reached 82 KB in one day and wedged completely, every turn dying at `posix_spawn` with `E2BIG` because the assembled system prompt passed `MAX_ARG_STRLEN` ([invariant 26](harnesses.md#inv-26)). Two things to keep. **A per-file cap is not a budget** — both files can be injected in the same prompt, so 256 KB per file authorised 512 KB of journal; the combined ceiling is what actually bounds the block, and a per-file number alone will always understate the worst case by 2x. **The combined ceiling must stay strictly GREATER than the per-file one** — today is served first and yesterday spends the remainder, so the difference (16 KB) is yesterday's guaranteed floor; collapse that and a heavy today silently deletes an undistilled yesterday, which when injected at all is the ONLY copy of that day anywhere. Note also that these are the belt to the argv spill's braces, not the fix for #426: the spill in `lib/harnessArgvFiles.ts` is what makes prompt size unable to wedge a persona, and this cap is what keeps the prompt a sane size where a spill is available — note the sweep never shrinks these two files either — since #461 `compactionCandidates` does not select daily files at all — so this cap is the ONLY thing acting and every truncation must `log.warn` and name `phantombot memory get memory/<date>.md`, which unlike `phantombot memory today` returns content rather than a path; **"distilled" is judged on the FILE, not the record** — `isDailyDistilled` in `lib/nightly.ts` is the single predicate the sweep and this module both call, and it re-checks the recorded mtime+size, so a day appended to after its sweep is injected again instead of silently lost; **the nightly sweep's own turns are skipped** by the explicit `skipDailyRecall` flag (with the `nightlyConversationKey` namespace as fallback, never a literal string), since a caller-controlled conversation id must not be able to switch journal injection off; **the journal is CONTAINED as well as framed** — `inertBlock` escapes a leading `#` on every line and strips control/bidi/zero-width characters, because [invariant 20](scheduler-and-concurrency.md#inv-20) is that framing alone still permits a whole forged prompt section; and the injected block frames the journal as DATA that cannot authorise an action — earlier turns wrote it, and some of those were driven by untrusted input, so this is the same rule as retrieved context and durable facts. It never throws: any failure degrades to no journal in the prompt, never to a dead turn. Behaviour is documented in [Memory lifecycle](../../../docs/concepts/memory-lifecycle.md); if you change the selection rule, update both. **Since #461 the SOURCE is the `journal_entries` table, not the file** — read [invariant 34](#inv-34) with this one: the WHICH-days rule above is unchanged, but the byte ceilings described here now apply only to the markdown FALLBACK path (a day the nightly has already rendered and pruned), and the open day spends a 16 KB budget over whole entries instead.

### 23. The five drawers are ROWS, not files — and the database that holds them has restore points (issue #417).

`memory/people.md`, `decisions.md`, `lessons.md`, `commitments.md` and `norms.md` no longer exist on a migrated persona: `src/memory/drawerRetire.ts` archives them under `memory/archive/<date>/` (original bytes AND the regenerated export, side by side) and removes them, and `personaScaffold.ts` does not seed them. **There is exactly ONE write path.** The heartbeat FILES a `[tag]` line as a row; it does not append markdown, and the no-database case deliberately leaves the line in the daily file for the next heartbeat rather than falling back to a file write — a second write path is how the drawers ended up with two disagreeing copies of the same entry. The nightly's distill stage files with `phantombot memory drawers --file`; if you ever see the prompt telling a model to append to `memory/decisions.md` again, that is the regression. **Retirement is gated on evidence, never on a flag.** Two gates, per drawer, in `retireDrawers()`: every entry parsed out of the live file must exist as a row (checked by an independent re-parse, not by trusting the ingest's own counts), and the rows must round-trip back out to markdown that re-parses to the same id set (`drawerExport.ts`). A drawer that fails either gate keeps its file, is reported as `held`, and blocks nothing else — one unparseable `lessons.md` must not hold `norms` hostage, and must not be swept along with the four that passed. `renderEntryMarkdown` INDENTS block body lines for the same reason: an unindented body line starting `## ` reads back as a section header and splits one entry into two. Identity survives indentation because ids are computed over `normalizeFact`, which collapses whitespace. **The export is of the WHOLE table**, superseded and dormant rows included — dropping the retired half turns a backup into a summary. **Snapshots: integrity is checked BEFORE the snapshot is taken, always.** `backupMemoryDb()` refuses to snapshot a database that fails `PRAGMA integrity_check`, because rotation would otherwise carry corruption into all five restore points over five nights and delete the last good one — a backup system that destroys exactly what it exists to protect. Snapshots use `VACUUM INTO` (never `cp`: a WAL-mode database is three files and a copy of the main one can be torn in a way `integrity_check` calls clean), restore moves the live file aside to `<name>.pre-restore-<stamp>` instead of overwriting it, and it deletes the `-wal`/`-shm` sidecars — a stale WAL replayed over a restored file turns a recovery into a corruption. `doctor` checks integrity BEFORE anything opens the store (it used to die with a raw `SQLiteError` on the one condition it most needed to report), treats a database that does not exist yet as fine rather than broken, and prints the exact `phantombot memory restore --from <newest good point>` command with the fault.

### 30. Drawer `--import` marker validation is structural, not best-effort (issue #437).

`<!-- id: kind:hexid -->` (`drawerExport.formatIdMarker`) is what lets a hand-edited `--export` file come back in through `--import` without every edit re-filing as a duplicate — unchanged content reaffirms the row the marker names, changed content supersedes it, no marker files fresh, same as plain ingest. Two guards keep the marker from being an attack surface, and both are enforced by CONSTRUCTION rather than by checking a value after the fact: a marker's embedded `kind` must equal the kind of the file being imported (`src/memory/drawerImport.ts` rejects a mismatch outright — a `norms.md` edited to claim `decisions:...` cannot touch a decision, full stop), and the id must resolve to a real row for THIS persona and kind (ids are `sha256(persona, kind, normalized content)[..16]`, a hash rather than a sequential counter, so nothing can be guessed into colliding — a forged or stale id just fails to match and the line degrades to filing as a new entry, never to overwriting the wrong row). Either rejection still files the line's own content normally; only the bogus supersession claim is dropped, and both are counted and reported (`rejected marker: …`) so a tampered export is visible rather than silently absorbed. **Supersede is loud on purpose**: every one is appended to that day's daily file (`- [drawer-import] superseded …`) so a stray keystroke that changes one character surfaces in the ordinary next-turn digest same-day, with no separate confirm/review flow built to carry it. That log line names the row ACTUALLY RETIRED (`ImportEntryResult.supersededId`, set from the resolved live row), not the marker's id, keeping the marker beside it as provenance only when the two differ — from the second edit of one exported file onward the marker names a row an earlier import already retired, so logging it would assert a fork that never happened and omit the real retirement from the only audit channel this mechanism has — reaffirm needed no such thing since it is exactly the existing re-file path. **A marker denotes a LINEAGE, not a snapshot.** An id is derived from content, so a marked line's id stops naming a live row the instant that line is edited and imported — and an export is a file people keep and edit again. A CHANGED line therefore resolves the marker FORWARD through `supersedes` (`DrawerStore.resolveLive`, scoped to persona+kind, cycle-safe via a `seen` set) and supersedes whatever stands in that row's place today; superseding the row the marker literally names would retire an already-retired row and strand its replacement active beside the new line — two active rows disagreeing, the exact duplicate #437 exists to kill. The walk is gated on "the content changed" rather than run up front, because an export lists a superseded row AND its successor each under its own marker, so an unconditional walk would turn an unedited re-import into a supersession. And when the walk lands on a row whose content already equals the line (the same edited file imported twice, the ordinary way to retry), it is a plain reaffirm — asking that row to supersede itself is what `fileEntry` throws on. Stdin form is refused without `--kind` for the same reason `--file` is: the directory form reads the kind off each filename and can loop, stdin carries one document and would otherwise be drained into `DRAWER_KINDS[0]`. Supersession log lines `JSON.stringify` both contents, because a block-form entry is multi-line and a body line spilled to column 0 in the shape `[norm] …` matches `promoteTaggedLines`' `TAG_PATTERN` and gets promoted as a brand-new entry on the next heartbeat. `parseDrawer` strips the marker line before it ever reaches `content` — a block-form entry that let the marker fall through unstripped would bake `<!-- id: ... -->` into the row forever. Applies to all five drawers uniformly since the mechanism only ever touches schema fields (`asserted_at`, `last_reaffirmed_at`, `supersedes`, `status`) every kind already has; only the decay rate differs per kind, not this.

### 34. The daily journal is ROWS; the markdown is a DERIVED artefact the nightly writes (issue #461).

`src/memory/journal.ts` + `journalIngest.ts` + `journalRender.ts`: every capture is a row in `journal_entries` with a content-derived id under `UNIQUE (persona, date, content_norm)`, and **tags are a COLUMN**. That single fact is the fix — `memory capture --tag decision --tag lesson` used to append the same paragraph *once per tag* (`cli/memory.ts`), and `dailyRecall` injected the whole file verbatim on every turn, so 41 % of a measured 17.6 KB journal was the same sentences twice, in every prompt, for the rest of the day. Load-bearing choices, each with a failure mode if "tidied": **recall SELECTS to a budget, it does not dump** — `selectForRecall` spends `JOURNAL_RECALL_BUDGET_BYTES` (16 KB, a fixed constant, not a share of some unbounded total) over WHOLE entries and reports how many it dropped, which demotes the 32 KB `E2BIG` tripwire ([invariant 22](#inv-22)) from load-bearing to a fallback ceiling. **The budget is a HARD bound, including against one row bigger than all of it** — `memory capture` caps nothing, so a single pasted log is enough, and the first draft's "always keep the highest-priority entry" made the budget advisory: a 200 KB capture came back whole, under a 16 KB budget, handing back the unbounded prompt the table exists to bound. An oversized row is never kept in full, is counted apart from an ordinary overflow (the remedy differs — it does not come back on a quiet day), and is left to `memory search`. That is the one case where a day with rows can select nothing IN FULL, so `readDayRows` must report it rather than return `undefined`: falling through to the markdown file there would resurrect, as a byte-slice, the very content the budget just refused. **Overflow is chosen by CLASS before age** — untagged narration goes before a tagged capture, because the byte-slice it replaced cut from the FRONT and so took the morning's decisions first; and a single oversized entry must not end the fill, or a 40-byte decision is dropped because a 4 KB narration came before it. **Truncation must SAY it truncated and where to look** — every row is indexed, so the block names `memory search`; a silent omission reads to the model as absence, which is exactly what makes it re-derive what it wrote down that morning. **What does not fit is DEGRADED, not dropped (issue #467)** — `selectForRecall` returns full entries plus one-line `renderStub` lines (tags, clock, ~80 characters of head text, `… · elided`), interleaved chronologically. The first day measured on the row path settled that: all 30 rows were tagged, so the class tier bought nothing and 14 of the morning's `decision`/`lesson` captures were dropped outright — and a bare count is honest but unsearchable, since a turn cannot look up something it does not know happened. The head text is what carries the search terms; that is the load-bearing part, not the count. Load-bearing details: **stubs are paid for out of the SAME budget** (~15 % reserved, floored at one stub and capped at half the budget, and nothing reserved at all on a day that fits) — a budget that counts only the full entries is not a budget, and the hard bound is what demotes the `E2BIG` tripwire; **the reserve costs at most one full entry on an overflowing day**, which is the deliberate trade: one entry's prose for an index of everything else; **`droppedForBudget` still means "not shown in full" and `droppedEntirely` means no trace at all** — the block must distinguish them, because the remedies differ; **stubs never reach DISK** — `renderEntry`/`renderDay` feed the artefact the nightly writes and `parseJournalLine` reads back, so a stub there would overwrite a day's rows with a summary of themselves. **Ordering inside the tagged class is weighted, not chronological** — `commitment` rows do not decay and sort first (age makes a commitment urgent, the same split `BELIEF_KINDS` makes in `drawers.ts`), everything else scores `weight · 2^(-ageHours / JOURNAL_RECALL_HALF_LIFE_HOURS)` with `decision` > `lesson` > `norm` > `person` > any other tag. The BANDS are strict: no weight, at any age, may lift untagged narration above a tagged capture. The half-life is 48 h so that the weight table can actually change an ordering across a working day — shorten it and weight stops mattering, lengthen it and the day stops being ordered by time. **The decay clock is the newest row in the SET, never `Date.now()`** — selection must be a pure function of its input, or the same journal orders differently depending on when the turn ran and no test can pin it. **Rows are indexed ON WRITE** — `indexOpenDay` publishes the open day as a VIRTUAL note (`files.virtual = 1`) at the path its file will eventually have, so a capture is recallable the same minute and the same key is later overwritten by the real file with no cutover; without it there is an up-to-24-hour hole in which `memory search` cannot see today. Virtual rows are exempt from `refreshStale`'s not-on-disk deletion sweep and supply their own embedding text. **A virtual row OWNS its path against an OLDER file (issue #469)** — the exemption was written into the removal loop and not the reindex loop, and `mtime_ms = -1`, chosen so no "unchanged" shortcut could skip the note, guarantees the opposite the moment a file does exist at that path: every refresh re-indexed the stale `memory/<date>.md` that `absorbDay` leaves on disk by design and flipped `virtual` back to 0. `refreshStale` runs on the heartbeat, on `memory index`, inside `rebuild()` and on every retrieval turn, so `indexOpenDay` won for seconds after each capture and lost permanently — a measured day froze its index at 17:24Z with 15 later tagged rows unreachable while the recall block went on printing "nothing is lost — `memory search`", which makes #468's stubs dead links. So the reindex loop skips a live file whose recorded row is virtual, and it is checked BEFORE `forceAll`, since a virtual note is the one thing in the index not derived from disk. Ownership is not unconditional and not only explicit: the journal relinquishes with `dropOpenDayIndex` after a verified render, but a file MODIFIED SINCE the note was published takes the path anyway, so the cutover self-heals if that call never ran. `files.indexed_at` is therefore load-bearing, which is why `rebuild()` carries each restored note's ORIGINAL publish time — re-dating the snapshot to "now" would make every artefact written before the repair look older than the stand-in it replaced, and the documented repair would pin the stale copy in place. The comparison is STRICT: mtime and `indexed_at` agree only to the millisecond, and a tie must fall to the file, because losing the row is repaired by the next capture republishing it while an over-held stand-in shadows the artefact for good and the rows behind it are pruned once the render verifies. **A merge keeps the EARLIEST `created_at` and UNIONs the tags** — a re-capture is evidence the note exists, not evidence it happened at 17:00. **`source: 'task'` rows are withheld from the block and COUNTED, never deleted** — scheduler bookkeeping injected inline reads as the persona's own reasoning, the same argument `turns.origin` makes. **Rendering is per-DATE, verified, and never touches today** — `renderClosedDays` writes each closed day, READS IT BACK, and only records `journal_days.rendered_at` when a fingerprint of what is on disk matches; today is excluded because it is still being appended to. A nightly that has not fired for three days therefore produces three correct daily files, not one blob. **Pruning requires a SECOND, independent run** — `prunableDates` only returns days verified on an EARLIER date, and the prune re-checks the artefact against the recorded fingerprint before deleting anything; a mismatch clears the record and re-renders instead. The cost of a nightly that dies mid-way is disk space, never content. **A stalled render is an ERROR, not a debug line** — recall reads only today, so a backlog past `JOURNAL_BACKLOG_ALARM_DAYS` (2) would otherwise be completely invisible in the prompt while memory quietly stops being written down. **No bulk migration** — days that predate the table stay the files they already are; `absorbDay` handles only a hand-edited or pre-#461 file, one-way and idempotent, and always runs BEFORE a render so a hand-appended line is adopted rather than clobbered. **The renderer and the parser must round-trip** — `renderEntry` writes the comma SET `[decision,lesson]`, so a parser that only understood `[decision]` reads that marker as CONTENT, a different `content_norm`, a new row minted on every heartbeat; there is a test pinning both directions. **Heartbeat promotion files the same drawer content as the file path did** (`[tag] text · HH:MMZ`, not the bare text): drawer ids are content-derived, so filing the bare text would re-file the entire back catalogue beside its own duplicates. **The write path is single** (`writeJournalEntry`) — and "single" is the claim, not the aspiration: the drawer-import audit shipped appending `memory/<date>.md` directly, which broke the open day twice over, since recall prefers the table once a day has rows (so the audit was never read) and the index's virtual note lives at exactly that path (so the next `refreshStale` replaced a whole day of searchable rows with the audit text). It files rows with `source: 'heartbeat'` — mechanical, but not `task`, which is withheld from the prompt, and #437 requires a supersession to be loud — and `drawer-import:` is plain CONTENT, not a tag, because a tag is a promotion instruction. The markdown append in `memory capture` is a RECOVERY path taken only when the database refuses the write, and the heartbeat absorbs it on the next pass. **`rebuild()` carries VIRTUAL notes across the delete** — everything else in the index is derived from disk and free to throw away, but the open day's only copy is the row, so `memory index --rebuild` (the documented repair) would delete it, re-walk disk, find no file and leave the persona blind to its own morning until the next capture republished it. Recall falls back to the file whenever the table has nothing for a date — a rendered-and-pruned day, or a database that will not open. **The compactor must never select a daily file again** — `compactionCandidates` scans only the budget list (`MEMORY.md`), and the `daily` kind, its 8 KB budget and its 30-day age gate are gone. Trimming a closed day was a real saving while the markdown WAS the journal and was injected verbatim on every turn; it is pure cost now, in all three directions at once — recall never reads a day older than yesterday so the prompt gains nothing, the archive pre-image is kept forever so the pass grows disk rather than reclaiming it, and `renderClosedDays` prunes a day's rows once the artefact verifies, which makes that file the ONLY copy of the day and the rewrite a summary of the last surviving record. Budget the journal at the row layer (`JOURNAL_RECALL_BUDGET_BYTES`), never with an LLM rewrite of the artefact. Tests: `tests/memory-journal.test.ts`, `tests/lib-dailyRecall-rows.test.ts`, `tests/lib-nightlyCompact.test.ts`, `tests/cli-nightly.test.ts`.

<a id="inv-68"></a>
### 68. The memory wizard PICKS the embedding model from the endpoint's own catalogue; the typed prompt is the fallback, not the default.

`src/lib/embeddingModels.ts` `fetchEmbeddingModels` asks `{base_url}/models?output_modalities=embeddings` and, like the audio picker ([invariant 65](cli-tui-and-wizards.md#inv-65)), **requires each row to declare the modality** — OpenRouter's unfiltered `/models` carries no embedding model at all, and an endpoint that ignores the query must not expose its chat catalogue as embeddings. Only when NO row is tagged (OpenAI, Ollama) are the ids filtered by name (`EMBEDDING_MODEL_NAME_PATTERN`); that filter is a heuristic, so the picker always keeps a typed **Other** entry and an empty or failed discovery (ONE 5s deadline across the tagged request and the plain-catalogue retry, never throws) falls back to the typed prompt. Three rules the flow depends on: **(a) the key is asked BEFORE the model**, because the list needs it; **(b) the configured model is always offered and preselected, listed or not**, so a re-run that keeps every default still writes nothing — but only while the base URL is unchanged (`sameEmbeddingEndpoint`), since another endpoint's model id means nothing in the new list; **(c) the screen flow (`tui/memoryFlow.ts`) and its clack twin (`cli/embedding.ts`) build their rows from the one `embeddingModelPickerOptions`**, so the two cannot offer different lists, and both reach discovery through the one `discoverEmbeddingModels({ baseUrl, apiKey })` — named, because two bare strings swap without a type error and a swapped pair silently degrades to the typed prompt. A picked model is still proven by the live validation embed before anything is saved. Pinned by `tests/lib-embeddingModels.test.ts` and `tests/tui-memoryFlow.test.ts`.

### 71. Embedding providers are interchangeable transports, not interchangeable vector spaces.

`src/lib/embedder.ts` resolves none, Gemini, and the
OpenAI-compatible `/embeddings` client; provider-specific prefixes stay in that
resolver. Every note/turn vector carries a deterministic per-row space
fingerprint: provider/model/dimensions, plus the OpenAI-compatible document
prefix. Query prefixes and credentials are excluded. Untagged pre-existing rows
are eligible only for the canonical historical Gemini default
`gemini-embedding-001` at 1536 dimensions, never inferred as
OpenAI-compatible; a successful full reembed tags and cleans them up. Mixed old
and new rows are therefore safe during an interrupted migration. `--reembed`
refreshes FTS first, performs a real document preflight, then force-writes the
current space without clearing the old rows up front; failures return nonzero
and obsolete spaces are removed only after a complete success. A provider,
model, or document-prefix change requires reembed even when dimensions happen
to match. Hybrid search filters by space before applying its independent
dimension guard; when no compatible rows exist it stays on lexical/OKF recall.
The OpenAI-compatible server is separately managed: PhantomBot does not own
its lifecycle, and this feature does not add Ollama, Qdrant, or MCP embedding
clients. Note/KB chunking is provider-aware: Gemini keeps its existing
18,000-character guard, while OpenAI-compatible endpoints default to the
configurable `max_chunk_chars = 5000`. The value is character-based rather
than an exact token guarantee, and must not be described as a llama.cpp
protocol limit. Chunking preserves source text exactly, prunes obsolete tail

### 73. The nightly renders the just-closed day BEFORE it builds the sweep queue (issue #633).

The queue is built from the daily `.md` files on disk, but a day only becomes a file when `renderClosedDays` runs — inside the maintenance stage that USED to sit at the tail of the sweep. So every midnight sweep processed the day before yesterday, the just-closed day waited ~24 h for the next sweep, and doctor showed `1 date pending (oldest …)` every morning (verified on four hosts on v1.1.412). `runMemoryMaintenance` now runs TWICE per sweep with split knobs: at the HEAD (`skipSnapshot: true`) so the render publishes the closed day before `sweepDailyFiles` stats the files, and at the TAIL (`skipRender: true`) so the dormancy sweep + restore point still capture the night's settled end state — a snapshot mid-sweep, or a re-render after compaction, would capture or re-write the wrong state. Placement is after the persona-dir check and the in-flight gate, so a skipped sweep still skips everything. Regression test seeds yesterday's journal rows with no daily file and asserts the same run renders AND distills it; it fails on the old ordering. Tests: `tests/cli-nightly.test.ts`, `tests/lib-nightlyMaintenance.test.ts`.
