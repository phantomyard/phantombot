# Scheduler and concurrency — contributor invariants

Part of the phantombot contributor guide: the turn registry, digests and workspace claims, the tick's wake budget. The index of every invariant is in [`/AGENTS.md`](../../../AGENTS.md). Numbers are stable identifiers — code comments and tests cite them — so a new rule takes the next free number and nothing is renumbered or reused (the one-time split of three duplicated numbers into 71–73 is recorded in AGENTS.md). Each rule records a real incident; a deliberate, documented trade-off is not a defect.

## Invariants

<a id="inv-19"></a>
### 19. A turn is registered for its lifetime, and `tick` defers a wake while the principal is talking (issue #391).

Two turns for one persona can run in DIFFERENT processes — the daemon serving a conversation and `phantombot tick` spawning its own harness — and the existing locks do not cover it: `runLock` guards `run` against `run`, `tick.lock` guards `tick` against `tick`, and nothing sits between the two. Observed twice: both turns worked the same PR and the same unlocked checkout 63 seconds apart, and a contributor got duplicate review comments. `src/lib/turnRegistry.ts` fixes it with a **registry, not a mutex** — one JSON file per in-flight turn under `$XDG_STATE_HOME/phantombot/turns/` (tmp+rename), read by `readdir`. Registration lives in `runTurn` itself (`src/orchestrator/turn.ts`), wrapping the body in a `try/finally`, precisely so a NEW entry point cannot forget to opt in; do not move it out to call sites. Two consumers: `cli/tick.ts` **defers** a due task while a turn is live or within `INTERACTIVE_COOLDOWN_MS` (3 min) of one ending, and `turn.ts` injects a one-line sibling notice into the system prompt for a turn that runs anyway. Load-bearing details, all of which have a failure mode if "simplified": deferral **never writes back to the task row**, so `run_count`, one-off deactivation and `--count` stay honest and "how long have we deferred" is just "how overdue is this task" — no extra column, no migration; it is bounded by `MAX_DEFERRAL_MS` (15 min) because a task that silently never fires is worse than the collision; **command-backed tasks are deferred too**, since the shipped poller contract (`src/persona/builder.ts`, and the README's Jira example) tells them to call `phantombot ask`, which starts a full turn — exempting them leaves a documented back door straight into the bug; and a live-looking entry is only believed if its pid is still the SAME process (`lib/processLiveness.ts`) AND it is younger than `MAX_TURN_LIFETIME_MS` (1 h), because `release()` cannot survive a SIGKILL or an abandoned generator. Kill switch `PHANTOMBOT_TURN_REGISTRY=0` degrades to the pre-#391 behaviour rather than to a crash, and it is off by default under `NODE_ENV=test` so unrelated suites cannot write live-looking entries into the real state dir — a test that means to exercise the registry must set it AND point `PHANTOMBOT_TURN_REGISTRY_DIR` at a temp dir. Both variables and the deferral behaviour are documented in [Concurrent work](../../../docs/operations/concurrency.md); if you change the lifecycle, the locations, or either ceiling, update both.

### 20. A background turn reports what it did, and a shared checkout can be claimed (issue #405).

[Invariant 19](#inv-19) stopped two turns colliding; it did nothing about why the collisions went unnoticed for so long — a turn woken by `tick` streams its reply into its OWN transcript, which the principal never opens, so a commit, a PR comment or a file edit made on their behalf leaves no trace anywhere they will look. Two mechanisms, both built on the registry. **`src/lib/turnDigest.ts`**: a turn whose origin is `task`/`notification`/`internal` writes a digest on exit — trigger, state-changing tool calls (`edit`/`delete`/`move`/`execute` only; reads are dropped, and `execute` is kept in full because we cannot tell `git status` from `git push` without parsing every shell dialect and the asymmetry favours noise) with the paths they named, and its closing summary — into `$XDG_STATE_HOME/phantombot/digests/`. The next INTERACTIVE, **TRUSTED, and PRIVATE** turn gets the pending ones injected into its system prompt and decides whether to mention them. Do not "improve" this into a notification: pushing every poller fire to Telegram breaks the standing don't-notify-unless-material rule and gets the channel muted, which returns us to zero visibility by a longer road; and writing a synthetic turn into the conversation history forges transcript that later retrieval treats as something the principal actually said. Load-bearing details: delivery is marked ONLY after the receiving turn succeeds (at-least-once — a duplicate costs a few lines of prompt, a drop loses the record precisely when the box is unhealthy); the write happens in a `finally`, so a background turn that pushed and then died still reports; only interactive turns receive digests, or two background turns bounce a report between themselves forever; **`trusted !== true` receives nothing and consumes nothing** — origin is NOT trust, a raw `phantombot ask` carrying an inbound email is origin `channel`, and a digest is persona-private context landing in a prompt a stranger is steering; **`replyAudience !== "private"` receives nothing and consumes nothing either** — trust authenticates the speaker, not the audience, so a trusted GROUP turn (`replyAudience: "shared"`) would disclose persona-private state to every member, and a wake-but-silent REACTION turn (`replyAudience: "silent"`, the fail-closed default) would consume a digest into the void — marked delivered, never seen. Omitted = `"silent"`: a caller that does not state its reply is private-and-visible receives no digests and consumes none. the block is capped at `MAX_DIGESTS_PER_TURN` taken **oldest-first**, with the overflow COUNTED in the notice and left PENDING — mark only what you showed, because marking the overflow destroys the record of a turn nobody saw, and draining newest-first starves the tail of a backlog under sustained load; titles, paths, trigger and summary are passed through `redactForLog` **at collection time**, since a tool title is a formatted command line and a digest is durable state a prompt later reads; and collection hangs off the same `onToolCall` hook as the audit log but is INDEPENDENT of it, because disabling `PHANTOMBOT_AUDIT_TOOL_CALLS` is not a request to go blind. **`src/lib/workspaceLock.ts` + `src/cli/workspace.ts`**: `phantombot workspace lock|unlock|status` records an advisory claim on a working copy, attributed to the turn via `PHANTOMBOT_TURN_ID` (set in the harness env beside `PHANTOMBOT_PERSONA`/`PHANTOMBOT_CONVERSATION`); a sibling's live claims are named in the prompt. **The holder is the TURN and liveness comes from the registry — never from the pid that wrote the record.** That is not a preference: the only writer is a CLI that exits milliseconds later, so pid liveness makes every lock prune itself as stale on the next query and the whole feature a silent no-op (shipped that way once; caught in review). `unlock` refuses unless the caller IS the holding turn — including a caller with no turn id at all, since a plain shell dropping a claim it never took is how a cooperative protocol becomes corruption — with `--force` as the deliberate override. Acquire is read-check-write, so it is serialised by a guard beside the lock; without it two simultaneous claims both read "free" and both win. **The guard is a TICKET QUEUE, not one exclusive pathname** (shipped as a single `wx` guard file twice; both cuts leaked the same way). One contested name must be DELETED to be freed, and deletion by pathname cannot be made ownership-safe — between reading a guard and unlinking it the guard can be replaced, and the unlink then removes its SUCCESSOR, handing two callers the section via the cleanup meant to protect it; POSIX has no compare-and-delete to close that with, so no amount of care inside those two syscalls fixes it. Instead each caller publishes its own uniquely named ticket (`<lock>.guard.<uuid>`) and the OLDEST LIVE ticket holds the section. Three properties carry the design and none may be traded away: publication is **write-to-temp + rename**, so a name that exists is always COMPLETE (the `wx`-then-write version left an empty guard whenever a process was descheduled between the two syscalls, and recovery then deleted it with no liveness check at all while its owner was alive and about to continue); every delete names a UUID that belongs to exactly ONE acquisition and is never reused, so no cleanup can reach a successor; and ordering is by **ctime** — the instant a name became visible — never mtime, because a scan can only miss tickets that appeared after it, which is precisely what makes two simultaneous winners impossible. **A ticket is surrendered on OWNERSHIP, never on age** (shipped as age-only twice; caught in review): a holder that is still running is a slow critical section on a loaded box, not an abandoned one, and it can resume INSIDE a section a successor has already entered — so a live owner keeps its ticket however old it gets, and a ticket is ignored only when the kernel says its owner is gone (no such pid, or a pid now held by a different process — start tokens differ). An unreadable start token is NOT evidence of death. **Off Linux that ownership question costs a CHILD PROCESS, which makes it a correctness concern and not a performance one** (shipped unbounded once; caught by the Windows runner). There is no `/proc` on Windows or macOS, so the token comes from `wmic`/PowerShell/`ps` — and the guard asks it about every foreign ticket on every retry, while `registerTurn` asks it about itself. Asking the EXPENSIVE tool first with a 10 s timeout, uncached, turned one contended acquire into dozens of interpreter starts against a ~120 ms budget: the section was never entered at all (`entered: 0`), and a no-I/O registry test timed out at 5021 ms. So: cheapest probe first, a timeout sized to the hot path, the working probe REMEMBERED (including "nothing here answers", or a locked-down box re-runs the whole ladder forever), and one answer cached per pid — every one of which can only go stale toward "still held", the safe direction. A non-zero exit is the probe ANSWERING about a dead pid, not a broken probe; demoting it there gives up the ladder the first time anyone asks about a corpse. `PHANTOMBOT_PROCESS_START_PROBE=0` is the operator off-switch, degrading to the pid-only check. **Every spawn on a Windows-reachable path sets `windowsHide`**: phantombot runs on Windows as a scheduled task with no console of its own, so each child otherwise allocates a NEW console and flashes a black window at the user — on a hot path that is a strobe, not a flicker. The single remaining timeout (`GUARD_ORPHAN_MS`) covers a ticket with no readable owner, which nothing this module writes can produce: corruption gets a timeout because liveness cannot be asked about it. **Release takes that guard just as strictly and refuses (`contended`) when it cannot get it** — "unlink is atomic" is NOT a reason to skip it (shipped that way once; caught in review), because an atomic unlink does not make read → ownership-check → unlink atomic, and the unguarded interleaving deletes a claim a concurrent guarded acquire has just published, leaving its holder working in a tree everyone else reads as free. Refusing cannot strand a workspace now that liveness is turn-based: a refused release self-heals when the holding turn ends, and a guard ticket dies with its holder. Be honest about the scope in any doc or review you write: phantombot is NOT in the path of the `git` a harness runs through its own Bash tool, so this reports and records a claim — it cannot prevent a write, and calling it a lock must not be read as a guarantee. **Pruning a stale lock happens UNDER the guard, with a compare-and-delete on the file's exact bytes** (shipped unguarded once; caught in review). Deciding a lock is stale is not instant — it reads the turn registry — so an unguarded prune reads claim A, a concurrent acquire publishes claim B over it, and the prune then unlinks B: its holder works in a tree everyone reads as FREE. This is the same defect class as the release bug above but on the READ path, which every `workspace status` and every prompt render walks, so it fired far more often. Never unlink a lock or a guard from a read path by pathname. `lock` fails fast rather than waiting (the answer to a held tree is a different directory, never a queue), it fails OPEN if the state file cannot be written — **which means the guard must distinguish EEXIST from I/O failure**; a single `catch {}` reporting a missing or unwritable state directory as `contended` (shipped that way once; caught in review) makes this documented fail-open path unreachable and turns a visibility feature into an outage — and a dead holder is broken on inspection when the registry reports its turn gone, plus a 1 h ceiling, so a crash can never wedge a workspace until a human clears a lockfile. When the registry CANNOT answer (switched off, or an id it has never seen) the lock is kept until that ceiling: guessing "free" on an unverifiable claim reintroduces the collision, guessing "held" costs one clone elsewhere. **Every field either block interpolates into a prompt goes through `src/lib/promptSafeText.ts` first** (shipped raw once; caught in review). A lock's `workspace`/`conversation`/`purpose` and a digest's `trigger`/`summary`/tool-call titles are written by ANOTHER turn, whose input may have come from email, a webhook or a raw `ask` — and they land in a later trusted, tool-capable turn's SYSTEM prompt having passed the threat judge exactly zero times, because the judge screens an untrusted turn's INPUT and nothing re-screens its output once that output is state on disk. A newline plus a `#` heading in a path was enough to end the list and open what read as a new instruction section. `inertText` confines a value (one line, no C0/C1 or bidi/zero-width characters, no backticks, bounded length) and the block's own prose names it as quoted data; **both halves are required** — confinement alone still permits a plausible one-line instruction, framing alone still permits a whole forged section. `redactForLog` is a SEPARATE concern (secrets, at collection time) and does not help here. Kill switches `PHANTOMBOT_TURN_DIGEST=0` and `PHANTOMBOT_WORKSPACE_LOCKS=0` degrade to the pre-#405 behaviour, and both are off by default under `NODE_ENV=test` for the same reason as the registry. Both are documented in [Concurrent work](../../../docs/operations/concurrency.md); if you change the lifecycle, the locations, the caps or the delivery rule, update both.

### 70. A wake's budget is config, and three things are derived from it — never re-hard-code one of them (issue #668).

The scheduled-wake budget used to be a constant 30 minutes in `cli/tick.ts` while every interactive surface used `harness_hard_timeout_s` (default 3600s). Worse than the mismatch: the soft deadline ([invariant 66](harnesses.md#inv-66), default 3000s) only armed when strictly below the hard cap, so on a wake it NEVER armed and a long healthy task was killed with its work discarded. Now: **(a) the budget** is `wakeBudgetMs(taskConfig)` — `[tick] wake_timeout_s` (env `PHANTOMBOT_TICK_WAKE_TIMEOUT_MS`) from the TASK PERSONA's config layer, and when unset the persona's harness hard cap, so the default is not a frozen copy; `0`/negative is ignored, never honoured. **(b) the soft deadline is FITTED, per attempt** (`orchestrator/softDeadline.ts` `fitSoftTimeoutToCap`, applied in `runWithFallback` only when `chainDeadlineMs` is set): under a chain deadline the hard cap is the time REMAINING, so a configured soft deadline at or past that cap becomes 80% of it — for the first attempt, a late fallback, a resumed slot and a nudge pass alike, always from the ORIGINAL request value. It is left disarmed when fitting would leave under 30s to wrap up, and `harness_soft_timeout_s = 0` still disables it. `runTurn` therefore passes the configured value through un-gated for chain-deadline turns; the foreground rule ("strictly below the hard cap, else disarmed") is unchanged, which is what keeps probes, recovery replies and the threat judge nudge-free. **(c) the claim records the run's budget** (`TaskClaim.budgetMs`, written by the runner through `adoptClaimPid(id, pid, budgetMs)` once it has its config; a pid handoff that names no budget preserves it) and the stale TTL is `claimStaleTtlMs` = 2× that budget, floored at the old 60 minutes. This is the part that is easy to forget and expensive to get wrong: with a fixed TTL, any budget above 30 minutes gets a LIVE claim swept as stale and the task dispatched a second time under the running wake — the double fire claim-then-dispatch exists to prevent. Command tasks record their timeout the same way (their default 60-minute timeout used to EQUAL the fixed TTL). `doctor`'s claim-age warning reads the same recorded budget. A claim with no budget (not yet adopted, or written by an older binary) is treated as 30 minutes, i.e. exactly as before. Tests: `tests/orchestrator-softDeadline.test.ts`, the #668 blocks in `tests/orchestrator-fallback.test.ts`, `tests/orchestrator-turn.test.ts`, `tests/cli-tick.test.ts`, `tests/lib-tasks.test.ts`, `tests/cli-doctor.test.ts`, `tests/config.test.ts`.
