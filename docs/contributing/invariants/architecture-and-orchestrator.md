# Architecture and the orchestrator — contributor invariants

Part of the phantombot contributor guide: the turn pipeline, prompt assembly and prompt-cache epochs, the embeddable engine. The index of every invariant is in [`/AGENTS.md`](../../../AGENTS.md). Numbers are stable identifiers — code comments and tests cite them — so a new rule takes the next free number and nothing is renumbered or reused (the one-time renumbering into 71–73 and 77 is recorded in AGENTS.md). Each rule records a real incident; a deliberate, documented trade-off is not a defect.

## Architecture at a glance

- **Citty CLI dispatcher** (`src/cli/index.ts`) → subcommand → orchestrator (for turn-spending commands like `run`, `ask`, `tick`, `nightly`).
- **One-turn coordinator** (`src/orchestrator/turn.ts`) loads persona files, loads recent turns from memory, builds system prompt, **screens untrusted input** (`screen.ts`), runs the harness chain, and persists the user+assistant turns on success.
- **Harness chain** (`harnesses/buildChain.ts` + `src/orchestrator/fallback.ts` + `lib/harnessRunner.ts`) resolves `[harnesses.personas.<name>].chain` first and uses the global `[harnesses].chain` when the persona has no non-empty override. Every turn entry point must pass its persona to `buildHarnessChain`; a daemon or tick process can serve several personas with different primaries. The resolved chain tries primary first and falls through on a recoverable error (with per-harness cooldown for fast fallback) — except for an idle-watchdog kill that had already produced output, which respawns the SAME harness once with a recovery preamble before the chain advances ([invariant 33](harnesses.md#inv-33)). Failover is invisible to the user by design, so `lib/harnessAlert.ts` notifies the owner when that silence would hide something real: a primary failing **authentication** for several turns in a row (still served, but by a fallback that may be billed per token), or the **whole chain exhausted** with no reply delivered. A harness killed by an external SIGTERM/SIGINT (systemd stopping the cgroup during a restart) is classified as shutdown, NOT as a recoverable harness error — otherwise every restart with a turn in flight spawns a paid fallback for a reply nobody receives.
- **Security perimeter** (`lib/threatJudge.ts` + `orchestrator/screen.ts`) — trusted principals act directly; untrusted input is judged in code before any capable harness sees it. See [Security perimeter](security-perimeter.md).
- **Channels** are a channel-agnostic core + thin per-channel adapters (`src/channels/core/` + `src/channels/telegram/`); `phantombot run` is the long-running process. See [Channel layer](channels.md).
- **Credential bootstrap** (`lib/vaultMigrate.ts` → `lib/vault.ts`) imports any legacy plaintext `.env` into the per-persona encrypted vaults ONCE, then `loadVaultIntoEnv()` injects the active persona's secrets into `process.env` at startup; each harness reloads that vault before every spawn so `phantombot vault set` takes effect mid-session. Nothing reads a `.env` file at runtime (#452).
- **Tick fires scheduled tasks** (`src/cli/tick.ts`); 1-minute systemd timer; missed runs are skipped, not piled up. Since #631 dispatch is CLAIM-THEN-DISPATCH: the tick lock covers selection only — each due task is atomically claimed (`TaskStore.claimForRun`: a live claim refuses, a dead-pid/over-TTL claim is stolen), command tasks run in-process first, and each agent wake is a DETACHED `phantombot tick --run-task <id>` child (via `systemd-run --user --scope` on Linux — a plain child of the oneshot unit is killed when the unit deactivates). The claim, not the lock, is the no-double-fire guarantee: the runner writes task_runs and advances the row BEFORE releasing the claim, so a crash between the two is swept, never re-fired. The claim's pid must track the RUNNER, not the exiting dispatcher — the dispatcher adopts the spawned child's pid (`TaskStore.adoptClaimPid`) and the wake child re-adopts its own on boot, or the stale-claim sweep probes the dispatcher's corpse and double-fires a live wake. One wake = one wall-clock budget shared across its whole harness chain (`runWithFallback` `chainDeadlineMs` clamps every attempt to the remaining time) — `[tick] wake_timeout_s`, default the persona's `harness_hard_timeout_s`, see [invariant 70](scheduler-and-concurrency.md#inv-70); `[tick] max_concurrent_wakes` (default 1) queues same-persona wakes in their own lane. A wake child boots with the vault-injected env keys SCRUBBED and `PHANTOMBOT_PERSONA` set to the task's persona, so it re-injects the right vault without inheriting the startup persona's secrets.
- **Heartbeat is mechanical** (no LLM); **nightly is cognitive** (LLM-driven distillation).
- **Prompt-cache optimization preserves PhantomBot's ownership.** The
  orchestrator owns history, retrieval, durable facts, daily recall, and
  restart reconstruction. The opt-in `[prompt_cache]` feature keeps persona,
  policy, security, and instruction-bearing overlays in the system prompt,
  then renders volatile PhantomBot context after canonical history and before
  the current user message for exact-prefix reuse. Its in-process epoch manager appends completed
  context/user/assistant triples until a conservative prompt budget requires a
  deterministic rebase from canonical history. Epoch state is disposable: it
  contains no SQLite rows, Pi sessions, llama.cpp slots, KV blobs, or backend
  handles. The feature is OFF by default; the llama.cpp/Pi cache is never a
  source of durable memory, and a backend that cannot reuse exact prefixes
  still receives correct prompts. If no epoch state exists, PhantomBot starts a
  fresh cold epoch from canonical history. Invalid, corrupt, or inconsistent
  state is discarded; preparation failures fall back to the normal feature-off
  prompt path for that request. Preparation, completion, and discard failures
  are best-effort and must not turn a successful model response into a failed
  user turn; cache-error telemetry contains safe metadata only, never prompt
  content. The opt-in config block is:
  `[prompt_cache]` with `enabled = false` and `max_epoch_bytes = 80000`;
  set `enabled = true` only when the optimization is wanted.
  Epoch entry is observed before screening and cache eligibility, including
  cache-disabled and no-history turns. Epochs explicitly rebase across
  trusted/untrusted transitions, discard before returning a held untrusted
  request, and discard a conversation's prior persona states on persona changes
  so A → B → A cannot revive an old epoch. For untrusted turns, only a returned
  screen pass is fingerprinted as screened; a missing screener is fingerprinted
  as unscreened, and a throwing one holds the turn (issue #663). Effective screening/tool-surface
  changes are explicit security boundaries; restart-required security
  configuration is already covered because epochs are process-local. These
  rules are security lifecycle controls. Security authority comes from explicit
  trust state, threat screening, security/system policy, and epoch invalidation,
  never from prompt position or token order.
  Use this primarily for self-hosted/local inference, such as llama.cpp or vLLM,
  where the operator controls the prefix/KV cache. Hosted-provider users should
  generally leave it disabled: hosted APIs manage caching differently, and an
  epoch can lengthen billed input while PhantomBot cannot control provider-side
  cache behavior.
- **`workingDir` is REQUIRED on every `runTurn` call** (#387) — the harness subprocess cwd, deliberately with no default. Interactive surfaces (telegram, phantomchat, ask, tick, reactions) pass `homedir()`, because the owner asks for work on repos all over their home dir. Machine-driven background turns (nightly) pass the **persona dir**. This used to silently default to `homedir()` and every background caller took the default, so nightly stages woke up in `$HOME` unable to see their own `memory/` from cwd — and went hunting for it. On macOS those recursive walks cross `~/Library/Containers`, tripping the TCC `kTCCServiceSystemPolicyAppData` prompt ("phantombot would like to access data from other apps") once per spawned date. If you add a `runTurn` caller, decide which tree it may treat as home and say so explicitly.

<a id="inv-29"></a>
### 29. The plan-then-confirm gate is CHANNEL-AGNOSTIC and lives in the orchestrator — one copy, overridable, and not in a channel suffix (issues #443, #447).

`CONFIRM_BEFORE_LONG_JOBS_INSTRUCTION` (`src/persona/builder.ts`) is appended by `orchestrator/turn.ts` to every turn that is `trusted`, `isInteractiveOrigin(origin)` and not `replyAudience: "silent"` — the owner has to be on the line to answer it. An UNTRUSTED turn with an interactive origin (an email- or webhook-woken `phantombot ask`) does NOT get it: there the threat judge is the one gate, and "outline your plan and STOP" was a second one nobody could open (see "One gate per channel" under Security perimeter). The block's wording is otherwise unchanged, including its third trigger ("anything that changes state you cannot easily undo"); `ANSWER_LENGTH_INSTRUCTION` was split out and keeps the wider audience (any interactive, non-silent turn). That is deliberate on all three axes and each one was learned the hard way. **(a) Scope is the orchestrator, never a channel.** The original lived in `TELEGRAM_REPLY_INSTRUCTION`, so a persona planned-and-asked in chat while the same persona ran unchecked from an ACP editor, phantomchat or `phantombot ask` — the gate has to sit where every interactive entry point passes, which is the overlay stack in `turn.ts`. Do not add a second copy to a channel suffix; two copies drift and the channel-local one is the one nobody updates. **(b) The threshold is more than THREE tool calls, plus git/build/deploy at any size.** The first version fired at *more than one*, which matches every real request — a review, a triage, a deploy — so it gated work the owner had already explicitly asked for, which is pure round-trip cost. If you find yourself lowering it back toward one, you are rebuilding that. **(c) The user outranks it, in the text itself.** The removed version said `do NOT fall back to a "safe default" and proceed anyway` with no escape clause, and a literal-minded harness kept asking after being told a dozen times to stop; because the block is re-injected verbatim each turn, nothing said in the conversation could outlast it. The wording now states that a direct instruction ("go ahead", "stop asking", or a request already detailed enough to act on) wins for the REST of the conversation. Any edit to this block keeps that clause. **(d) Only where a human can answer.** A nightly (`origin: internal`), a task wake and a silent reaction turn all get the overlay withheld — a turn that stops to ask a question nobody will read is a turn that stalls forever. The same block carries the 50-word answer-length rule for direct questions, for the same channel-agnostic reason. Tests: `tests/channels-telegram.test.ts` (present on chat turns) and `tests/orchestrator-confirm-gate.test.ts` (present for ACP/CLI, withheld for nightly/task/silent).

<a id="inv-39"></a>
### 39. Prompt-cache ordering and epochs must stay disposable.

The opt-in
`[prompt_cache]` feature keeps stable persona/policy/security material
in `systemPrompt`, uses `HarnessRequest.turnContext` for the current turn's
facts, retrieval, daily recall, and display-only channel data, and carries
completed triples in `HarnessRequest.epochTurns`. Adapters must use
`renderConversationPayload()` so the order remains canonical history → retained
epoch context/user/assistant triples → current turn context → current user;
this order exists for cache/prefix reuse only and does not assign trust or
authority.
The orchestrator owns epoch state above the harnesses; it must never become a
second memory owner or persist llama.cpp/Pi cache handles. Do not move
trusted/untrusted policy or instruction-bearing overlays into the data block.
The epoch's exact-prefix guarantee is about PhantomBot's serialized payload,
not full backend KV reuse: stateless Pi/Claude/Codex chat-template role
transitions mean the immediately previous generated assistant response is not
guaranteed reusable on the following request, though it becomes part of the
stable serialized prefix on a later request.

### 42. A hosted prompt-cache key follows a CONTEXT EPOCH, never a conversation (issue #504).

`hostedPromptCacheKey()` in `src/orchestrator/promptCache.ts` is the only sanctioned source of a provider `prompt_cache_key`, and it derives that key from `EpochState.epochId` and a process-local salt — nothing else. Why the seam exists before its first caller does: a cache key is a routing hint, not a semantic boundary. The provider matches on the actual prefix, so a key stable for the *lifetime of a Telegram conversation* would advertise reuse across hours of unrelated topics, while rotating it could never clear a polluted context. The epoch is the point at which PhantomBot genuinely reconstructs the prefix, so it is the only honest lifetime. Everything else falls out of the derivation rather than needing its own bookkeeping: a warm `append` keeps the key; every rebase reason rotates it (`history_changed` — which is how `/reset` and any future compaction surface — plus `trust_changed`, `security_changed`, `system_changed`, `concurrent_turn`, `budget`); a discarded epoch (threat hold, invalidation, cache error) can never be resumed under its old key, because `newEpochId()` is RANDOM per epoch rather than derived from epoch content — a rebase back to byte-identical history must still get a new key, or a held turn's prefix would be re-pinned under the key it was held on. Persona is an INGREDIENT, not a trigger: a conversation is bound to one persona and per-persona state is already keyed separately, so two personas cannot share a key without any change-watching. A turn with `retainEpoch === false` (oversized base) gets NO key at all — there is no retained prefix, so pinning one would advertise a prefix that will never be reused. The salt also keeps the value non-reversible: a persona name, conversation id or channel must never be recoverable from a string handed to a third party, and two processes serving the same conversation must not collide. Tests: `tests/prompt-cache-hosted-key.test.ts`.

### 45. Reply LANGUAGE is stated to the harness as ONE deterministic rule that names the SOURCE — it is never inferred from turn content, never classified in code, and never restated a second time (issues #534, #548, #580).

`REPLY_LANGUAGE_INSTRUCTION` (`src/persona/builder.ts`) is pushed by the ORCHESTRATOR (`orchestrator/turn.ts`) as the LAST overlay on EVERY turn: reply — including pre-tool narration — in the language of the user's LATEST message, and here is the list of things that are DATA and do not decide it (document being read, tool output, retrieved memory, journal, quoted reply, group catch-up, the persona's own previous turns). Four things are load-bearing. **It is UNCONDITIONAL.** #534 shipped a function-word classifier that resolved a concrete language and injected "Reply in English"; when it could not decide it injected NOTHING, so Chinese, Russian, Greek and Arabic messages — zero score in a Latin-script lexicon — got no rule at all and drifted worst. Any change that makes injection conditional on a detection reintroduces that hole; `tests/channels-telegram.test.ts` pins the rule's presence on CJK/Cyrillic/Greek/Arabic input. **Do not reintroduce a language list.** Widening the lexicon is unbounded maintenance that still cannot separate the Latin-script languages this deployment mixes daily (en/es/nl/fr/de); pointing at the message is free and total. `src/lib/replyLanguage.ts`, its state file and `PHANTOMBOT_REPLY_LANGUAGE_STATE` were deleted in #548 — do not resurrect them. **There is exactly ONE copy, and it sits LAST.** It lived in the Telegram and phantomchat `systemPromptSuffix` arrays until #580, which meant two copies of one rule and NO language rule at all in ACP, the TUI or `ask` — all of which call `runTurn` directly. Moving it to the orchestrator fixed both at once. Last position is not cosmetic: whatever sits last is the freshest instruction the model reads. Moving another overlay after it, or copying the rule into a channel suffix or a persona `IDENTITY.md`, re-opens #534/#535 — a per-persona restatement of this rule is an ANTI-PATTERN, not a reinforcement. **Nothing downstream may mention language at all.** `PRE_TOOL_NARRATION_INSTRUCTION` (`src/persona/builder.ts`) held the last slot until #580 and carried its own language paragraph, illustrated with one named language ("if the user wrote to you in Spanish, narrate in Spanish"). Across ~14,800 scored turns on two personas, 100% of measured violations were narration lines in exactly that language while the reply body was correct — body leaks: zero. The block now says nothing about language, and `tests/orchestrator-turn.test.ts` asserts the narration block contains no language text and that the reply-language block is last. Recovery (`orchestrator/recovery.ts`) points at the user's message for the same reason. Enforcement beyond prose (detect each narration line's language in the chunk stream and STRIP on mismatch — never regenerate, narration is cosmetic) is specified in #580 and not yet built; prose here is compliance, not a guarantee. Documented in [Voice and reply behavior](../../../docs/how-to/voice.md). Tests: `tests/channels-telegram.test.ts` and `tests/channels-phantomchat-server.test.ts` (presence at both chat channels), `tests/orchestrator-turn.test.ts` + `tests/cli-ask.test.ts` (position, single copy, and the narration block's silence on language).

### 46. Fleet-wide behavioural rules ship as PROSE IN THE BINARY, not as a file on the host.

`LOCAL_HYGIENE_SECTION` in `src/persona/builder.ts` is pushed by `buildStableSections`, so every persona on every host gets it on every turn and a release updates it everywhere at once. The alternative designs were considered and rejected: a persona's own `AGENTS.md` is OPTIONAL (`create-persona` scaffolds SOUL/IDENTITY/MEMORY only — it is read-if-present in `persona/loader.ts`), owner-editable and per-host, so a rule written there reaches exactly the personas that already knew it; `SOUL_TEMPLATE` is written only when the file is MISSING (`personaBackfill.ts`), so it never reaches an existing persona; and rewriting a managed section of a host file at boot buys no tokens (loader splices `AGENTS.md` into the same system prompt, inside the same cache prefix) while adding file mutation on every start and merge conflicts with hand edits. The split is: the BINARY states the principle, the persona's own files hold the concrete paths. Content rules for this section — each line is a real incident generalised (a dev checkout scheduling live systemd units and `bun test` rewriting live host state → the scratch-copy line; a stale shadow memory directory swallowing writes → the remembered-paths line; plaintext credentials in settings/config files → the vault line; a `GITHUB_TOKEN` env var shadowing the classic PAT and duplicate norms making an injected rule nondeterministic → the one-canonical-place line) — and it carries NO git, repo or branch vocabulary, because most operators are not software engineers and none of these failures are developer-specific. It is on every prompt of every persona forever, so it stays short. Tests: `tests/persona-builder-hygiene.test.ts`. **`buildRuntimeSection` (same file, issue #616) is the same pattern for RUNTIME SELF-KNOWLEDGE**: the prompt described every tool and nothing about the process holding them, so the model under-reached — it guessed at its own plumbing and re-derived facts `phantombot --help` answers. The section is GENERATED from live state (`VERSION`, `process.platform`), never hand-maintained prose about a release, because a stale self-description is worse than none: the model cannot tell it is stale. Both values are constant for the process lifetime, so it stays in the CACHEABLE stable prefix (`buildStableSections`) — do not move it below retrieved context or the journal. Content rules: it claims only what is true of EVERY install (the subsystems phantombot always owns) and never names a channel, harness, MCP server or persona, since those come from the sections built off live config and a guess would be a confident falsehood in every prompt on the host; the repo URL is a POINTER for reading the implementation, not a substitute for the inlined facts (a native Windows turn may have no fetch tool, and following a link costs a turn); and it does not restate the tool sections that follow it. **Three claims in it look universal and are not — review of #617 blocked on all three, and each is now pinned by a test.** (a) It must NOT say the surrounding process is LONG-RUNNING: the same stable prefix is built for one-shot processes — `phantombot ask`, a `tick` scheduled turn, the nightly, the phantomchat greeter (`channels/phantomchat/greet.ts`) and the threat screen (`orchestrator/screen.ts`) all call `buildSystemPrompt` outside the channel daemon — so it says RUNTIME/orchestrator, which is true of every path. (b) Other personas are CONDITIONAL ("any other personas configured on this host"): a single-persona host has none and this function is handed no persona inventory. (c) The repo is REFERENCE MATERIAL, not authority: a bare `github.com/<org>/<repo>` URL resolves the CURRENT DEFAULT BRANCH, which diverges from the running binary on the next merge, so the "this is the code you are running" claim is made only against the `v<version>` release tag and only when the build has one (a `-dev` build says it is unreleased and claims no tag). Telling the model to treat fetched source as authoritative would also invert the security perimeter, which classes web and tool output as untrusted data — so what the section marks authoritative is LOCAL: itself, `phantombot --help`, and what the runtime does when you run it. Tests: `tests/persona-builder-runtime.test.ts` (wiring on both trust paths, stable-prefix placement, live version/platform, no host-specific claims, plus one test per claim above; proven by removing the `sections.push` — 3 failures — and by restoring the pre-review prose — 6 failures).

### 64. The embeddable engine (`src/engine/`) is a FACADE over the daemon's own functions, scoped by AsyncLocalStorage — never by `process.env` (`phantombot/engine`, docs/reference/engine.md).

An application imports `createEngine({ root })` and gets personas, memory, the threat screen, the harness chain, structured output and the decision model. Five rules, each with a failure it prevents. **(a) Scope, don't mutate.** `lib/engineScope.ts` carries the root in an `AsyncLocalStorage`; `xdgConfigHome`/`xdgDataHome`/`xdgStateHome`, `writeLogLine` and `withPersonaEnv` consult it first. Outside a scope every one of them is byte-identical to before — the daemon and the CLI never enter one, which is what makes the library additive (`tests/lib-engineScope.test.ts` pins the outside-scope shapes). Rewriting `process.env` instead would repoint the host daemon if both ran in one process, and would leak between two engines. **(b) Host LOCATION overrides are ignored inside a scope.** `HOST_LOCATION_ENV` (`PHANTOMBOT_CONFIG`, `_PERSONAS_DIR`, `_MEMORY_DB`, `_DEFAULT_PERSONA`, `_STATE`, the registry/digest/lock/state-file dirs) is read through `hostLocationEnv()`, which returns undefined in a scope, and `withPersonaEnv` strips them from a scoped child while adding the scope's `XDG_*` so a tool that shells back into `phantombot` reads the same root. A new location override MUST join that list, or an app silently writes into the host's personas. Tuning variables are deliberately not listed. **(c) Async generators and abort listeners escape the scope.** A generator body resumes in the context of whoever calls `next()`, and an abort listener runs in the context of whoever called `abort()` — the application's. So the turn stream is wrapped in `bindToScope`, and every `abort()` the engine triggers (cancel, external signal, `close()`) goes through `engine.enter()`. Without it harness kill logs land on the host's stderr (caught live; `tests/engine.test.ts` pins it). **(d) Trust is explicit and tools are off.** `source` is REQUIRED (`"untrusted"` screened, `"principal"` not) and `tools` defaults to `"none"`, which `runTurn` now accepts and fingerprints as an empty grant. `askJson` retries only tool-less turns by default, because a retry re-runs a turn that may have had side effects. A held turn yields ONLY a `held` event — its notice is not reply text. **(e) One owner per root, and no shared vault mirror.** The root is `flock`ed (`<root>/state/phantombot/engine.lock`); secrets are written to the persona vault WITHOUT the wizard's `process.env` mirror, since a mirrored key becomes ambient and readable by every other persona in the process. `vault.ts`'s per-spawn config cache is keyed by config home for the same reason. App conversations are `app:<key>`: turns stamp `private`, the room reads `multi-party` (`roomAudience`), so one end user's turns never surface for another. **(f) The decision model is a SLOT, not a vendor** ([invariant 63](security-perimeter.md#inv-63)): `DecisionModelConfig.provider` is any string — `openrouter`/`typesafe` are built-in transports, anything else is a custom decisions provider that MUST carry `baseUrl` (refused at `configure`, before any write, because the loader would otherwise refuse the persona), with its own `keyName`; a provider switch drops the previous `model`/`base_url`/`key_env`. Public names and docs say "decision model"; Jev is only the default. The on-disk `[jev]` block is the wire contract and stays. The public contract is `src/engine/types.ts` + `errors.ts`; `bun run build:engine-types` regenerates the COMMITTED declarations in `types/engine/` (with `stripInternal`; it FAILS if a public declaration imports an internal module) and `tests/engine-public-types.test.ts` fails when they are stale. They are committed because a git-tag install (`github:phantomyard/phantombot#v1.1.N`) runs no build step — without them an application's typecheck would fall through to phantombot's internal sources. **(g) Credentials never cross the scope through `process.env` (PR #608 review).** Every adapter builds its child env from `harnessSpawnEnv(persona)` (`lib/vault.ts`), never from a `process.env` it reconciled itself. Outside a scope that is `reloadVaultForPersona` + `process.env`, byte-for-byte the daemon's behaviour. Inside a scope it is a per-spawn COPY with the vault applied ON TOP: the vault WINS over the application's ambient value — the daemon's sticky rule protects an operator's deliberate shell export, but inside an application the "shell" is the application's own process, and honouring it handed the host's key to every tenant persona, billed to the wrong account, with `secrets.has()` still saying true — the application's env is never written (a persona's secrets used to stay readable by the app, its libraries and the next persona's turn until a later reload reconciled them away), and there is no shared state between concurrent turns (the old safety invariant was "no `await` between the reload and the snapshot", stated nowhere). A persona-LESS request — the threat judge, durable-fact extraction — draws from `scope.persona` (`Engine.run/enter/bind` take the persona; `Persona` always passes its own), because `default_persona` under an engine root is host-shaped and has no vault, which left the judge keyless and screening failing OPEN. The scoped branch FAILS CLOSED (PR #608 round 2, Kai/Robbie): an unopenable vault or a persona directory that does not exist THROWS and the spawn is refused (surfaced by the chain as `harness_failed`, never reaching `Bun.spawn`), and every row that fails to decrypt is DELETED from the copy so neither the vault's nor the application's value under that name reaches the child — the daemon's tolerance (keep the injected env on a transient open failure, skip a bad row and load its neighbours) is right on an operator's own box and is the wrong-account substitution on a tenant's, because the name that fails is exactly the one whose ambient value must not stand in. There is deliberately no `catch` in that branch: a degradation path that returns the application's env is the bug, and one no test could prove. Every route is mutation-proven (`tests/engine.test.ts` "credentials"). Do not reintroduce a `process.env` credential read in an adapter; read the spawn env. **(h) `tools: "none"` never runs on codex, and neither does the threat screen** (`READ_ONLY_TOOLLESS` in `engine.ts`): codex maps a tool-less request to `--sandbox read-only`, a shell that can still read `identity.json` and the vault from the default cwd. The daemon's judge accepts that floor because only its score is consumed; an application cannot audit what the judge read, and the judge is spawned in the persona dir holding the untrusted text itself, so under an engine the screen runs on the SAME tool-less set as a `"none"` turn. A `"none"` turn with nothing tool-less in the chain is `not_configured`, and so is ANY untrusted turn on such a chain, whatever `tools` it asked for and even with the decision model judge enabled — that judge decides first but the harness judge is its fallback, and `makeScreener` with an empty chain has nothing to judge with, so a codex-only chain plus a decision-model outage would hold every untrusted turn (it used to pass them to codex with full tools, unscreened — issue #663). The refusal happens before any harness runs. A new harness that only reaches read-only joins the set. **(i) A stream is checked against `closed` when its body STARTS**, not only when `turn()` is called: streams are lazy, and one created before `close()` and iterated after it would reopen memory under a root another engine may already own. **(j) A native provider switch carries no key**: `PHANTOMBOT_PI_API_KEY` is one slot, so `configure` refuses a provider change without `apiKey` while a key is stored, before any write ([invariant 63](security-perimeter.md#inv-63)'s rule, applied to the brain). **(k) Tool children carry `PHANTOMBOT_ENGINE_SCOPE=1`** (`scopedChildEnv`) and `migratePlaintextToVault` returns early on it — `~/.env` is a HOST path, and a `phantombot` CLI the model ran under the root would otherwise fold the host operator's plaintext secrets into the application's vaults. The root's three directories are created `0o700`. Not included yet, and documented as such: engine-driven heartbeat/nightly (the heartbeat heals host service units, so it must not be pointed at an engine root), chat channels, Node/Deno. Tests: `tests/engine.test.ts` (including the real Codex adapter driven through `Persona.ask()`), `tests/lib-engineScope.test.ts`, `tests/engine-structured.test.ts`, `tests/vault-migrate.test.ts` (abort scoping, XDG scoping, vault precedence, the closed-stream guard, the codex exclusion for both the turn and the screen, the provider-switch refusal, the legacy-import guard and the directory mode all proven by mutation).

### 69. A turn's scratch files live under the PERSONA dir, are named INJECTIVELY, and the env var is RUNTIME-owned (issue #661).

`src/lib/scratch.ts`: every harness subprocess gets `PHANTOMBOT_SCRATCH` pointing at `scratch/<tier>/<conv>[/<turn>]` under the persona dir — the #365 rule (persona-owned, never the shared system `/tmp`) applied to a turn's working files, since repro clones and test output carry the same conversation context a spilled payload does. Four invariants, each with the failure it prevents. **(a) The env var is set by the runtime and never inherited.** `withPersonaEnv` (`lib/envBootstrap.ts`) sets it AFTER the base spread and DELETES an ambient value when the turn has no scratch dir, so an inherited `PHANTOMBOT_SCRATCH` can never point a turn at an attacker-chosen tree. **(b) Dir names are `<slug>-<full sha256 hex of the raw key>` (`scratchDirName`), never the slug alone.** `sanitizeScratchName` is lossy in two ways — substitution (everything outside `[A-Za-z0-9._-]` folds to `_`) and truncation (96 chars) — so `matrix:room/a` and `matrix:room:a` aliased into one shared trusted tree and could read or overwrite each other's files (#662 review). The digest is over the FULL raw key, so distinct keys cannot alias and a conversation keeps its dir across turns and restarts; the digest is NOT truncated to a short prefix — the 12-hex first cut was found by a birthday search in ~22s on this repo's own host (two distinct keys sharing slug `matrix___________________________` and digest `45b4c10eeee5`), and 48 bits is not an isolation boundary, so the full 64-hex digest IS the boundary. Any NEW name derived from a conversation or turn key goes through `scratchDirName`, and all three collision classes (substitution, truncation, digest birthday) stay covered in tests. **(c) Untrusted scratch is ephemeral by CONSTRUCTION, not by a flag someone remembers** — per-TURN nesting `<conv>/<turn>` (two concurrent untrusted turns in one conversation can neither read nor delete each other's files) plus teardown in `runTurn`'s `finally` (covers early-hold, throw and clean drain), containment-guarded to `scratch/untrusted/` so a corrupted `TurnScratch` cannot become an `rm` primitive. Trusted scratch is cross-turn and swept on the same deliberately-fat 24h-idle TTL as `PERSONA_TMP_SWEEP_MAX_AGE_MS` (#367), so a running turn's files are never reaped mid-run; the sweep runs on PROVISION, so the TTL cannot be forgotten. **(d) Provisioning fails OPEN** — a filesystem error degrades the turn to "no scratch dir", never to a dead turn. The prompt notice names the ENV VAR, not the path (the path is runtime-owned; keeping it out keeps volatile absolute paths out of the byte-compared prompt-cache layout), and every on-disk name it lists is attacker-influenced: rendered through `promptSafeText`, capped at 20 entries / 1200 chars. Tests: `tests/lib-scratch.test.ts` (both collision classes pinned at name and provision level, and mutation-proven: dropping the digest turns 4 red). Documented in the README's "Scratch workspace" subsection; if you change the layout, the naming or the env contract, update both files.
