# Harnesses — contributor invariants

Part of the phantombot contributor guide: the tool watchdog, spawn/kill/timeout coordination, the fallback chain, resume and nudge, native Pi. The index of every invariant is in [`/AGENTS.md`](../../../AGENTS.md). Numbers are stable identifiers — code comments and tests cite them — so a new rule takes the next free number and nothing is renumbered or reused (the one-time renumbering into 71–73 and 77 is recorded in AGENTS.md). Only the `### N.` headings below, each with its `inv-N` anchor, are numbered invariants; a numbered list in an intro section is prose, so never cite its item numbers. Each rule records a real incident; a deliberate, documented trade-off is not a defect.

## Coder-swap empty completion recovery (issue #692)

The existing ladder in `src/harnesses/pi.ts` treats a completed attempt with no
usable assistant text and no tool progress as a recoverable empty result.
Whitespace, reasoning/replay, and lifecycle/completion markers are not answers.
Hold terminal success until classification; discard leading whitespace only for
empty attempts. Empty results and eligible explicit errors share the existing
three coder attempts, followed by one primary attempt. Preserve the existing
routing/manual overrides, timeout policy, cancellation, hard-cap, terminal-error,
rate-limit and outer fallback rules. Never replay usable text or tool progress.
Log the fixed empty-result reason through existing retry/exhaustion diagnostics,
without including reply/reasoning content or tool arguments.

### 9. Adding a new harness — three places that must be touched, not one.

`src/harnesses/buildChain.ts` (factory: instantiate the wrapper class), `src/cli/harness.ts` (`SUPPORTED_HARNESSES` for the TUI + `detectAvailability` for the binary-on-PATH check), and `src/config.ts` (Config type slot + loader for `[harnesses.<id>]`). ### 26. Two different kernel limits govern argv, and the one that bites on Linux is per-STRING (issue #426).

`getconf ARG_MAX` reports ~2 MB and bounds argv **plus** the environment in total; `MAX_ARG_STRLEN` is **131,071 bytes for a single argv element**, hard-coded as 32 pages in `fs/exec.c`, with no sysctl and no ulimit to raise it. `lib/harnessArgvFiles.ts` cited the wrong one for a year and gated its temp-file spill on `platform === "win32"` alone, on the stated reasoning that "POSIX ARG_MAX is ~2 MB, so phantombot's rendered payloads pass fine as argv". They did not: a persona whose journal grew past ~128 KB wedged completely, every turn dying at `posix_spawn` with `E2BIG: argument list too long` on a box with gigabytes free. `argvNeedsTempFiles(platform, payloadBytes)` is therefore **size-aware everywhere and unconditional only on Windows** — Windows' limit is on the WHOLE command line (~8,191 chars), which no per-payload test can clear because the other args share the same budget, while on POSIX any payload past `ARGV_SPILL_THRESHOLD_BYTES` (96 KB, ~35 KB of headroom) goes to a temp file. Load-bearing details: **measure `Buffer.byteLength`, never `.length`** — a journal of em dashes or CJK is up to 3x its character count in UTF-8, and a char-based threshold would leave a 270 KB argv inline and reproduce the bug exactly; **spill early rather than snugly**, since an over-eager spill costs one small file write and one read in the child while an under-eager one takes the persona off the air entirely; and **claude is the only harness that needed this** — pi already spills unconditionally, codex sends everything on stdin, and claude's conversation is on stdin too, so `--system-prompt` is the single argv element at risk and is what gets sized. The second half of the same bug is in `orchestrator/fallback.ts`: `Bun.spawn` **throws** E2BIG/ENOENT/EACCES rather than yielding an error chunk, and an uncaught throw propagated straight out of `runWithFallback`, so the chain never advanced and one unspawnable primary silently disabled every fallback behind it — the log read `trying harness claude attempt 1 of 2` and then nothing. The `for await` over `harness.invoke()` is wrapped: a throw becomes the recoverable failure the loop already knows how to handle (cool off, alert, fall through), and on the last harness it becomes an error chunk plus a `noteExhausted`, never a rejected iterator. `describeInvokeThrow` glosses E2BIG with the real limit, because the raw message "argument list too long" sends an operator to `getconf ARG_MAX` and a dead end. Treat any harness adapter as able to throw; the chain's job is to survive it. Finally, **the spill is an optimisation, never a precondition**: it touches a filesystem, and a filesystem can refuse (full disk, read-only mount, drifted perms on the persona dir), so `claude.ts` wraps the `createHarnessTempDir` / `file()` pair in its own `try` and degrades to the inline `--system-prompt` with a `log.warn` rather than letting the failure leave `invoke()`. That degraded path is honest and bounded — on POSIX anything in the 96 KB-128 KB band still spawns fine inline, and above it (or on Windows, where the whole command line is the budget) the spawn fails as a NORMAL harness error the chain can act on. A partially-created temp dir is cleaned up on that path rather than leaked. The rule this instantiates is the general one: on a headless box nobody is watching, so a best-effort convenience must never be able to take the daemon off the air. **Spilled payloads land under `<personaDir>/tmp`, never the shared system `/tmp`** (issue #365) — a system prompt carries that persona's memory, drawers and conversation, so all three production callers (`orchestrator/turn.ts`, `lib/threatJudge.ts`, `orchestrator/durableFacts.ts`) resolve a persona-scoped `tmpBaseDir`; the judge and the extractor derive it from the same `cwd` they already floor at `homedir()`, so even the degenerate no-persona-dir case stays in a directory owned by the running user. `createHarnessTempDir`'s `os.tmpdir()` fallback survives for tests only and now `log.warn`s when taken, because a production spill landing there is a plumbing regression rather than a configuration choice.

### 31. There is ONE harness detector, and a persisted bin is a CACHE that must be platform-checked (issue #450).

`resolveHarnessAvailability()` (`src/lib/harnessAvailability.ts`) is the single resolver: absolute path with `PATHEXT` suffixes, then `PATH`, then the `harnessSearchPath()` sweep (`%APPDATA%\npm`, `~/.bun/bin`, nvm/fnm node dirs), then an absolute -> bare-name retry for a stale configured path. `checkConfiguredHarnesses` and `detectAvailability` (`src/cli/harness.ts`) both go through it, and nothing may reintroduce a second one. The bug this closes: the `phantombot harness` wizard and `init` called a bare `whichBinary()` on the configured bin, skipping the sweep AND the retry, so `doctor`/`run` resolved claude while the wizard reported NOT FOUND on the same config — **the wizard must never be a weaker detector than the daemon it configures**, because it is the tool an operator reaches for precisely when detection is already suspect, and a false NOT FOUND there sends them to reinstall a harness that was working. Separately, `loadConfig` reads `state.harness_bins.<id>` AHEAD of the bare-name default, and `state.json` lives in the DATA DIR, not beside `config.toml` — so a once-resolved absolute path survives editing or deleting the config file entirely and there is no obvious knob that clears it. A path written by a WSL/Git-Bash run and read back natively on Windows is the live case: `path.win32.isAbsolute("/bin/claude")` is `true`, so it looks well-formed, never resolves, and reads to the user exactly like a bad hardcoded default — which is why #450 was reported against `config.ts` where the default is in fact already the correct bare `"claude"`. `usablePersistedBin` (`src/lib/harnessBinPath.ts`) therefore drops a persisted value whose path FLAVOUR cannot belong to this platform (POSIX-rooted on win32; drive-letter or UNC on POSIX) so the chain falls through to the default the sweep can find. Two properties to keep: it is a **pure string test, never a filesystem check** — a well-formed path that merely does not exist right now is KEPT, because reporting a missing install against the configured path is the honest diagnostic and silently rewriting it would hide an uninstalled harness; and it is applied at the READ in `loadConfig`, not at the write in `saveHarnessBins`, so an already-poisoned `state.json` on a live box is neutralised without a migration. Documented in `docs/operations/harness-detection.md`; if you change the precedence chain or the sweep, update it.

### 33. A turn wedged mid-flight is RESUMED with context, not dropped — and the trade that buys is stated, not hidden (issue #459).

`orchestrator/resume.ts` + the attempt loop in `fallback.ts`: when a harness is killed by the IDLE watchdog *after* it had already streamed output, the orchestrator respawns that same harness ONCE, in the same chain slot, handing it a preamble built from the killed attempt's chunk log — the narration the user can already see, plus the `progress` titles of the tool calls that were in flight. Before this, that case had no recovery path anywhere: pi's coder ladder is gated on `!producedOutput` precisely so it never replays a side effect, and a single-entry chain (`chain = ["pi"]`, how every pi-only persona is configured) has no next harness, so the turn was dropped and the user got an apology bubble. Six such kills on one persona in a week. Load-bearing, each with a failure mode if "tidied": **the branch keys on the STRUCTURED `killCause` on the error chunk, never on the message text** — `killCauseToErrorChunk` sets it for all five causes and there is a test pinning each, because recovering the distinction by matching on the prose is one rename away from silently disabling the whole feature. **Only `idle` qualifies.** A hard-cap `timeout` is the one timer that must stay final (resuming it multiplies a 60-minute cap), `startup` means no output at all and the ordinary fall-through already covers it more cheaply, `aborted` is `/stop`, `policy` is a tripwire. **Only after output.** With nothing produced there is nothing to resume WITH, and the plain chain is both safer and faster. **One resume per harness per turn** (`MAX_RESUME_ATTEMPTS`): a second wedge is not transient and each attempt costs a full idle window of the user's patience. **The preamble must not claim the tool failed.** The stall may have happened AFTER a tool completed perfectly; the honest — and the only safe — instruction is that each call *may or may not have applied* and current state must be VERIFIED before anything is redone. Weaken that wording into "retry the call" and this becomes the blind replay it was designed to avoid. **The resume is preferred over falling through even when a next harness exists**, because the harness that was making progress holds the context a cold hand-off to a different model does not. **No config flag, deliberately** (Andrew, 2026-08-27): an opt-in fix for a user-visible failure is a fix nobody gets, and the guarantee being traded away ("never silently replay a side effect") is replaced by a better one ("never silently drop a turn") — with *silently* doing the work, since the recovery attempt is told exactly what is uncertain. The chunk log is per ATTEMPT, not per harness slot, or a second wedge would describe the first one's calls. **Only a structured `chunk.tool` counts as a started tool call** — the chunk contract allows bare `progress` for diagnostics and liveness lines, and letting one satisfy the output predicate would both steal the turn from the cheaper no-output fall-through and tell the model that a version warning may or may not have applied. **A resumed slot's terminal `done.finalText` is STITCHED across both attempts**, because that field is contracted to be the sum of the slot's text chunks: `runTurn` persists it, voice and other non-streaming channels deliver only it, and the Telegram/PhantomChat transports diff it against what they already sent to compute the remaining suffix — forwarding the recovery attempt's own `finalText` would drop the pre-kill text from history and from voice, and make the transports resend the tail. Tests: `tests/orchestrator-resume.test.ts`.

<a id="inv-44"></a>
### 44. Two Pi providers are two harness INSTANCES, never one shared Pi config.

Brain and `phantombot harness` encode Pi-to-Pi failover as `pi-primary -> pi-fallback`, backed by `[harnesses.instances.<id>]`. Each instance owns routing and a distinct persona-vault API-key name, and its full instance id must survive into `Harness.id`: cooldown, alert incidents, status/model reporting, probing, and fallback decisions key on that id. Collapsing either instance back to bare `pi` couples provider failures and credentials. Existing bare `pi`, `[harnesses.pi.routing]`, and `PHANTOMBOT_PI_API_KEY` are the backward-compatible default instance and must keep working unchanged.

<a id="inv-48"></a>
### 48. `recoverable` on an orchestrator error chunk describes what the ORCHESTRATOR may do, NOT whether the user was spared — never filter on it at a channel.

`runWithFallback` consumes the recoverable errors it can fall through from, so the only error chunks that reach a channel are terminal or chain-exhausted: both mean no reply. `chatSession` used to drop them, which turned a dead harness into a blank bubble with no error anywhere. Every error chunk now surfaces, and a turn that produced no text renders `(no reply)` in BOTH the TUI and `--no-tui` — an empty bubble is never a valid render.

### 56. The native harness runs the pi engine EMBEDDED in the binary; everything else about pi is the host's business.

Harness ids: `native` (the engine compiled in via `@earendil-works/pi-coding-agent`, pinned EXACTLY in `package.json`, spawned as `<phantombot> __pi …`, driven by `[harnesses.pi.routing]`), `pi-host` (the host's own `pi`, passed no `--provider`/`--model`/`--api-key` — configured by its owner like claude and codex), `claude`, `codex`. Load-bearing, each with the failure it prevents: **native ALWAYS uses the embedded engine, even when a host pi exists** — the routing schema is tied to the version we ship and test, and a different host pi breaks it silently. **`src/index.ts` keeps its static import graph and dispatches `__pi` in its body** — a dynamic-import entry changes bun's module init order in a compiled binary and `@peculiar/x509`'s tsyringe reflect polyfill throws on every start (caught only by running the COMPILED binary; `bun src/index.ts` is fine). **Import pi's unbundled `dist/`, through TWO resolution paths** — `dist/bundle/cli.js` breaks extension loading (`Cannot find module jiti`) and pi's `exports` map hides `dist/`. COMPILED: literal relative paths into the checkout's node_modules (`piDistModule`, `piThemeFiles`, `piPackageJson` in `lib/embeddedPi.ts`), which the bundler inlines. FROM SOURCE — including phantombot installed as a DEPENDENCY, where the package manager hoists pi next to phantombot and no relative node_modules path exists — the same files are read from pi's real root, located through its `package.json` (the one subpath its exports map answers). Never collapse this to one path: the literal-only version made `import "phantombot/engine"` fail on every hoisted install, and a runtime-only version would not be embedded. Both paths serialise the theme assets identically, so `EMBEDDED_PI_ASSETS_HASH` (part of the extraction dir name) does not change with the path taken. Photon has no exports map and is imported by bare specifier. **`PI_PACKAGE_DIR` only when compiled** (`embeddedPiChildEnv`): a compiled pi dies on `ENOENT theme/dark.json` without it, and under `bun src/index.ts` it would point pi's theme lookup at the wrong layout; the assets extract to a version+hash dir so an update never rewrites files a running engine reads. **Photon's WASM is served from INSIDE the binary** (`lib/embeddedPhoton.ts`, installed by `runEmbeddedPi` when compiled): photon-node reads `photon_rs_bg.wasm` from its `__dirname`, which a compiled binary bakes to the BUILD machine's node_modules, and pi's fallbacks (beside the executable, cwd) are files pi's release ships and ours does not. On a miss pi's `loadPhoton()` swallows the error and EVERY image becomes `[Image omitted: could not be resized below the inline image size limit.]` whatever its size, so native vision was silently dead fleet-wide until 2026-09-17. The wasm is a `with { type: "file" }` import and every read of that filename is redirected to it, even when a file exists on disk. Only a COMPILED binary run from a host with no build tree shows the bug: `tests/lib-embeddedPhoton.test.ts` compiles from a staged copy and deletes it before running `__pi`. **Attribution (`Phantomyard's Phantombot`, `https://phantombot.bot`) is an inline extension factory in `runEmbeddedPi` and nowhere else**, so only native reports it; pi mutates headers IN PLACE and ignores the hook's return. **The capability-routing extension's delegates re-enter the engine via `PHANTOMBOT_PI_COMMAND`**; a host pi is spawned with it blanked. **The per-turn API key never travels on argv — it is relayed via the provider's NATIVE env var, and the native store is stripped so env is the ONLY source (#602, PR #606)**: `/proc/<pid>/cmdline` is world-readable (0444) while `environ` is 0400 owner-only, so `--api-key` would publish the key to every local user for the process's lifetime. Pi prefers a STORED credential over env vars, and the native agent dir is PER-PERSONA (one per persona under `personas/<persona>/agent`, lib/nativeAgentDir.ts) — a left-behind api_key entry would decide THIS persona's key (wrong account billed silently after a vault rotation). So each relayed turn removes the provider's api_key entry from that persona's OWN native `auth.json` before spawn (`removePiApiKey`, which requires an `agentDir` target — the host's `~/.pi` is never deletable), and persona-scoping is what makes the strip safe on a multi-persona host: a sibling's tier-2 fallback or oauth login lives in the sibling's own store and is unreachable (PR #606 round-4). The strip is FAIL-CLOSED (PR #606 re-review): Pi resolves ANY stored credential — api_key AND an oauth login — ahead of env vars, so a strip failure or a surviving oauth entry ABORTS the relayed turn with a loud error BEFORE spawn (nothing authenticates as the wrong key) rather than warn-and-spawn; tier-2 no-key turns are untouched. A persona's first scoped use absorbs the LEGACY shared dir (`<root>/agent`) — auth.json OAUTH-FILTERED (api_key entries only: the shared file has no persona attribution, and one operator's interactive login must not become every persona's stored fallback or a fail-closed abort on their first relayed turn — the operator who logged in re-runs Configure→Brain once) plus the local-config files pi resolves `useLocalConfig` turns from (settings.json, models.json, models-store.json — verbatim, or a pre-upgrade local-config persona keeps its credential but silently loses its model choice), so pre-scoping upgrades keep tier-2 fallbacks working. The absorb is gated on an explicit SENTINEL (`personas/<persona>/agent/.legacy-absorbed`, LEGACY_ABSORBED_MARKER), never on the store file's existence (issue #609, PR #610): a strip that empties the store leaves `{}` on disk, and file-existence-as-marker would block the legacy re-absorb forever. A real strip therefore deletes the sentinel BEFORE committing the stripped store — a crash or unlink failure in between must leave the OLD store intact (re-absorbable), never a thinned store behind an intact marker reporting `ok: true` — and any unlink error other than ENOENT (no marker: never absorbed / already stripped / ephemeral dir, the normal case) aborts the strip fail-closed before the rewrite. The next tier-2 ensure then re-absorbs at PROVIDER level: missing legacy providers merge back in, wizard/persona-owned entries are never clobbered, so even a PARTIAL strip heals. The legacy dir is STRICTLY a read-only migration source (plus the agent dir for a bare persona-less NON-relayed `__pi` hand-run): a persona-less RELAYED turn (threat judge, durable-fact extraction) carries its key in env and needs no store, so it runs on a per-turn EPHEMERAL agent dir under the turn's temp dir — the strip never reaches the legacy file and a legacy oauth entry can never abort a judge/extraction turn. The wizard re-writes the entry transiently for its own `--list-models` runs, and only a provider missing from `PI_PROVIDER_CATALOG` (live-only) keeps the legacy argv flag, with a logged warning. The managed capability-routing extension stays stamped ONCE at the host level and is handed to each persona child explicitly via pi's `--extension` flag — the persona-scoped agent dir carries only its own auth, never a copy of the stamp. A delegate child inherits the same relayed env, never key argv. **The menus detect LIVE**: native always offered, host harnesses only when their binary resolves, nothing is ever installed (the Pi installer is gone). **native is never persisted to `state.json harness_bins`** (its path is this binary, which moves on update); pi-host persists under `pi`. **A legacy `pi` has ONE decision (`lib/harnessReconcile.ts`) with two callers**: `loadConfig` maps it in memory with host-pi presence UNKNOWN (routing → native, else pi-host — the pre-upgrade meaning), and `doctor` (repair on; also the daemon's startup doctor) writes it with a live probe (routing-less + no host pi → native), backing up `config.toml` first. A claude-/codex-only config is a normal state: zero changes, zero output, file untouched, native never injected. The second run is byte-identical. Rollback to a pre-native binary is accepted as unsupported (older binaries skip unknown ids), so the migration must be right, not reversible. Tests: `tests/lib-harnessReconcile.test.ts`, `tests/lib-embeddedPi.test.ts`, `tests/lib-embeddedPhoton.test.ts`, `tests/harnesses-nativeChain.test.ts`, `tests/harnesses-pi.test.ts` (native vs pi-host), `tests/cli-harness.test.ts`, `tests/tui-brain-flow.test.ts`, `tests/brain-onboarding.test.ts`. **On win32 the agent dir is also seeded with `defaultTools` so the model has a shell it can actually run (issue #614).** Pi's `powershell` tool is OPT-IN — pi's built-in default set is `read, bash, edit, write`, and `getShellConfig()` on win32 resolves bash from `%ProgramFiles%\Git\bin\bash.exe`, the x86 variant, then `bash.exe` on PATH — so on a Windows box without Git Bash EVERY command failed with "No bash shell found" and `getPowerShellConfig()` (pwsh.exe ?? powershell.exe) was unreachable in the same bundle. `ensureWindowsShellTools` (lib/nativeAgentDir.ts) writes pi's defaults PLUS `powershell` into the dir's `settings.json` — both shells, so a box WITH Git Bash keeps the behaviour existing prompts assume. It runs AFTER the legacy absorb (the absorb may have just inherited a settings.json — seeding first would write a list the absorb then refuses to clobber, losing the operator's model choice), and REFUSES an unparseable or non-object file rather than clobbering it; ephemeral relayed-turn dirs get it too. **ONLY AN ABSENT `defaultTools` IS SEEDED — a present key is authoritative whatever its shape and is never written (PR #615 round 1, Kai blocking + Lena concurring).** The earlier version appended `powershell` to any array, which re-armed a model-callable shell on exactly the configurations that exist to remove one: pi's `docs/settings.md` documents `defaultTools: []` as "no built-in tools while preserving extension and SDK custom tools", and a list like `["read"]` omits every shell on purpose. A present-but-non-array value (a string, `null`) is refused too, not replaced with our list — same refuse-don't-clobber rule as the auth absorb. The accepted cost is that an operator who hand-writes a tool list on Windows does not get `powershell` for free; that fails CLOSED, and a tool list is the one file where a silent superset is a security regression rather than a convenience. Deliberately NOT pi's `--tools` flag: that is a strict allowlist over ALL tools and would disable the managed capability-routing extension's tools. Test: `tests/lib-nativeAgentDir.test.ts` (issue #614 block, proven by removing both call sites — 7 failures — and the present-key rule by restoring the append branch — 5 failures).

### 59. A failed-over harness dies with its stream, and heartbeats are not progress.

Two failures from one 2026-09-16 turn. (a) claude emitted a recoverable, non-terminal `server_error`; `runWithFallback` `break`s to the next harness, which returns the adapter generator, but `runHarnessProcess`'s `finally` only disposed timers and cancelled the reader, so claude ran 78s more and applied a Home Assistant change while native applied the same prompt in parallel. The `finally` now AWAITS `KillCoordinator.abandon()` (cause `abandoned`) whenever stdout did NOT reach EOF and no policy tripwire already killed it; a normally-finished process is never touched. Abandonment SIGKILLs the group with no grace and resolves only once the process has exited, so the next harness cannot start while the old one lives: a fire-and-forget SIGTERM with a 5s grace let a TERM-trapping primary run its side effect after the fallback had started (review of #572). Probe a killed child via `proc.exited`, never `exitCode` (null for a signalled process). (b) native then went silent for 40 minutes with neither the 5-min idle nor the 20-min tool timer firing, because `touch()` ignored its activity class and every `"model"` heartbeat re-armed the full idle window. `"model"` activity now extends the idle deadline only to `lastProductiveAt + thinkingTimeoutMs` (default `DEFAULT_THINKING_TIMEOUT_MS` = 600s, `harness_thinking_timeout_s`), never shortens an armed deadline, and productive output or a finished tool restarts the budget. The public contract is therefore `max(idle, thinking)` after the last productive output: the idle window is a floor. EVERY config-backed request builder (engine, PhantomChat turns AND reactions, ask, tick, ACP, TUI, durable facts, the PhantomChat greeting) passes `thinkingTimeoutMs` next to `toolTimeoutMs`; `tests/harness-thinking-propagation.test.ts` scans `src/` and fails when a builder forwards `harnessIdleTimeoutMs` without it, so the setting cannot depend on which entry point started the turn. Also: aborted turns persist through ONE helper, `channels/core/interrupted.ts` (`persistInterruptedTurn` + `abortReasonString`), on EVERY interactive surface: Telegram, PhantomChat, the TUI (`tui/chatSession.ts`) and the ACP editor bridge (`connectors/acp/turnBridge.ts`, so every editor connector). It keeps streamed text ahead of `[interrupted before reply]`, skips `/reset`, and never writes a turn that already reported `done`. Abort reasons are uniform: `/stop`, TUI `^c` and ACP `session/cancel` are `"stop"`; a new prompt mid-turn is `"interrupt"`. The TUI follows the same "type to interrupt" design as the other channels: a prompt sent while a turn runs aborts it and is sent once the old turn has unwound (a prompt superseded while waiting is dropped, like the backlog flush), and the input box stays live during a turn. Tests: `tests/harness-failover-kill.test.ts` (real subprocess through `runWithFallback`; side-effect file must not appear), `tests/channels-core-interrupted.test.ts`, `tests/channels-phantomchat-server.test.ts` (/stop persists), `tests/channels-telegram.test.ts`, `tests/tui-chat-interrupt.test.tsx` (session persistence + screen interrupt/stop reasons), `tests/connectors-acp-server.test.ts` (cancel persists); all proven by mutation. **A pi `assistantMessageEvent toolcall_*`/`tool_use_*` record is `'model'`, NEVER `'tool'` (issue #641)** — it is the model COMPOSING a tool call inside its message, not executing one; pi signals execution with the top-level `tool_execution_start`/`_update`, which stay `'tool'` AND open a per-tool timer via `piToolBoundary`. The stream-side records never drive a `toolStart`, so classifying them `'tool'` handed every delta a FULL unbounded idle reset with no cap covering it — that is how a stalled GLM turn emitting nameless toolcall noise outran the 600s ceiling (873s observed). The fix-1 trip stays "no activity of any kind for `idleTimeoutMs`": true silence already trips at the idle window, and heartbeats/toolcall noise only buy the thinking budget — a genuinely working tool run (Kai's hour-long turns) keeps its full resets and is untouched. Named toolcall records are still `'model'` too: until `tool_execution_start` fires the model is only planning, and the next execution event restores the full reset. Claude/codex need no equivalent change — their `'tool'` classifications are always paired with a real boundary id. Tests: `tests/harnesses-pi.test.ts` (classification), `tests/lib-harnessRunner.test.ts` (thinking-budget cap, legacy no-budget guard, in-tool immunity).

### 61. A harness crash may fail a turn; it may not erase the request or its evidence (issue #571).

`runTurn` applies `DEFAULT_HISTORY_MAX_BYTES` (128 KiB UTF-8) after the 30-row query and before prompt-cache preparation, keeping the newest whole stored messages and logging the loaded/included bytes with the registry turn id. Do not move this into Pi: every harness receives the same bounded canonical history, while system prompt, current message, retrieval and cache epochs keep their own budgets. When the terminal chain result is an error, the orchestrator atomically appends the user message plus an assistant recovery marker telling the next turn to verify side effects before retrying; operator aborts and host shutdowns are excluded because the channel interruption path owns those. `runHarnessProcess` stamps natural failures with structured `exitCode`/`signalCode`; the outer `runTurn` wrapper writes status, safe error, exit/signal and the already-redacted 20-line stderr tail into the existing turn-registry JSON retained for two hours. `pi-host` may set `[harnesses.pi] max_old_space_mb` (or per-instance) / `PHANTOMBOT_PI_MAX_OLD_SPACE_MB`; the child env appends the explicit max-old-space cap so Node's last-flag-wins behavior overrides inherited values without reparsing or damaging other `NODE_OPTIONS`. Never derive or auto-raise it from RAM: on small hosts that silently trades a V8 abort for system-wide swap/OOM pressure. Daemon startup probes host Node only when `pi-host` has no explicit cap and warns below `EXPECTED_PI_HEAP_MB` (2048); native Pi runs under the embedded Bun runtime and is not probed. Tests: `tests/orchestrator-turn.test.ts`, `tests/lib-turnRegistry.test.ts`, `tests/lib-harnessRunner.test.ts`, `tests/harnesses-pi.test.ts`, `tests/cli-run.test.ts`.

### 66. The hard cap is a backstop, not the deadline — and outage alerts speak for the persona that died (issues #639, #638).

Two halves of the 2026-10-01 kw-phantombot incident: kai's codex primary was quota-dead, pi-native served a legitimate 502-tool-call hour of work, and the 3600s hard cap killed it mid-flight — with the resulting 🚨 notification emitted from the DEFAULT persona's channels, and no stderr anywhere to say why codex had failed. **(a) Soft deadline + nudge (`orchestrator/turn.ts`).** At `harness_soft_timeout_s` (default 3000s; only armed when strictly below the hard cap — short-cap turns like recovery replies, probes and the threat judge are auto-disabled, so no caller needed touching) the kill coordinator SIGTERMs the process group with a NEW kill cause `"soft"`, and `runTurnBody` starts a NEW pass: same chain, fresh hard budget, the nudge as the user message, and the interrupted pair(s) appended to the request's `epochTurns` (original user message → partial streamed text + `INTERRUPTED_MARKER`) so the fresh process knows what was asked and how far the reply got. The pairs are APPEND-ONLY onto the epoch turns — that keeps a prepared prompt-cache prefix valid and lands them after history and before the current message, which is exactly the slot the render order gives them; do not flatten them into `history`. The nudge pass's `done.finalText` is stitched onto the earlier passes' text — on the internal `finalText` AND on the yielded chunk, because consumers take the reply from `done.finalText` and the transports diff it against what they streamed (unstitched = pass 1's delivered text vanishes from history and voice; caught in test). Passes are bounded by `harness_nudge_cap` (default 2); after exhaustion the soft deadline is disarmed and the hard cap kills for real. A soft kill is NOT a harness failure: `runWithFallback` returns it without a cooldown bump, an alerter incident or a fall-through, and `runTurnBody` swallows the chunk so a chat channel never sees an error bubble over a reply that is still coming. The persistent turn pair stays ONE pair (original user → full stitched reply); the nudge is runtime bookkeeping, not conversation history. **(b) Attribution + evidence (`lib/harnessAlert.ts`, `orchestrator/fallback.ts`, `lib/harnessFailureLog.ts`).** `AlertSender` takes the originating persona (`req.persona`); `cli/run.ts` routes `runNotify` through THAT persona's bot/phantomchat identity, falling back to the daemon default only when the turn had none. Every failure the orchestrator records (recoverable fall-through, terminal, throw, empty reply) also flows through `onHarnessFailure` into `<agentDir>/harness-failures/<date>.jsonl` — bounded (last 20 stderr lines × 400 chars), redacted upstream, best-effort (a broken sink latches off rather than breaking a failing turn) — because a mid-chain failure a fallback absorbed previously left NO evidence: the turn registry only records the terminal error's tail, and the alerter kept counts. The exhausted alert gains a one-line excerpt from the chain's FIRST failure, so "native timed out" can also say "codex: You've hit your usage limit" without SSH. Tests: `tests/orchestrator-turn.test.ts` (soft deadline block), `tests/lib-harnessRunner.test.ts`, `tests/orchestrator-fallback.test.ts`, `tests/lib-harnessAlert.test.ts`, `tests/lib-harnessFailureLog.test.ts`, `tests/config.test.ts`.

### 74. Tool watchdog (issue #552): tool execution is a parser-owned lifecycle, not an idle activity hint.

`runHarnessProcess` receives stable tool start/end IDs from every adapter and
`KillCoordinator` suspends model-idle watching while any ID remains in flight.
Each tool has its own `harness_tool_timeout_s` cap (default 1200s, clamped to
the hard turn cap); the final matching end restarts idle from zero, and every
terminal path clears the set. Tool-cap kills never fall through to another
harness. Claude pairs `tool_use.id` with `tool_result.tool_use_id`, Pi pairs
`tool_execution_start`/`tool_execution_end` by `toolCallId`, and Codex pairs
tool `item.started`/`item.completed` by `item.id`; anonymous names and progress
text are not identifiers because parallel calls make them ambiguous.

### 79. A bring-your-own-endpoint provider is a `models.json` ENTRY phantombot owns — never a vendor entry, never a guess (issue #694).

Pi resolves every catalogue provider's endpoint itself; the two providers added
for self-hosters (`openai-compatible`) and PhantomOps users (`phantomops`) have
no such entry, so `lib/piCustomProvider.ts` writes one into the child's agent
dir (`providers.<id>` with `baseUrl`, `api: "openai-completions"`, `apiKey` and
`models`). Load-bearing, each with the failure it prevents: **the key is a
`$VAR` reference, never a value** — the per-turn relay stays on the existing
`PI_PROVIDER_CATALOG` env-var contract (#602), so a credential never reaches a
world-readable agent dir; **an unauthenticated endpoint gets a literal
placeholder, not an unresolvable reference** — verified against pi 1.0.4, a
provider whose `apiKey` cannot be resolved is not merely unauthenticated, it is
INVISIBLE (`pi --list-models` omits it and the turn dies with "Use /login to log
into a provider"), which is why "no key" is spelled `no-key-required`; **the
merge REFUSES an unparseable or non-object document instead of clobbering it** —
the agent dir is shared with whatever the operator or a host pi put there, and
`removeProviderEntry` deletes only phantombot's own id; **models are UNIONED,
never replaced** — the wizard seeds them from the live `/models` list and adds
the operator's picks, and the spawn-time refresh deliberately passes none so a
turn can never shrink the list under the operator; **nothing is ever guessed** —
`openai-compatible` has no default endpoint (that is the whole point of the
provider), PhantomOps defaults to the gateway so its personal token is the only
input, and a base URL is normalised at the prompt (trailing slash, pasted
`/chat/completions` or `/models`) rather than at request time; **the entry is
re-asserted at SPAWN**, because a turn must not depend on a wizard write from an
upgrade ago, and it is written only when it has drifted (`entryMatches`);
**`base_url` is TOML-only and belongs to the provider** — `computeRoutingWrites`
drops it for a catalogue provider and `computeRoutingClears` erases it, so a
leftover endpoint can never read like a live setting; and `phantomops/auto`
stays FIRST in the picker (a product decision, restated in code so a server-side
reorder cannot silently demote the full phantom to a raw model). Tests:
`tests/lib-piCustomProvider.test.ts`, `tests/lib-providerModelCatalog.test.ts`,
`tests/lib-providerKeyProbe-custom.test.ts`, `tests/lib-piRouting.test.ts`,
`tests/cli-harness-routing.test.ts`.
