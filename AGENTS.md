# AGENTS.md — guide for any agent contributing to phantombot

This file is for **any agent (human or LLM) working on the phantombot codebase itself**. If you're a Claude Code session, an OpenAI-Codex agent, a future maintainer, or just yourself catching up after time away — read this before opening a PR. It captures the small set of project-specific conventions that aren't obvious from the code.

> **Naming-collision warning.** This `/AGENTS.md` (project root) is **not the same as** `personas/<name>/AGENTS.md` (a persona-specific tool-hint file phantombot reads when loading that persona). They share a name because OpenClaw uses the same convention for persona files; phantombot's persona loader accepts both `tools.md` and `AGENTS.md` as the persona-tools slot. If a contributor refers to "AGENTS.md" without context, they almost always mean *this* file (the repo-level one). If you're editing a file under `personas/` or `agents/`, you're touching a persona, not the contributor guide.

## The contributing discipline (READ FIRST)

**Every PR that changes user-facing behavior, architecture, or developer workflow must update both `README.md` and this file in the same PR.** No exceptions. Reviewers should reject PRs where the docs don't match the code.

What "user-facing behavior" means:
- New / removed / renamed CLI subcommand or flag
- Change to systemd unit shape (added/removed timer, new `EnvironmentFile=`, etc.)
- Change to where files live (config path, memory db path, persona dir, lockfile)
- Change to credential discovery / hygiene rules
- Change to release pipeline (asset names, version scheme, trigger)
- Change to architecture invariants (the persona model, runLock, etc.)

What's *not* user-facing and doesn't need a docs update:
- Pure refactors that preserve behavior
- Bug fixes that restore the documented behavior
- Internal lib changes with no public API change
- Tests

If unsure, update the docs. Cheaper than the post-merge "wait, the README says X but the code does Y" archeology.

## Build / test / typecheck

```bash
~/.bun/bin/bun install                  # install deps (cron-parser, citty, smol-toml, @clack/prompts)
~/.bun/bin/bun tsc --noEmit             # typecheck
~/.bun/bin/bun test                     # full test suite
~/.bun/bin/bun test tests/lib-X.test.ts # one file
~/.bun/bin/bun run build                # → dist/phantombot (linux x64-baseline; ~98 MB)
~/.bun/bin/bun run build:arm64          # → dist/phantombot-arm64 (cross-compile)
```

`bun-version` is pinned to `1.x` in CI for reproducibility (see `.github/workflows/release.yml`).

The build target **must remain `bun-linux-x64-baseline`** (not plain `bun-linux-x64`). The supervisor box that runs kai is pre-AVX2 silicon; the non-baseline binary SIGILLs on launch there. If you "optimise" to plain x64, you'll break production. See PR #37 for the post-mortem.

## Architecture at a glance

- **Citty CLI dispatcher** (`src/cli/index.ts`) → subcommand → orchestrator (for turn-spending commands like `run`, `ask`, `tick`, `nightly`).
- **One-turn coordinator** (`src/orchestrator/turn.ts`) loads persona files, loads recent turns from memory, builds system prompt, **screens untrusted input** (`screen.ts`), runs the harness chain, and persists the user+assistant turns on success.
- **Harness chain** (`harnesses/buildChain.ts` + `src/orchestrator/fallback.ts` + `lib/harnessRunner.ts`) resolves `[harnesses.personas.<name>].chain` first and uses the global `[harnesses].chain` when the persona has no non-empty override. Every turn entry point must pass its persona to `buildHarnessChain`; a daemon or tick process can serve several personas with different primaries. The resolved chain tries primary first and falls through on a recoverable error (with per-harness cooldown for fast fallback) — except for an idle-watchdog kill that had already produced output, which respawns the SAME harness once with a recovery preamble before the chain advances (invariant 33). Failover is invisible to the user by design, so `lib/harnessAlert.ts` notifies the owner when that silence would hide something real: a primary failing **authentication** for several turns in a row (still served, but by a fallback that may be billed per token), or the **whole chain exhausted** with no reply delivered. A harness killed by an external SIGTERM/SIGINT (systemd stopping the cgroup during a restart) is classified as shutdown, NOT as a recoverable harness error — otherwise every restart with a turn in flight spawns a paid fallback for a reply nobody receives.
- **Security perimeter** (`lib/threatJudge.ts` + `orchestrator/screen.ts`) — trusted principals act directly; untrusted input is judged in code before any capable harness sees it. See "Security perimeter".
- **Channels** are a channel-agnostic core + thin per-channel adapters (`src/channels/core/` + `src/channels/telegram/`); `phantombot run` is the long-running process. See "Channel layer".
- **Credential bootstrap** (`lib/vaultMigrate.ts` → `lib/vault.ts`) imports any legacy plaintext `.env` into the per-persona encrypted vaults ONCE, then `loadVaultIntoEnv()` injects the active persona's secrets into `process.env` at startup; each harness reloads that vault before every spawn so `phantombot vault set` takes effect mid-session. Nothing reads a `.env` file at runtime (#452).
- **Tick fires scheduled tasks** (`src/cli/tick.ts`); 1-minute systemd timer; lockfile prevents overlap; missed runs are skipped, not piled up.
- **Heartbeat is mechanical** (no LLM); **nightly is cognitive** (LLM-driven distillation).
- **`workingDir` is REQUIRED on every `runTurn` call** (#387) — the harness subprocess cwd, deliberately with no default. Interactive surfaces (telegram, phantomchat, ask, tick, reactions) pass `homedir()`, because the owner asks for work on repos all over their home dir. Machine-driven background turns (nightly) pass the **persona dir**. This used to silently default to `homedir()` and every background caller took the default, so nightly stages woke up in `$HOME` unable to see their own `memory/` from cwd — and went hunting for it. On macOS those recursive walks cross `~/Library/Containers`, tripping the TCC `kTCCServiceSystemPolicyAppData` prompt ("phantombot would like to access data from other apps") once per spawned date. If you add a `runTurn` caller, decide which tree it may treat as home and say so explicitly.

## Channel layer (core + adapters)

As of #168 the channel layer is split into a **channel-agnostic core** and **thin per-channel adapters**, so a second transport (Matrix, Slack, …) is a small adapter rather than a fork of the engine.

- **`src/channels/core/`** is channel-blind. `engine.ts` holds the streaming turn engine + server loop (moved verbatim out of the old `telegram.ts`); `routing.ts` is the pure group-reply decision; `prompts.ts` holds the channel-layer prompt suffixes (`VOICE_REPLY_INSTRUCTION`, the capture nudge, the voice-unavailable message); `types.ts` defines the contract: `Channel` / `ChannelTransport` / `ChannelMessage`, a `ChannelCapabilities` object (`voice` / `typing` / `attachments` / `encryption`), and `encrypt`/`decrypt` hook signatures.
- **`src/channels/telegram/`** is the first adapter: `transport.ts` (HTTP client), `parse.ts` (update → `ChannelMessage`), `channel.ts` (capabilities + encrypt/decrypt).
- **`src/channels/telegram.ts`** is now a **backward-compat barrel** that re-exports the core + adapter symbols under their old names, so importers and the test suite kept their surface unchanged across the refactor.

Two invariants worth knowing before you touch this:

1. **IDs are channel-neutral strings.** The core speaks `conversationId: string` / `senderId: string`. Telegram's numeric ids are normalized at the adapter boundary only — `String(chat.id)` on ingest (`parse.ts`), and `Number(conversationId)` right before the Telegram API call (`transport.ts`). Don't reintroduce a numeric id into the core contract; Matrix/Slack ids aren't numbers. The numeric update-notify recipient ids (`updateNotify.ts`, `notify.ts`) and the slash-command logging id are separate, Telegram-specific, and converted at their own boundary.
2. **The encrypt/decrypt seam is placed but empty.** Telegram's `encrypt`/`decrypt` are identity pass-throughs (Telegram bots have no E2EE) with `encryption: false`. They return `T | Promise<T>` so async crypto (Matrix Megolm) can slot in later with no signature change. There is deliberately **zero crypto code and zero Matrix code** — the actual Matrix adapter + E2EE are parked for the community discussion in issue #154.

## Security perimeter — trusted vs untrusted input

Phantombot runs a **two-tier perimeter**, enforced in code (not by trusting a model's say-so — the bug that prompted this design was a model *claiming* it had notified/recorded when it hadn't).

- **Trusted** input — an authenticated Telegram principal — is acted on directly. The principal *is* the gate; no screening. Nightly (`cli/nightly.ts#runNightlyTurn`) is the one non-principal caller that also sets `trusted: true`: its prompt is machine-authored by the stage itself, it operates only inside its own persona dir, and the call carries no `retrieve`/`pullFacts` so no ambient content rides in via injection — command authority over its own files, not exposure to a third party. Provenance stays pinned to `other` regardless (see `TurnInput.userSource`), so this doesn't inflate the persona-wide fact pool the way a real principal turn does. Any future non-chat caller wanting `trusted: true` needs to clear the same bar.
- **Untrusted** input — email, web, Twilio, webhooks, raw `phantombot ask`, any future app — is read by a **tool-less threat judge** (`lib/threatJudge.ts`) before any capable harness runs. `orchestrator/screen.ts` (`makeScreener`, wired into `turn.ts` like `makeRetriever`) does the side-effecting orchestration around the pure judge: it first **briefs** the judge with semantic recall from the threat-relevant drawers (`decisions` = prior rulings, `people` = known senders, `norms` = what's routine), then the judge returns a 0–100 threat score. Below threshold → green-lit silently; at/above → the untrusted turn is **HELD** (does nothing) and surfaced to the principal.
- A **ruling is only recorded from a trusted turn** — the judge and the untrusted turn never write decisions. When the principal concludes, the ruling (with its weight) is captured to the `decisions` drawer so the next similar screening recalls it.

If you add a new untrusted entry point (a new inbound channel, a new `ask`-style API), it MUST route through the screener — don't let untrusted content reach a harness unscreened.

## Persona model — many personas, one process

**One process serves every persona this host starts** (phantombot#439). The persona "library" on disk (under `~/.local/share/phantombot/personas/`) can hold many directories; which of them run is an explicit choice, never inferred from what happens to be on disk:

- `default_persona` — the persona that owns the host. It always starts, and it alone answers the lifecycle commands `/update` and `/restart` (`/stop` is per-chat and stays ungated).
- `autostart_personas` — the explicit roster of ADDITIONAL personas to start. Absent means "exactly what this host did before the key existed"; present (even empty) is the whole truth, and a persona outside it is not started even if it has a `phantomchat.json` or a legacy `[channels.telegram.personas.<name>]` entry.

`runRun` builds one Telegram listener per persona-with-a-bot and one PhantomChat listener per persona-with-an-identity, all inside the single `phantombot run` process. The `runLock` (`src/lib/runLock.ts`) still prevents two `phantombot run` processes on one box — the multiplexing is inside the process, not across processes. There is no supervisor, no subprocess per persona, and adding one is a rejected design (crash isolation is not worth a supervisor, backoff, orphan handling on update, and the cgroup trap of #415).

Telegram account parsing is deliberately permissive: an account without a token resolves to no `TelegramAccount`. `Config.channels.telegramStated` and `telegramPersonasStated` preserve whether TOML nevertheless stated that account, so `planListeners` can warn and `doctor` can fail without making startup fatal. Do not infer intent from `channels.telegram === undefined`: that shape also describes a valid PhantomChat-only persona. A broken Telegram account disables only that listener; sibling Telegram listeners and PhantomChat must keep running.

**Config is two layers** (`src/lib/personaConfig.ts`, `loadConfig(persona)`):

| File | Holds |
|---|---|
| `<config-home>/phantombot/config.toml` | HOST globals: `default_persona`, `autostart_personas`, `update_channel`, `personas_dir`, `memory_db`, harness bin paths |
| `<personas-root>/<persona>/config.toml` | that persona's own settings: its Telegram bot, `[voice]`, `chattiness`, `[retrieval]`, its `[harnesses].chain` |

Resolution is a per-key deep merge, persona wins, env still wins over both. A key the persona file omits falls back to the GLOBAL FILE, never to a constant. Host-only keys are stripped from the persona layer, so a persona cannot elect itself default or relocate the root.

Two rules that follow from this, and that new code keeps breaking:

1. **Resolve the persona BEFORE loading config.** Any persona-aware entry point (`notify`, `ask`, `nightly`, `heartbeat`, `tick`, `voice`, `telegram`, `harness`) must call `loadConfigForPersona(name)` / `loadConfig(name)` rather than loading the default layer and picking a persona out of it afterwards. Loading first silently runs one persona on another's settings.
2. **Write where the read path looks.** A per-persona setting is written through `resolvePersonaWriteTarget()`: the persona's own file once it exists, the global file (in its historical shape) until then. A writer that ignores this "saves" successfully and changes nothing.

Migration from the old single-file layout is copy-only (never delete, so a rollback still boots), additive (fills only the keys the persona file omits, so a hand edit always wins) and runs on every daemon start, which is what makes `/update` order-independent from any older version.

The README's [Personas](README.md#personas) and [Multiple personas](README.md#multiple-personas) sections are the user-facing explanation; if you change this model, update both.

## Service model (systemd + launchd + Windows Task Scheduler)

Phantombot ships on **Linux (systemd --user)**, **macOS (launchd, per-user LaunchAgents)**, and **Windows (per-user Task Scheduler logon task plus three periodic tasks)**. `lib/platform.ts` is the single router that decides which backend to talk to; each backend sits behind a common `ServiceControl` surface with an injectable runner so tests never touch the real service manager. Windows uses `InteractiveToken` and the current user's SID, so installation needs no password or elevation; installation preserves healthy existing task definitions and only repairs missing/stale entries. Windows `start`/`restart` re-enable the task and use a hidden native detached launch for SSH/terminal control because Task Scheduler cannot `/Run` an interactive-token task from a non-interactive session. `windowsJob.ts` assigns harness children to kill-on-close Job Objects.

On Linux, `phantombot install` creates **three** systemd-user units:

| Unit | Cadence | What it does |
|---|---|---|
| `phantombot.service` | always-on | `phantombot run` — Telegram listener |
| `phantombot-heartbeat.timer` → `.service` | every 30 min | mechanical maintenance, no LLM |
| `phantombot-tick.timer` → `.service` | every 1 min | fires due scheduled tasks |

There is deliberately no nightly unit. The cognitive pass is event-driven —
`run` fires a sweep at startup, and the heartbeat fires one when it notices the
calendar day changed since its last fire. A clock would miss the day entirely on
any box that sleeps at 02:00. Installs that predate this have their
`phantombot-nightly.timer` stopped, disabled and deleted on the next heartbeat.

A nightly stage is deliberately the **narrowest turn phantombot runs**: no MCP
(`mcpMode: "none"`), cwd pinned to the persona dir, and a positive tool grant of
`NIGHTLY_TOOLS` = `Bash,Read,Write,Edit` (`toolsMode: { allow }`, #387). The
allowlist exists to drop claude's native `Glob`/`Grep`, whose parallel workers
recursively walk the tree from cwd; a stage searches through
`phantombot memory search` (an index query), never a filesystem walk. Note the
grant is claude-only — pi and codex have no positive-grant flag and ignore it —
so treat it as defence-in-depth, **not** a trust boundary. `toolsMode: "none"`
is the real boundary, and it's reserved for the threat judge.

Services carry **no `EnvironmentFile=` lines** (#452). They used to source `~/.config/phantombot/.env` and `~/.env`, which made those plaintext files authoritative in practice while the docs called the vault canonical — and gave macOS (whose launchd plists cannot source a file) a permanently different credential path.

Credentials now travel one way on every platform: `loadVaultIntoEnv()` decrypts the ACTIVE persona's vault at startup and injects it into `process.env`, and each harness calls `reloadVaultForPersona()` before a spawn so a `phantombot vault set` from the previous turn is visible without a restart. An existing shell export always wins over a vault value, exactly as it did over the old files.

Service units also set a deterministic `PATH` that includes `~/.local/bin` plus stable user harness shim locations such as `~/.local/share/pi-node/bin` and `~/.local/share/pi-node/current/bin`. Do not rely on interactive shell startup files for service harness discovery. When Phantombot finds a harness in PATH or common npm/pi-node versioned locations, it saves the absolute path in `state.json` and executes that path directly on later starts. `phantombot run` must never fail startup just because a harness binary is missing; log loudly, keep the headless service alive, and let `phantombot doctor` report/repair the configured chain. Windows keep-alive tasks invoke `phantombot run --if-not-running`, which treats an existing run lock as a silent success; foreground invocations retain the diagnostic error.

**Service log retention (`src/lib/logRotate.ts`, #428).** Only macOS and Windows
need it: on Linux the units log to journald, which owns retention, so
`serviceLogDir()` returns `null` there and rotation is a no-op. Everywhere else
phantombot writes plain files (`~/Library/Logs/phantombot/`,
`<data>/phantombot/logs/`) that nothing ever capped — one macOS box reached
~700 MB. The **heartbeat** rotates them (every 30 min), because it is already
the host maintenance pass that heals units and scheduled tasks, so this needs no
new timer and inherits the same platform dispatch. Defaults are 16 MiB per file
and 3 retained generations (~64 MB per log worst case), overridable with
`PHANTOMBOT_LOG_MAX_BYTES` and `PHANTOMBOT_LOG_KEEP`; a junk or negative value
falls back to the default rather than disabling rotation, and `keep=0` discards
existing generations instead of stranding them. Three invariants that look like
tidy-up candidates and are not. **Rotation is COPY-TRUNCATE, never rename** —
the live file is held open by a process we do not control (launchd, the Windows
`cmd >>` wrapper) with an O_APPEND descriptor, and a descriptor follows the
INODE, so renaming the live file leaves the writer appending to the renamed
inode forever while the new log stays empty. **The live copy is staged to a
temporary file in the same directory BEFORE any generation is pruned or
shifted**, and published with a rename: the copy is the step that fails
(Windows EBUSY/EACCES on a log held by its writer), and pruning first means a
permanently unrotatable file ages its generations away on every heartbeat
without ever writing a new snapshot — retained history destroyed by the thing
meant to retain it. **The directory lock is ownership-aware**: takeover of a
stale lock is serialised by a second exclusive `wx` create and re-validated
under it, because every contender reads the same stale timestamp and a plain
overwrite lets all of them decide they won; release is gated on the token the
holder wrote, so a pass whose lock was stolen cannot delete its successor's.
The whole thing is guarded on `isPhantombotBinary`, so a dev run or a stray test
cannot truncate a developer's real logs.

If you change a unit body (any `generate*` function in `src/lib/systemd.ts`), `ensureUnitCurrent` will detect the on-disk unit as stale on the next `phantombot voice` / `phantombot harness` / etc. run and rewrite it automatically. The previous body is preserved as `${unitPath}.bak` for rollback.

## Credentials

Credentials live in the per-persona encrypted vault. The agent NEVER appends
secrets to `.env` or puts literal secret values in command arguments. It uses
`printf '%s' "$VALUE" | phantombot vault set NAME`; the positional
`phantombot vault set NAME "value"` form also remains available for backward
compatibility. Empty stdin is rejected unless `--allow-empty` is explicit, so a
failed pipe cannot silently erase an existing credential. The full credential
discovery + hygiene rules are baked into every persona's system prompt via
`CREDENTIALS_SECTION` in `src/persona/builder.ts`. If you change those rules, update both
`CREDENTIALS_SECTION` and the README's [Credentials](README.md#credentials)
section.

## Release pipeline

Every merge to `main` auto-releases `v1.1.<RUN_NUMBER>` as a **prerelease**. The
workflow at `.github/workflows/release.yml`:

1. Triggers on `push: main` (branch protection means a push IS a merge), minus a
   narrow `paths-ignore` denylist of docs/website surfaces. NOT
   `pull_request: closed` — a fork-merged PR runs that with a read-only token and
   `gh release create` 403s.
2. Checks out `github.sha` (the merge commit), so the tag pins to exactly the
   code that merged.
3. Runs `bun tsc --noEmit` and `bun test` as gates.
4. `sed -i "s/0.1.0-dev/1.1.${RUN_NUMBER}/" src/version.ts` (replaces only the
   literal placeholder, preserves the doc comment block).
5. Regenerates + version-stamps the embedded VS Code extension.
6. Cross-compiles linux x64-baseline/arm64, darwin x64/arm64, windows x64/arm64.
7. Computes `SHA256SUMS`.
8. `gh release create v1.1.<RUN_NUMBER> --prerelease --target <sha> …`.

**Release rings (#432).** `--prerelease` in step 8 is the whole gate. GitHub's
`/releases/latest` excludes prereleases, and that is what a `stable` host
resolves (`src/lib/githubReleases.ts`); a host with `update_channel = "preview"`
resolves the `/releases` LIST instead and takes its newest non-draft entry. So a
merge reaches only the preview ring until a human runs the
`.github/workflows/promote.yml` workflow_dispatch, which flips
`--prerelease=false --latest` on an **existing** release.

Four things here look like tidy-up candidates and are not:

- **Promotion must never rebuild.** The point of a ring is that the bytes the
  fleet installs are the bytes that soaked. A promotion that rebuilt would ship
  an artifact nobody ran, and the soak would be theatre.
- **CI must not decide stable.** Green tests are the bar for MERGING. If they
  were also the bar for promotion the two rings would be one ring. Stable means
  a human watched a real host run it.
- **The updater compares versions for EQUALITY, not `>`** (`src/cli/update.ts`).
  This is what makes rollback free: a host stranded on preview `1.1.291` flips
  `update_channel` back to `stable` and installs `1.1.280`, a LOWER number.
  Turning that into a "newer than" compare strands every preview host on
  whatever build broke; `tests/cli-update.test.ts` has a test that goes red if
  you do.
- **An unrecognised `update_channel` falls back to `stable`, not preview**
  (`resolveUpdateChannel` in `src/config.ts`). A typo must never opt a box into
  a ring its operator did not choose.

`phantombot update`, the `/update` chat command and the heartbeat update-check
all resolve through the host's configured ring, and `phantombot doctor` reports
it — a bug report that does not say which ring it came from is uninterpretable
once `latest` stops meaning "newest build".

**Versioning is intentionally not semver.** `1.1.<RUN_NUMBER>` — patch is the
release workflow's monotonic run number, not semantic impact and not the PR
number (PR numbers can regress; the PR is recorded in the release title/notes).
Don't bolt semver-aware logic on (`phantombot update --major-only` etc.); the
version string can't carry that information.

## How to add a new subcommand

1. **Write the file** at `src/cli/<name>.ts`. Export `defineCommand({ … })` as default and a `run<Name>` function for testability (the function takes injectable deps + returns an exit code).
2. **Register** in `src/cli/index.ts` `subCommands` (alphabetical order).
3. **Update the test** in `tests/cli.test.ts` — the `expect(names).toEqual([…])` list must include the new subcommand.
4. **Test the function directly** (in `tests/cli-<name>.test.ts`) by injecting fake deps. Don't drive `defineCommand` end-to-end; @clack/prompts is non-TTY-hostile in tests.
5. **Update README** — add the command to the "Commands" section.
6. **Update AGENTS.md** if the command introduces new conventions (a new lockfile, a new file location, a new credential interaction).

## Testing conventions

- **Per-test `mkdtemp`**, never write to real `~/.config/phantombot/` or `~/.local/share/phantombot/`. Each test creates an isolated workdir in `os.tmpdir()` and cleans it in `afterEach`. The `installPhantombotUnit` test pollution from PR #44 was exactly this problem (untracked).
- **Mock external IO** via fetch override (`globalThis.fetch = …`), `SystemctlRunner` injection, `TelegramTransport` injection, etc.
- **Don't drive @clack/prompts** in tests — it requires a TTY and will hang in CI. Either extract a prompt-free helper (the `maybeUpgradeUnit` / `ConfirmFn` pattern) or inject a stub confirm.
- **Tests should pass on a fresh clean Linux runner.** If a test passes locally but fails in the GH workflow, suspect environment leakage (real systemd dir, real $HOME, etc.) — see PR #43 / #44.

## Common pitfalls

1. **`bun-linux-x64` instead of baseline** — SIGILLs on pre-AVX2 hardware. Use `bun-linux-x64-baseline`. Documented at the top of `.github/workflows/release.yml`.
2. **`echo … > src/version.ts` in CI** — would clobber the comment block. Use `sed -i "s/0.1.0-dev/$VERSION/" src/version.ts` instead. The placeholder literal must round-trip exactly; if you change `version.ts`, also update the sed pattern in the workflow.
3. **`sudo cp` to install someone's binary** — leaves `.bak` root-owned, blocks future `phantombot update` from the unprivileged user. Use `sudo install -o <user> -g <group> -m 755 …`. Documented in PR #47's repro.
4. **`copyFile` over an existing foreign-owned file** — fails with EACCES because `O_TRUNC` checks the existing file's mode. `applyUpdate` unlinks `.bak` first; if you add similar copy logic, do the same.
5. **@clack/prompts confirm in non-TTY context** — returns the cancel sentinel. If you write code that calls `p.confirm` directly and expect a boolean, tests will hit the cancel path silently. Prefer `ConfirmFn` injection (see `src/cli/harness.ts`).
6. **Forgetting `tests/cli.test.ts` subcommand list** — every new subcommand needs to be added there or that test fails on PR merge.
7. **Creating/importing/restoring a persona on a fresh box without setting it as default** — the built-in fallback `default_persona = "phantom"` doesn't have a directory; `phantombot run` would fail with "persona 'phantom' not found." Every persona-producing path (`runImportPersona`, `runImportFromPath`, `runRestoreArchive`, `applyPersona`) calls `adoptAsDefaultIfMissing` from `src/lib/personaDefault.ts` so the new persona becomes default when there's no working default. If you add another persona-producing path, call it too — and add a `state.json` isolation `beforeEach` to its tests so they don't pollute the real `~/.local/share/phantombot/state.json`.
8. **`install.sh` piped to `sh` runs without a TTY** — interactive @clack TUIs would misbehave. The script detects this with `[ -t 0 ] && [ -t 1 ]` before launching the persona TUI, and prints the next-step hint instead. If you add interactive setup steps to the install flow, repeat the check.
9. **Adding a new harness — three places that must be touched, not one.** `src/harnesses/buildChain.ts` (factory: instantiate the wrapper class), `src/cli/harness.ts` (`SUPPORTED_HARNESSES` for the TUI + `detectAvailability` for the binary-on-PATH check), and `src/config.ts` (Config type slot + loader for `[harnesses.<id>]`). Plus inline test fixtures across ~12 files that have a literal Config object. If you forget any, typecheck + tests catch it — but it's tedious; the buildChain.ts extraction was specifically to retire the *fourth* duplicate that was about to land with each new harness. Gemini CLI is retired; Gemini embeddings remain under `[embeddings]`.
10. **Channel-specific behavior belongs in the channel layer, not in personas.** Brevity for voice replies, formatting for Slack, etc. should be appended to the system prompt at the channel boundary (see `VOICE_REPLY_INSTRUCTION` in `src/channels/core/prompts.ts`, passed via `runTurn`'s `systemPromptSuffix`). Putting "be brief on voice" in a persona's BOOT.md/SOUL.md throttles text replies too — and persists across all the persona's contexts where verbosity is fine. Channel-layer suffixes are scoped to the turn that needs them.

11. **Reply modality is mirror-input by default, with a per-message text override available.** `processChatMessage` in `src/channels/core/engine.ts` picks the wire format (sendMessage vs sendVoice) via `replyModalityOverride()` from `src/lib/audio.ts`: when the user's message (post-STT, so voice transcripts count) contains an explicit directive like *"reply in text"*, *"no voice"*, or *"send a voice note"*, that wins; otherwise modality mirrors input. The override is parsed by a small, deliberately conservative regex set — anchored on reply-verbs and unmistakable shorthand, no bare-noun matches ("text message to John" must not trigger). Voice is still capped by `ttsSupported(config)`: an override asking for voice when no TTS provider is configured degrades to text gracefully, same as the original no-TTS fallback. If you extend the regex set, add cases to `replyModalityOverride` in `tests/lib-audio.test.ts` AND to the three end-to-end scenarios in `tests/channels-telegram.test.ts` (voice-in→text, text-in→voice, text-in→voice-without-TTS).

12. **`GITHUB_TOKEN` for `phantombot update` isn't always safe to send.** GitHub App installation tokens are scoped to a single org's repos; using one against the public `phantomyard/phantombot` releases endpoint returns 401 even though the endpoint is anonymously reachable. `findLatestRelease` in `src/lib/githubReleases.ts` therefore retries once *without* the auth header on 401/403 before failing, and the final error mentions org-scoping explicitly. If you add another auth'd GitHub API call (e.g. for changelog fetch, asset metadata, etc.), reuse the `buildHeaders(withAuth)` helper and replicate the unauth-retry path — otherwise users with org-scoped tokens hit a dead end on what should be a public read. See issue #115 / PR #120.

13. **The narration/streaming loop is DUPLICATED across the two chat channels — gate both.** `src/channels/core/engine.ts` (Telegram) and `src/channels/phantomchat/server.ts` (PhantomChat) each carry their own near-identical `flushNarration` + segment-send state machine; PhantomChat *mirrors* engine.ts rather than calling into it. Any change to how interim progress bubbles are emitted (the `/chattiness` gate is the current example — a `resolveNarrationEnabled()` check at the top of both `flushNarration`s) must be applied in **both** files or half of it silently doesn't work. Both sites carry a `TODO(dedup)` breadcrumb. Scope is Telegram + PhantomChat only — the editor (ACP) surface is deliberately left untouched. Per-conversation overrides live in `src/lib/chattiness.ts` (JSON under `xdgStateHome`, mirroring `coderSwap.ts`). See issue #243.

14. **ACP has TWO scopes — a workspace and a thread — and history must only ever load into the thread one.** `src/connectors/acp/session.ts` derives both: the WORKSPACE key `acp:<sha256(cwd)[0..12]>` (stable per project directory) and the CONVERSATION key `acp:<cwdhash>:<threadid>` (stable per editor thread). Turn history is keyed on the **conversation**, so a new thread starts empty. This is load-bearing, not cosmetic: the conversation used to be keyed on cwd alone, so every "new" editor thread replayed the previous thread's turns **as USER messages** — a fresh thread opened onto a trailing queue of *"open a PR…" / "Go."*, and the model, reading the last thing the user had apparently asked for, went off and did unrequested work with nothing visible in the editor to cancel. If you touch the keying, keep the two scopes distinct and never widen the conversation key back to the workspace. Workspace-wide context is supplied *instead* by `briefing.ts` — prior turns rendered into a **system-role** block explicitly framed as finished sessions with void approvals, via `recentTurnsForConversationPrefix` in `src/memory/store.ts`. **Role is the whole mechanism**: the same bytes as `user` turns are live instructions; as a system briefing they're inert reference. Don't "simplify" the briefing back into history injection. The thread id rides inside the opaque sessionId (`acp_<cwdhash>_<thread>`), so `session/load` resumes a thread verbatim; legacy tokens with no thread segment still resolve to the old cwd-wide conversation, so pre-existing threads keep their history.

15. **Slash commands on the ACP surface must be dispatched OUT OF BAND, ahead of the serial request queue.** `src/connectors/acp/commands.ts` owns the allowlist (`/stop`, `/reset`, `/status`, `/harness`, `/help`) and delegates *behaviour* to the same `handleSlashCommand` in `src/channels/commands.ts` that Telegram uses — don't reimplement it. The dispatch point in `server.ts` is the part with a trap in it: `/stop` exists to kill the long-running prompt that is **currently blocking the queue**, so queueing it behind that prompt means it only fires once the turn it was meant to cancel has already finished. Route it out of band, the same exemption `session/cancel` already has. Commands are also advertised **per session** — an `available_commands_update` notification (`protocol.ts`) sent on both `session/new` and `session/load`, *not* in the `initialize` result — or the editor's `/`-menu is empty and users can't discover them. If you add a session-creating path, it must send that notification too. The allowlist is enforced in the ACP module *before* delegation, so this surface can't silently inherit a new Telegram-only command; `/update` and `/restart` are deliberately excluded (they bounce a service whose lifecycle the editor owns). Anything not on the list must fall through to the harness — personas define their own slash-isms, and a prompt that merely starts with `/` (a path, a regex) must not be swallowed.

16. **`/status` live probes must stay bounded — a dead provider must never hang the diagnostic.** `src/channels/statusProbes.ts` runs the fresh-on-every-call subsystem probes (Telegram `getMe`, ACP editor connectors, memory/embeddings backend, voice provider + key validation) that `handleStatus` in `src/channels/commands.ts` awaits before rendering `/status`. Because `/status` is what you reach for when something is broken, the whole fan-out is capped by a single shared wall-clock deadline (`PROBE_DEADLINE_MS`, ~5s): it's threaded into every client that accepts an `AbortSignal` (so the socket is actually cancelled — no #135-class leak) **and** raced in `gatherStatusProbes.settle` as a hard cap in case a client stalls before its fetch or ignores the signal. If you add a probe, give its client a `signal` param and thread `deadline` through it; a bare `await someFetch()` with no timeout re-opens the exact wedge this guards against. The deadline is injectable via `StatusProbeDeps.deadlineMs` purely for tests. Probe output is **user-facing** (the `phantomchat: npub…` line and the probe block both render in the reply), so any change to what `/status` prints must update the `/status` rows in `README.md` (both the Telegram command table and the editor-commands table) — this is the concrete case of the "user-facing change ⇒ README + AGENTS" rule below.

17. **macOS code-signing must shell out to `/usr/bin/openssl` (LibreSSL), never a PATH-resolved `openssl`.** `src/lib/macSigning.ts` builds the self-signed identity by generating a cert + PKCS#12 with openssl, then importing it via `security import`. The launchd environment phantombot runs under (and therefore the `/update` re-sign path) puts `/opt/homebrew/bin` **ahead** of `/usr/bin` on `PATH`, so a bare `openssl` resolves to Homebrew's OpenSSL 3.x. Its `pkcs12 -export` writes the MAC/PBE with modern algorithms that Apple's LibreSSL-era `security import` rejects with `MAC verification failed during PKCS12 import` — which silently failed the import step of **every** macOS `/update` re-sign (rollback → binary stays ad-hoc → TCC keeps nagging). Pin both calls to the exported `OPENSSL_BIN` (`/usr/bin/openssl`), the system LibreSSL that is always present and produces import-compatible p12s. `-legacy` is **not** the fix — that flag is an OpenSSL-3-ism and errors on LibreSSL. This is a distinct bug from the #363 keychain-search-list fix (which is downstream, at the codesign step); both are needed. **Dogfooding:** the `/update resign` chat subcommand (`handleUpdateResign` in `src/channels/commands.ts`, reusing `runFixSigning`) re-signs the current on-disk binary in place — no download/reinstall/restart/version-change — so this launchd-context bug can be reproduced and verified without cutting a release. It runs the same routine `/update` applies post-swap; macOS-only, a friendly no-op elsewhere. Because it's a user-facing chat command, its behaviour is documented in the `/update` row of `README.md`.

18. **The default-persona switch is gated on confirmation and agent-scoped switches are refused (PR #383 / issue #371).** `phantombot persona <name>` persists `state.default_persona` **only after** an explicit confirmation: interactive TTYs get a @clack confirm, non-TTY contexts require `--yes` (exit 2 otherwise), and tests inject a `confirm`/`isInteractive` into `runSwitchPersona`. A persona agent (harness sets `PHANTOMBOT_PERSONA`) can't re-point the daemon-wide default — that's the #371 ghost-switch bug — so the scope check refuses with exit 2 regardless of `--yes`. After confirmation the state is **re-loaded** (not the pre-confirm snapshot) to avoid clobbering a concurrent writer (e.g. `harness_bins` discovery), and the persona dir is re-validated right before the commit (TOCTOU). Any new user-facing CLI flag needs its README.md **and** AGENTS.md documentation — this PR documented `--yes` in both.

19. **A turn is registered for its lifetime, and `tick` defers a wake while the principal is talking (issue #391).** Two turns for one persona can run in DIFFERENT processes — the daemon serving a conversation and `phantombot tick` spawning its own harness — and the existing locks do not cover it: `runLock` guards `run` against `run`, `tick.lock` guards `tick` against `tick`, and nothing sits between the two. Observed twice: both turns worked the same PR and the same unlocked checkout 63 seconds apart, and a contributor got duplicate review comments. `src/lib/turnRegistry.ts` fixes it with a **registry, not a mutex** — one JSON file per in-flight turn under `$XDG_STATE_HOME/phantombot/turns/` (tmp+rename), read by `readdir`. Registration lives in `runTurn` itself (`src/orchestrator/turn.ts`), wrapping the body in a `try/finally`, precisely so a NEW entry point cannot forget to opt in; do not move it out to call sites. Two consumers: `cli/tick.ts` **defers** a due task while a turn is live or within `INTERACTIVE_COOLDOWN_MS` (3 min) of one ending, and `turn.ts` injects a one-line sibling notice into the system prompt for a turn that runs anyway. Load-bearing details, all of which have a failure mode if "simplified": deferral **never writes back to the task row**, so `run_count`, one-off deactivation and `--count` stay honest and "how long have we deferred" is just "how overdue is this task" — no extra column, no migration; it is bounded by `MAX_DEFERRAL_MS` (15 min) because a task that silently never fires is worse than the collision; **command-backed tasks are deferred too**, since the shipped poller contract (`src/persona/builder.ts`, and the README's Jira example) tells them to call `phantombot ask`, which starts a full turn — exempting them leaves a documented back door straight into the bug; and a live-looking entry is only believed if its pid is still the SAME process (`lib/processLiveness.ts`) AND it is younger than `MAX_TURN_LIFETIME_MS` (1 h), because `release()` cannot survive a SIGKILL or an abandoned generator. Kill switch `PHANTOMBOT_TURN_REGISTRY=0` degrades to the pre-#391 behaviour rather than to a crash, and it is off by default under `NODE_ENV=test` so unrelated suites cannot write live-looking entries into the real state dir — a test that means to exercise the registry must set it AND point `PHANTOMBOT_TURN_REGISTRY_DIR` at a temp dir. Both variables and the deferral behaviour are documented in the README's [Turn registry](README.md#turn-registry-concurrent-turns) section; if you change the lifecycle, the locations, or either ceiling, update both.

20. **A background turn reports what it did, and a shared checkout can be claimed (issue #405).** Invariant 19 stopped two turns colliding; it did nothing about why the collisions went unnoticed for so long — a turn woken by `tick` streams its reply into its OWN transcript, which the principal never opens, so a commit, a PR comment or a file edit made on their behalf leaves no trace anywhere they will look. Two mechanisms, both built on the registry. **`src/lib/turnDigest.ts`**: a turn whose origin is `task`/`notification`/`internal` writes a digest on exit — trigger, state-changing tool calls (`edit`/`delete`/`move`/`execute` only; reads are dropped, and `execute` is kept in full because we cannot tell `git status` from `git push` without parsing every shell dialect and the asymmetry favours noise) with the paths they named, and its closing summary — into `$XDG_STATE_HOME/phantombot/digests/`. The next INTERACTIVE, **TRUSTED, and PRIVATE** turn gets the pending ones injected into its system prompt and decides whether to mention them. Do not "improve" this into a notification: pushing every poller fire to Telegram breaks the standing don't-notify-unless-material rule and gets the channel muted, which returns us to zero visibility by a longer road; and writing a synthetic turn into the conversation history forges transcript that later retrieval treats as something the principal actually said. Load-bearing details: delivery is marked ONLY after the receiving turn succeeds (at-least-once — a duplicate costs a few lines of prompt, a drop loses the record precisely when the box is unhealthy); the write happens in a `finally`, so a background turn that pushed and then died still reports; only interactive turns receive digests, or two background turns bounce a report between themselves forever; **`trusted !== true` receives nothing and consumes nothing** — origin is NOT trust, a raw `phantombot ask` carrying an inbound email is origin `channel`, and a digest is persona-private context landing in a prompt a stranger is steering; **`replyAudience !== "private"` receives nothing and consumes nothing either** — trust authenticates the speaker, not the audience, so a trusted GROUP turn (`replyAudience: "shared"`) would disclose persona-private state to every member, and a wake-but-silent REACTION turn (`replyAudience: "silent"`, the fail-closed default) would consume a digest into the void — marked delivered, never seen. Omitted = `"silent"`: a caller that does not state its reply is private-and-visible receives no digests and consumes none. the block is capped at `MAX_DIGESTS_PER_TURN` taken **oldest-first**, with the overflow COUNTED in the notice and left PENDING — mark only what you showed, because marking the overflow destroys the record of a turn nobody saw, and draining newest-first starves the tail of a backlog under sustained load; titles, paths, trigger and summary are passed through `redactForLog` **at collection time**, since a tool title is a formatted command line and a digest is durable state a prompt later reads; and collection hangs off the same `onToolCall` hook as the audit log but is INDEPENDENT of it, because disabling `PHANTOMBOT_AUDIT_TOOL_CALLS` is not a request to go blind. **`src/lib/workspaceLock.ts` + `src/cli/workspace.ts`**: `phantombot workspace lock|unlock|status` records an advisory claim on a working copy, attributed to the turn via `PHANTOMBOT_TURN_ID` (set in the harness env beside `PHANTOMBOT_PERSONA`/`PHANTOMBOT_CONVERSATION`); a sibling's live claims are named in the prompt. **The holder is the TURN and liveness comes from the registry — never from the pid that wrote the record.** That is not a preference: the only writer is a CLI that exits milliseconds later, so pid liveness makes every lock prune itself as stale on the next query and the whole feature a silent no-op (shipped that way once; caught in review). `unlock` refuses unless the caller IS the holding turn — including a caller with no turn id at all, since a plain shell dropping a claim it never took is how a cooperative protocol becomes corruption — with `--force` as the deliberate override. Acquire is read-check-write, so it is serialised by a guard beside the lock; without it two simultaneous claims both read "free" and both win. **The guard is a TICKET QUEUE, not one exclusive pathname** (shipped as a single `wx` guard file twice; both cuts leaked the same way). One contested name must be DELETED to be freed, and deletion by pathname cannot be made ownership-safe — between reading a guard and unlinking it the guard can be replaced, and the unlink then removes its SUCCESSOR, handing two callers the section via the cleanup meant to protect it; POSIX has no compare-and-delete to close that with, so no amount of care inside those two syscalls fixes it. Instead each caller publishes its own uniquely named ticket (`<lock>.guard.<uuid>`) and the OLDEST LIVE ticket holds the section. Three properties carry the design and none may be traded away: publication is **write-to-temp + rename**, so a name that exists is always COMPLETE (the `wx`-then-write version left an empty guard whenever a process was descheduled between the two syscalls, and recovery then deleted it with no liveness check at all while its owner was alive and about to continue); every delete names a UUID that belongs to exactly ONE acquisition and is never reused, so no cleanup can reach a successor; and ordering is by **ctime** — the instant a name became visible — never mtime, because a scan can only miss tickets that appeared after it, which is precisely what makes two simultaneous winners impossible. **A ticket is surrendered on OWNERSHIP, never on age** (shipped as age-only twice; caught in review): a holder that is still running is a slow critical section on a loaded box, not an abandoned one, and it can resume INSIDE a section a successor has already entered — so a live owner keeps its ticket however old it gets, and a ticket is ignored only when the kernel says its owner is gone (no such pid, or a pid now held by a different process — start tokens differ). An unreadable start token is NOT evidence of death. **Off Linux that ownership question costs a CHILD PROCESS, which makes it a correctness concern and not a performance one** (shipped unbounded once; caught by the Windows runner). There is no `/proc` on Windows or macOS, so the token comes from `wmic`/PowerShell/`ps` — and the guard asks it about every foreign ticket on every retry, while `registerTurn` asks it about itself. Asking the EXPENSIVE tool first with a 10 s timeout, uncached, turned one contended acquire into dozens of interpreter starts against a ~120 ms budget: the section was never entered at all (`entered: 0`), and a no-I/O registry test timed out at 5021 ms. So: cheapest probe first, a timeout sized to the hot path, the working probe REMEMBERED (including "nothing here answers", or a locked-down box re-runs the whole ladder forever), and one answer cached per pid — every one of which can only go stale toward "still held", the safe direction. A non-zero exit is the probe ANSWERING about a dead pid, not a broken probe; demoting it there gives up the ladder the first time anyone asks about a corpse. `PHANTOMBOT_PROCESS_START_PROBE=0` is the operator off-switch, degrading to the pid-only check. **Every spawn on a Windows-reachable path sets `windowsHide`**: phantombot runs on Windows as a scheduled task with no console of its own, so each child otherwise allocates a NEW console and flashes a black window at the user — on a hot path that is a strobe, not a flicker. The single remaining timeout (`GUARD_ORPHAN_MS`) covers a ticket with no readable owner, which nothing this module writes can produce: corruption gets a timeout because liveness cannot be asked about it. **Release takes that guard just as strictly and refuses (`contended`) when it cannot get it** — "unlink is atomic" is NOT a reason to skip it (shipped that way once; caught in review), because an atomic unlink does not make read → ownership-check → unlink atomic, and the unguarded interleaving deletes a claim a concurrent guarded acquire has just published, leaving its holder working in a tree everyone else reads as free. Refusing cannot strand a workspace now that liveness is turn-based: a refused release self-heals when the holding turn ends, and a guard ticket dies with its holder. Be honest about the scope in any doc or review you write: phantombot is NOT in the path of the `git` a harness runs through its own Bash tool, so this reports and records a claim — it cannot prevent a write, and calling it a lock must not be read as a guarantee. **Pruning a stale lock happens UNDER the guard, with a compare-and-delete on the file's exact bytes** (shipped unguarded once; caught in review). Deciding a lock is stale is not instant — it reads the turn registry — so an unguarded prune reads claim A, a concurrent acquire publishes claim B over it, and the prune then unlinks B: its holder works in a tree everyone reads as FREE. This is the same defect class as the release bug above but on the READ path, which every `workspace status` and every prompt render walks, so it fired far more often. Never unlink a lock or a guard from a read path by pathname. `lock` fails fast rather than waiting (the answer to a held tree is a different directory, never a queue), it fails OPEN if the state file cannot be written — **which means the guard must distinguish EEXIST from I/O failure**; a single `catch {}` reporting a missing or unwritable state directory as `contended` (shipped that way once; caught in review) makes this documented fail-open path unreachable and turns a visibility feature into an outage — and a dead holder is broken on inspection when the registry reports its turn gone, plus a 1 h ceiling, so a crash can never wedge a workspace until a human clears a lockfile. When the registry CANNOT answer (switched off, or an id it has never seen) the lock is kept until that ceiling: guessing "free" on an unverifiable claim reintroduces the collision, guessing "held" costs one clone elsewhere. **Every field either block interpolates into a prompt goes through `src/lib/promptSafeText.ts` first** (shipped raw once; caught in review). A lock's `workspace`/`conversation`/`purpose` and a digest's `trigger`/`summary`/tool-call titles are written by ANOTHER turn, whose input may have come from email, a webhook or a raw `ask` — and they land in a later trusted, tool-capable turn's SYSTEM prompt having passed the threat judge exactly zero times, because the judge screens an untrusted turn's INPUT and nothing re-screens its output once that output is state on disk. A newline plus a `#` heading in a path was enough to end the list and open what read as a new instruction section. `inertText` confines a value (one line, no C0/C1 or bidi/zero-width characters, no backticks, bounded length) and the block's own prose names it as quoted data; **both halves are required** — confinement alone still permits a plausible one-line instruction, framing alone still permits a whole forged section. `redactForLog` is a SEPARATE concern (secrets, at collection time) and does not help here. Kill switches `PHANTOMBOT_TURN_DIGEST=0` and `PHANTOMBOT_WORKSPACE_LOCKS=0` degrade to the pre-#405 behaviour, and both are off by default under `NODE_ENV=test` for the same reason as the registry. Both are documented in the README's [Background-turn digests](README.md#background-turn-digests) and [Workspace locks](README.md#workspace-locks-shared-working-copies) sections; if you change the lifecycle, the locations, the caps or the delivery rule, update both.

21. **Drawer entries are rows now, and only THREE of the five drawers decay (issue #410).** `src/memory/drawers.ts` gives every drawer entry a content-derived id (`sha256(persona, kind, normalizeFact(content))[..16]`) behind `UNIQUE (persona, kind, content_norm)`, so re-filing the same entry REAFFIRMS one row instead of appending a duplicate — the dedupe that step 2 of the nightly asked a model to do by reading a 663 KB file, which is why one live persona reached 64 exact duplicate decisions. Three invariants that look like tidy-up candidates and are not. **`BELIEF_KINDS` is exactly `decisions`, `lessons`, `norms`, and `commitments`/`people` must never be added to it.** Decay is `weight · 2^(-ageDays / halfLifeDays)` off `last_reaffirmed_at`, which is right for a claim about how the world works and catastrophic for an obligation: age makes a commitment MORE urgent, so decaying it silently buries the one thing that needed surfacing, and a person fact ("date of birth") is not less true for going a year unmentioned. Both move by `status` alone, `sweepDormant()` refuses to walk them, and there is a test asserting the membership of the list — if you extend it, you are changing what the system forgets. **Nothing is ever deleted.** `superseded`, `dormant`, `discharged` and `expired` rows stay queryable forever and merely stop being injected; retirement is a ranking decision, never a `DELETE`, the same rule the compaction stage runs on. **Re-filing does not revive a `superseded` entry** (a dormant one it does revive, since a restated belief is live by definition) — otherwise a third-party tool that re-files its old norm on every startup resurrects it over whatever replaced it, and supersession stops meaning anything. Conversely, superseding an id that was never filed is a deliberate no-op, not an error: on a fresh persona the old entry never existed and that must not fail the write of the entry replacing it. `src/memory/drawerIngest.ts` migrates the markdown and **never rewrites or deletes it** — it parses both wild shapes (`###` blocks and the heartbeat's flat `- - [tag] …` bullets), dates each entry from its `## YYYY-MM-DD` section header, and is idempotent, so it is safe to re-run while both representations coexist. Third-party tools file and correct norms through this API, so any change to the contract needs `docs/memory-drawers.md` updated with it. **The rows are WIRED, and since #417 they ARE the source of truth** (the paragraph below was written when the markdown was — read invariant 23 with it). `src/memory/drawerSync.ts` is the only bridge: `syncDrawers()` runs in the heartbeat right after tagged lines are promoted (so a line captured this cycle is a row by the end of the same cycle), and `orchestrator/screen.ts` briefs the threat judge from RANKED rows instead of the first 16 KiB of a file. Do not invert that direction — nothing in the row path may write markdown, because the files are what the nightly writes, what the owner edits and what phantomtools merges into, and a table that can rewrite them turns a rebuildable projection into a second, authoritative copy. Three details that look incidental: the sync skips a drawer on an unchanged **content hash** (not mtime+size — the compaction stage rewrites drawers wholesale, and a same-length rewrite in the same millisecond is exactly when a skipped sync strands the rows on stale text), the sync marker is written only AFTER a successful ingest (a crash re-runs the drawer rather than marking stale text done), and the briefing's file fallback is **per drawer, not per briefing** — a persona mid-first-sync can legitimately have rows for `decisions` and none for `norms`, and failing open to "no norms at all" is precisely what makes the judge cry wolf on routine operations. The 16 KiB briefing cap is now shared out by `packBriefing` and trims on entry boundaries: before this, a 663 KB `decisions.md` consumed the whole budget and `norms` never reached the prompt, and the cut landed mid-entry so the judge read half a ruling as the whole one. **Any new drawer code needs a caller in the same PR** — stages two and three of #410 shipped a correct schema and a correct parser that nothing imported, which reads exactly like a finished feature in review and was live nowhere.

22. **Which daily journals reach the prompt is decided in CODE and must stay there (issue #410).** `src/lib/dailyRecall.ts` runs on the prompt path of every turn (`orchestrator/turn.ts`, just before `buildSystemPrompt`): TODAY'S journal always — the day is still open, so nothing has been distilled out of it and if it is not in the prompt it is not in the turn — and YESTERDAY'S **only** when the `.nightly-state.json` ledger has no `ok`-with-every-stage record for that date. This lived in persona `AGENTS.md` prose before, which failed in both directions: an agent could simply not do it, and anything able to write the persona directory could edit the rule out. Load-bearing choices, each with a failure mode if "simplified": **no config switch and no caller hook** — this is not `retrieve`/`pullFacts`, no channel, config file or persona gets a say, because a persona that switches it off loses a whole day of memory the first time a sweep fails and has no way to notice; **no lookback past yesterday** — a second undistilled day is a nightly bug to fix (the sweep retries unprocessed dates by itself), not a reason to grow every prompt forever; **the exclusion is the healthy case, not an omission** — a swept day already lives deduplicated and weighted in the drawers, `MEMORY.md` and `kb/`, so re-injecting the raw file only adds a staler second copy, and the raw journal is a FALLBACK for failed distillation; **an unreadable or missing ledger counts as NOT distilled**, erring toward including the file, which is the safe direction; **the byte cap keeps the TAIL** (a journal is append-ordered, so the newest entries are the ones a turn needs and the oldest are the ones distillation reached first) and is `DAILY_RECALL_CEILING_BYTES` (32 KB per file) plus `DAILY_RECALL_COMBINED_CEILING_BYTES` (48 KB for today and yesterday TOGETHER) — deliberately plain constants rather than the persona's daily compaction budget via `resolveDailyBudgetBytes`, because those two numbers measure different things (how large a CLOSED, fully-distilled day may stay on disk versus how much of an OPEN day a turn is allowed to see) and pinning them together silently clipped the morning off heavy days, 26 KB of 34 KB in one observed case, losing exactly the tagged captures on their way to the drawers. The cap was 256 KB per file until #426, set from the largest daily ever observed on the fleet on the reasoning that a runaway `memory capture` writer was the only thing it needed to stop. That was evidence about the past dressed up as a bound: a persona reached 82 KB in one day and wedged completely, every turn dying at `posix_spawn` with `E2BIG` because the assembled system prompt passed `MAX_ARG_STRLEN` (invariant 26). Two things to keep. **A per-file cap is not a budget** — both files can be injected in the same prompt, so 256 KB per file authorised 512 KB of journal; the combined ceiling is what actually bounds the block, and a per-file number alone will always understate the worst case by 2x. **The combined ceiling must stay strictly GREATER than the per-file one** — today is served first and yesterday spends the remainder, so the difference (16 KB) is yesterday's guaranteed floor; collapse that and a heavy today silently deletes an undistilled yesterday, which when injected at all is the ONLY copy of that day anywhere. Note also that these are the belt to the argv spill's braces, not the fix for #426: the spill in `lib/harnessArgvFiles.ts` is what makes prompt size unable to wedge a persona, and this cap is what keeps the prompt a sane size where a spill is available — note the sweep never actually shrinks these two files (`compactionCandidates` requires fully-distilled AND `DAILY_MIN_AGE_DAYS`), so this cap is the ONLY thing acting and every truncation must `log.warn` and name `phantombot memory get memory/<date>.md`, which unlike `phantombot memory today` returns content rather than a path; **"distilled" is judged on the FILE, not the record** — `isDailyDistilled` in `lib/nightly.ts` is the single predicate the sweep, the compactor and this module all call, and it re-checks the recorded mtime+size, so a day appended to after its sweep is injected again instead of silently lost; **the nightly sweep's own turns are skipped** by the explicit `skipDailyRecall` flag (with the `nightlyConversationKey` namespace as fallback, never a literal string), since a caller-controlled conversation id must not be able to switch journal injection off; **the journal is CONTAINED as well as framed** — `inertBlock` escapes a leading `#` on every line and strips control/bidi/zero-width characters, because invariant 20 is that framing alone still permits a whole forged prompt section; and the injected block frames the journal as DATA that cannot authorise an action — earlier turns wrote it, and some of those were driven by untrusted input, so this is the same rule as retrieved context and durable facts. It never throws: any failure degrades to no journal in the prompt, never to a dead turn. Behaviour is documented in the README's [Which daily journals reach the prompt](README.md#which-daily-journals-reach-the-prompt) section and in `docs/architecture.md`; if you change the selection rule, update both.

23. **The five drawers are ROWS, not files — and the database that holds them has restore points (issue #417).** `memory/people.md`, `decisions.md`, `lessons.md`, `commitments.md` and `norms.md` no longer exist on a migrated persona: `src/memory/drawerRetire.ts` archives them under `memory/archive/<date>/` (original bytes AND the regenerated export, side by side) and removes them, and `personaScaffold.ts` does not seed them. **There is exactly ONE write path.** The heartbeat FILES a `[tag]` line as a row; it does not append markdown, and the no-database case deliberately leaves the line in the daily file for the next heartbeat rather than falling back to a file write — a second write path is how the drawers ended up with two disagreeing copies of the same entry. The nightly's distill stage files with `phantombot memory drawers --file`; if you ever see the prompt telling a model to append to `memory/decisions.md` again, that is the regression. **Retirement is gated on evidence, never on a flag.** Two gates, per drawer, in `retireDrawers()`: every entry parsed out of the live file must exist as a row (checked by an independent re-parse, not by trusting the ingest's own counts), and the rows must round-trip back out to markdown that re-parses to the same id set (`drawerExport.ts`). A drawer that fails either gate keeps its file, is reported as `held`, and blocks nothing else — one unparseable `lessons.md` must not hold `norms` hostage, and must not be swept along with the four that passed. `renderEntryMarkdown` INDENTS block body lines for the same reason: an unindented body line starting `## ` reads back as a section header and splits one entry into two. Identity survives indentation because ids are computed over `normalizeFact`, which collapses whitespace. **The export is of the WHOLE table**, superseded and dormant rows included — dropping the retired half turns a backup into a summary. **Snapshots: integrity is checked BEFORE the snapshot is taken, always.** `backupMemoryDb()` refuses to snapshot a database that fails `PRAGMA integrity_check`, because rotation would otherwise carry corruption into all five restore points over five nights and delete the last good one — a backup system that destroys exactly what it exists to protect. Snapshots use `VACUUM INTO` (never `cp`: a WAL-mode database is three files and a copy of the main one can be torn in a way `integrity_check` calls clean), restore moves the live file aside to `<name>.pre-restore-<stamp>` instead of overwriting it, and it deletes the `-wal`/`-shm` sidecars — a stale WAL replayed over a restored file turns a recovery into a corruption. `doctor` checks integrity BEFORE anything opens the store (it used to die with a raw `SQLiteError` on the one condition it most needed to report), treats a database that does not exist yet as fine rather than broken, and prints the exact `phantombot memory restore --from <newest good point>` command with the fault.

24. **The phantomchat allowlist IS the principal list — bridges get their own, lower tier (issue #400).** A sender that passes `allowed_npubs` is treated as the owner speaking: trusted `SECURITY_PERIMETER` block, no threat screen, slash commands, reaction turns, private post-turn digests. So anything that speaks FOR OTHER PEOPLE — a Matrix/Slack bridge, a meeting-room relay — must never go in that list. `relay_npubs` (`src/channels/phantomchat/personaStore.ts`) is the tier for those: `authorize()` in `server.ts` returns `"trusted" | "relay" | "drop"` rather than a boolean, and a relay sender is answered but runs untrusted — screened, no slash path, never arms TOFU, no reaction turns, `replyAudience: "shared"`. Relay membership is checked BEFORE the allowlist so an npub in both resolves to relay: least privilege wins, and a copy-paste slip can only de-escalate. If you add a new capability to the phantomchat path, decide explicitly which tier gets it, and remember that a relay envelope's `origin`/`room`/`speaker` fields are attacker-controlled — render them through `relayEnvelope.ts`, never interpolate them raw.

25. **Exit 143 from a self-restart is our own cgroup teardown, not a failed restart (issue #408).** `defaultSystemdServiceControl().restart()` spawns `systemctl` **inside phantombot's own cgroup**, so the moment systemd accepts the restart job and begins the stop it SIGTERMs that child too — which Bun surfaces as exit 143 (128+SIGTERM). `SELF_RESTART_ARGS` carries `--no-block` and its old comment claimed that *prevented* this; it does not. Nothing orders "systemctl exits 0" before "systemd kills the cgroup", so on a fast host the flag loses the race and every **successful** Linux `/update` logged `updateNotify: restart failed after binary swap` at `error` level, while the unit was already restarting. That is worse than cosmetic: it is the fleet's only "the update did not come back" signal, so making it fire on every update trains humans and log-scrapers to ignore the one line that should page. The classification lives in `isSelfRestartTeardown` (`src/lib/systemd.ts`) and is applied by `runSelfRestart`, which is the extracted body of `restart()` precisely so it can be tested against a fake runner instead of a live user-systemd bus. Three deliberate edges: **137/SIGKILL is NOT included** — that's the OOM killer or a hard kill, a real fault, the same line the harness classifier draws (invariant in `lib/harnessAlert.ts`'s neighbourhood); **any other non-zero exit still fails** so a bad unit name or an unreachable session bus surfaces normally; and it is scoped to `restart()` only — **not** because restart is the internal verb and stop the external one (it isn't: `phantombot update --restart` in `src/cli/update.ts` and `src/cli/harness.ts` both reach `restart()` from a terminal), but because `restart()` is the only verb that can be issued from **inside the unit it acts on**; a self-`stop()` would never come back, so `stop()` is always issued from outside the doomed cgroup and a SIGTERM'd `systemctl` there is a real interruption. 143 stays correct for the external `restart()` callers too, since that CLI is usually itself spawned from inside the running service and shares the cgroup; the residual case (a genuinely detached CLI whose `systemctl` child is SIGTERM'd for an unrelated reason) reports an indistinguishable success, which is accepted as rarer and cheaper than crying failure on every successful update. The Windows path is unrelated: there `ok:false` means the deferred relaunch failed to schedule, which is genuinely broken. The unit template has declared `SuccessExitStatus=143` for this exact reason since day one; this is the same judgement finally applied to the code path.

26. **Two different kernel limits govern argv, and the one that bites on Linux is per-STRING (issue #426).** `getconf ARG_MAX` reports ~2 MB and bounds argv **plus** the environment in total; `MAX_ARG_STRLEN` is **131,071 bytes for a single argv element**, hard-coded as 32 pages in `fs/exec.c`, with no sysctl and no ulimit to raise it. `lib/harnessArgvFiles.ts` cited the wrong one for a year and gated its temp-file spill on `platform === "win32"` alone, on the stated reasoning that "POSIX ARG_MAX is ~2 MB, so phantombot's rendered payloads pass fine as argv". They did not: a persona whose journal grew past ~128 KB wedged completely, every turn dying at `posix_spawn` with `E2BIG: argument list too long` on a box with gigabytes free. `argvNeedsTempFiles(platform, payloadBytes)` is therefore **size-aware everywhere and unconditional only on Windows** — Windows' limit is on the WHOLE command line (~8,191 chars), which no per-payload test can clear because the other args share the same budget, while on POSIX any payload past `ARGV_SPILL_THRESHOLD_BYTES` (96 KB, ~35 KB of headroom) goes to a temp file. Load-bearing details: **measure `Buffer.byteLength`, never `.length`** — a journal of em dashes or CJK is up to 3x its character count in UTF-8, and a char-based threshold would leave a 270 KB argv inline and reproduce the bug exactly; **spill early rather than snugly**, since an over-eager spill costs one small file write and one read in the child while an under-eager one takes the persona off the air entirely; and **claude is the only harness that needed this** — pi already spills unconditionally, codex sends everything on stdin, and claude's conversation is on stdin too, so `--system-prompt` is the single argv element at risk and is what gets sized. The second half of the same bug is in `orchestrator/fallback.ts`: `Bun.spawn` **throws** E2BIG/ENOENT/EACCES rather than yielding an error chunk, and an uncaught throw propagated straight out of `runWithFallback`, so the chain never advanced and one unspawnable primary silently disabled every fallback behind it — the log read `trying harness claude attempt 1 of 2` and then nothing. The `for await` over `harness.invoke()` is wrapped: a throw becomes the recoverable failure the loop already knows how to handle (cool off, alert, fall through), and on the last harness it becomes an error chunk plus a `noteExhausted`, never a rejected iterator. `describeInvokeThrow` glosses E2BIG with the real limit, because the raw message "argument list too long" sends an operator to `getconf ARG_MAX` and a dead end. Treat any harness adapter as able to throw; the chain's job is to survive it. Finally, **the spill is an optimisation, never a precondition**: it touches a filesystem, and a filesystem can refuse (full disk, read-only mount, drifted perms on the persona dir), so `claude.ts` wraps the `createHarnessTempDir` / `file()` pair in its own `try` and degrades to the inline `--system-prompt` with a `log.warn` rather than letting the failure leave `invoke()`. That degraded path is honest and bounded — on POSIX anything in the 96 KB-128 KB band still spawns fine inline, and above it (or on Windows, where the whole command line is the budget) the spawn fails as a NORMAL harness error the chain can act on. A partially-created temp dir is cleaned up on that path rather than leaked. The rule this instantiates is the general one: on a headless box nobody is watching, so a best-effort convenience must never be able to take the daemon off the air. **Spilled payloads land under `<personaDir>/tmp`, never the shared system `/tmp`** (issue #365) — a system prompt carries that persona's memory, drawers and conversation, so all three production callers (`orchestrator/turn.ts`, `lib/threatJudge.ts`, `orchestrator/durableFacts.ts`) resolve a persona-scoped `tmpBaseDir`; the judge and the extractor derive it from the same `cwd` they already floor at `homedir()`, so even the degenerate no-persona-dir case stays in a directory owned by the running user. `createHarnessTempDir`'s `os.tmpdir()` fallback survives for tests only and now `log.warn`s when taken, because a production spill landing there is a plumbing regression rather than a configuration choice.

27. **Per-persona config has three rules, and each has already been broken once (issue #439).** One process serves every persona, and each persona's settings live in `<personas-root>/<persona>/config.toml` layered over the host's global file. **(a) Resolve the persona BEFORE loading config.** Every persona-aware entry point — `notify`, `ask`, `nightly`, `heartbeat`, `tick`, `voice`, `telegram`, `harness` — must call `loadConfigForPersona(name)` (or `loadConfig(name)`) instead of loading the default layer and picking a target out of it afterwards; the old shape silently runs one persona on another's bot, chain, voice and retrieval policy, and it fails *quietly*, which is why it needs a rule rather than a code review. Host-level harness BINS are carried over from the host layer by `withHostHarnessBins` — a `bin` names something installed on this machine and a stale persona copy must not shadow what `doctor` just probed. **(b) Write where the read path looks.** `resolvePersonaWriteTarget()` is the single write resolver: the persona's own file once it exists, the global file in its historical shape until then. A writer that hard-codes the legacy `[channels.telegram.personas.<name>]` / `[harnesses.personas.<name>]` tables reports "saved" and changes nothing on any migrated host, because the persona file outranks it on read. For the same reason `loadConfig(persona)` drops that persona's OWN legacy entry when its file states a chain, and a NON-default persona never inherits the global `[channels.telegram]` block — that bot belongs to the default persona, and handing it to a second listener trips the duplicate-token guard and takes Telegram down for everyone. **(c) Existing on disk never starts a persona.** The boot roster is `default_persona` + `autostart_personas`, applied to PhantomChat as well as Telegram (`selectPhantomchatPersonas`) — `listPhantomchatPersonas` scans directories, which is the right answer to "who is configured" and the wrong answer to "who talks to the world"; an imported, restored or archived-and-recreated identity must not start answering strangers because its folder exists. The gate is opt-in: `autostart_personas` ABSENT keeps exactly the pre-#439 behaviour, so an upgrade never silently loses a channel. Migration is copy-only (a rollback must still boot), ADDITIVE per key (a persona file holding only `[voice]`, which `phantombot voice --persona` will happily create before the first restart, must still get its Telegram translation) and runs on every daemon start, which is what makes `/update` order-independent from any version.

28. **A persona's brain is persona-scoped, and "cleared" must be SPELLED, not implied (issue #441).** The whole `[harnesses]` block — chain, Claude/Codex model, Pi provider and capability routing — resolves per persona: suffixed env (`PHANTOMBOT_PRIMARY_MODEL_LENA`) > that persona's `config.toml` > the host's unsuffixed env > the global `config.toml` > the default. Three things follow and each has already bitten. **(a) Every harness writer uses `resolveHarnessWriteTarget()`.** Not just the wizard — `/model` writes models too, and a write that lands in the global file is not "the host default", it is *every other persona's* value under the per-key merge. The resolver lives in `src/lib/harnessWriteTarget.ts` precisely so a non-TUI writer can share it. **(b) Deleting a key does not clear it.** Absence means "inherit", so removing a persona's routing hands it the host's routing and re-enables the host's ambient env var for that key. A cleared state needs its own on-disk spelling: `[harnesses.pi.routing] use_local_config = true` for "use Pi's own config" (it also withholds the api-key, which is read from the ambient env and would otherwise be the HOST's credential), and `model = ""` for a cleared codex pin. Any future persona-scoped opt-out needs the same treatment. That tombstone is only ever written into a PERSONA file — in the global file it would be inherited by every persona that has not stated its own, turning one persona's opt-out into the host's. **(c) A per-persona file must not fall back to another persona's file.** The managed pi extension directory is stamped once per host, so the harness names this persona's routing in `PHANTOMBOT_ROUTING_JSON`; when that var is STATED the extension reads only it, and a missing/invalid file registers nothing rather than falling through to the host-stamped sibling. A fallback across an isolation boundary is the leak, not the safety net.

29. **The plan-then-confirm gate is CHANNEL-AGNOSTIC and lives in the orchestrator — one copy, overridable, and not in a channel suffix (issues #443, #447).** `CONFIRM_BEFORE_LONG_JOBS_INSTRUCTION` (`src/persona/builder.ts`) is appended by `orchestrator/turn.ts` to every turn that is `isInteractiveOrigin(origin)` and not `replyAudience: "silent"`. That is deliberate on all three axes and each one was learned the hard way. **(a) Scope is the orchestrator, never a channel.** The original lived in `TELEGRAM_REPLY_INSTRUCTION`, so a persona planned-and-asked in chat while the same persona ran unchecked from an ACP editor, phantomchat or `phantombot ask` — the gate has to sit where every interactive entry point passes, which is the overlay stack in `turn.ts`. Do not add a second copy to a channel suffix; two copies drift and the channel-local one is the one nobody updates. **(b) The threshold is more than THREE tool calls, plus git/build/deploy at any size.** The first version fired at *more than one*, which matches every real request — a review, a triage, a deploy — so it gated work the owner had already explicitly asked for, which is pure round-trip cost. If you find yourself lowering it back toward one, you are rebuilding that. **(c) The user outranks it, in the text itself.** The removed version said `do NOT fall back to a "safe default" and proceed anyway` with no escape clause, and a literal-minded harness kept asking after being told a dozen times to stop; because the block is re-injected verbatim each turn, nothing said in the conversation could outlast it. The wording now states that a direct instruction ("go ahead", "stop asking", or a request already detailed enough to act on) wins for the REST of the conversation. Any edit to this block keeps that clause. **(d) Only where a human can answer.** A nightly (`origin: internal`), a task wake and a silent reaction turn all get the overlay withheld — a turn that stops to ask a question nobody will read is a turn that stalls forever. The same block carries the 50-word answer-length rule for direct questions, for the same channel-agnostic reason. Tests: `tests/channels-telegram.test.ts` (present on chat turns) and `tests/orchestrator-confirm-gate.test.ts` (present for ACP/CLI, withheld for nightly/task/silent).

30. **Drawer `--import` marker validation is structural, not best-effort (issue #437).** `<!-- id: kind:hexid -->` (`drawerExport.formatIdMarker`) is what lets a hand-edited `--export` file come back in through `--import` without every edit re-filing as a duplicate — unchanged content reaffirms the row the marker names, changed content supersedes it, no marker files fresh, same as plain ingest. Two guards keep the marker from being an attack surface, and both are enforced by CONSTRUCTION rather than by checking a value after the fact: a marker's embedded `kind` must equal the kind of the file being imported (`src/memory/drawerImport.ts` rejects a mismatch outright — a `norms.md` edited to claim `decisions:...` cannot touch a decision, full stop), and the id must resolve to a real row for THIS persona and kind (ids are `sha256(persona, kind, normalized content)[..16]`, a hash rather than a sequential counter, so nothing can be guessed into colliding — a forged or stale id just fails to match and the line degrades to filing as a new entry, never to overwriting the wrong row). Either rejection still files the line's own content normally; only the bogus supersession claim is dropped, and both are counted and reported (`rejected marker: …`) so a tampered export is visible rather than silently absorbed. **Supersede is loud on purpose**: every one is appended to that day's daily file (`- [drawer-import] superseded …`) so a stray keystroke that changes one character surfaces in the ordinary next-turn digest same-day, with no separate confirm/review flow built to carry it. That log line names the row ACTUALLY RETIRED (`ImportEntryResult.supersededId`, set from the resolved live row), not the marker's id, keeping the marker beside it as provenance only when the two differ — from the second edit of one exported file onward the marker names a row an earlier import already retired, so logging it would assert a fork that never happened and omit the real retirement from the only audit channel this mechanism has — reaffirm needed no such thing since it is exactly the existing re-file path. **A marker denotes a LINEAGE, not a snapshot.** An id is derived from content, so a marked line's id stops naming a live row the instant that line is edited and imported — and an export is a file people keep and edit again. A CHANGED line therefore resolves the marker FORWARD through `supersedes` (`DrawerStore.resolveLive`, scoped to persona+kind, cycle-safe via a `seen` set) and supersedes whatever stands in that row's place today; superseding the row the marker literally names would retire an already-retired row and strand its replacement active beside the new line — two active rows disagreeing, the exact duplicate #437 exists to kill. The walk is gated on "the content changed" rather than run up front, because an export lists a superseded row AND its successor each under its own marker, so an unconditional walk would turn an unedited re-import into a supersession. And when the walk lands on a row whose content already equals the line (the same edited file imported twice, the ordinary way to retry), it is a plain reaffirm — asking that row to supersede itself is what `fileEntry` throws on. Stdin form is refused without `--kind` for the same reason `--file` is: the directory form reads the kind off each filename and can loop, stdin carries one document and would otherwise be drained into `DRAWER_KINDS[0]`. Supersession log lines `JSON.stringify` both contents, because a block-form entry is multi-line and a body line spilled to column 0 in the shape `[norm] …` matches `promoteTaggedLines`' `TAG_PATTERN` and gets promoted as a brand-new entry on the next heartbeat. `parseDrawer` strips the marker line before it ever reaches `content` — a block-form entry that let the marker fall through unstripped would bake `<!-- id: ... -->` into the row forever. Applies to all five drawers uniformly since the mechanism only ever touches schema fields (`asserted_at`, `last_reaffirmed_at`, `supersedes`, `status`) every kind already has; only the decay rate differs per kind, not this.

31. **There is ONE harness detector, and a persisted bin is a CACHE that must be platform-checked (issue #450).** `resolveHarnessAvailability()` (`src/lib/harnessAvailability.ts`) is the single resolver: absolute path with `PATHEXT` suffixes, then `PATH`, then the `harnessSearchPath()` sweep (`%APPDATA%\npm`, `~/.bun/bin`, nvm/fnm node dirs), then an absolute -> bare-name retry for a stale configured path. `checkConfiguredHarnesses` and `detectAvailability` (`src/cli/harness.ts`) both go through it, and nothing may reintroduce a second one. The bug this closes: the `phantombot harness` wizard and `init` called a bare `whichBinary()` on the configured bin, skipping the sweep AND the retry, so `doctor`/`run` resolved claude while the wizard reported NOT FOUND on the same config — **the wizard must never be a weaker detector than the daemon it configures**, because it is the tool an operator reaches for precisely when detection is already suspect, and a false NOT FOUND there sends them to reinstall a harness that was working. Separately, `loadConfig` reads `state.harness_bins.<id>` AHEAD of the bare-name default, and `state.json` lives in the DATA DIR, not beside `config.toml` — so a once-resolved absolute path survives editing or deleting the config file entirely and there is no obvious knob that clears it. A path written by a WSL/Git-Bash run and read back natively on Windows is the live case: `path.win32.isAbsolute("/bin/claude")` is `true`, so it looks well-formed, never resolves, and reads to the user exactly like a bad hardcoded default — which is why #450 was reported against `config.ts` where the default is in fact already the correct bare `"claude"`. `usablePersistedBin` (`src/lib/harnessBinPath.ts`) therefore drops a persisted value whose path FLAVOUR cannot belong to this platform (POSIX-rooted on win32; drive-letter or UNC on POSIX) so the chain falls through to the default the sweep can find. Two properties to keep: it is a **pure string test, never a filesystem check** — a well-formed path that merely does not exist right now is KEPT, because reporting a missing install against the configured path is the honest diagnostic and silently rewriting it would hide an uninstalled harness; and it is applied at the READ in `loadConfig`, not at the write in `saveHarnessBins`, so an already-poisoned `state.json` on a live box is neutralised without a migration. Documented in `docs/harness-detection.md`; if you change the precedence chain or the sweep, update it.

32. Embedding providers are interchangeable transports, not interchangeable
vector spaces. `src/lib/embedder.ts` resolves none, Gemini, and the
OpenAI-compatible `/embeddings` client; provider-specific prefixes stay in that
resolver. Every note/turn vector carries a deterministic per-row space
fingerprint: provider/model/dimensions, plus the OpenAI-compatible document
prefix. Query prefixes and credentials are excluded. Untagged pre-existing rows
are eligible only for the canonical historical Gemini default
`gemini-embedding-001` at 1536 dimensions, never inferred as
OpenAI-compatible; a successful full reembed tags and cleans them up. Mixed old
and new rows are therefore safe during an interrupted migration. `--reembed`
refreshes FTS first, performs a real document preflight, then force-writes the
current space without clearing the old rows up front; failures return nonzero
and obsolete spaces are removed only after a complete success. A provider,
model, or document-prefix change requires reembed even when dimensions happen
to match. Hybrid search filters by space before applying its independent
dimension guard; when no compatible rows exist it stays on lexical/OKF recall.
The OpenAI-compatible server is separately managed: PhantomBot does not own
its lifecycle, and this feature does not add Ollama, Qdrant, or MCP embedding
clients. Note/KB chunking is provider-aware: Gemini keeps its existing
18,000-character guard, while OpenAI-compatible endpoints default to the
configurable `max_chunk_chars = 5000`. The value is character-based rather
than an exact token guarantee, and must not be described as a llama.cpp
protocol limit. Chunking preserves source text exactly, prunes obsolete tail
chunks, and uses explicit chunk/file accounting.

32. **`.env` is a ONE-WAY LEGACY IMPORT — no runtime read, no write, and the file is kept rather than deleted (issue #452).** Phantombot sold the vault as canonical while `~/.env` and `~/.config/phantombot/.env` were still live on both sides: the units sourced them, `lib/envBootstrap.ts` re-sourced them before every spawn, and the model/voice/harness/importer wizards wrote to them — so the startup migration deleted files a later wizard run promptly recreated, and docs and reality disagreed about where a secret lived. All of it is gone in one direction: `vaultMigrate.ts` imports each plaintext file into the per-persona vaults exactly once and NOTHING reads one afterwards (`envFile.ts` is a read-only parser with `vaultMigrate` as its only importer, guarded by a test that enumerates the importers). Wizards write secrets through `lib/vaultSecrets.ts` into the persona's vault; non-secret model/routing settings write to `config.toml` only, and the old `PHANTOMBOT_*_MODEL` env mirror is deleted — a mirror nothing reads can only drift. Three things are load-bearing. **The plaintext file is NOT deleted.** An operator has to be able to roll back to an older phantombot that still sources it, so the migration keeps the bytes; what changes is that they stop mattering. **Therefore the migration needs a STAMP, not an absence.** `<file>.migrated-to-vault` is what makes the import happen once; without it a retained file would be re-imported on every startup and would silently stomp any `phantombot vault set` rotation made since — the file's absence used to carry that state, and keeping the file removed the signal. The stamp is written only after every key read back through the decrypt path, and a failure to write it means the whole file is retried next startup (verified-but-unstamped is reported as NOT imported, never as done). **Deprecation must be LOUD and repeated.** A surviving `.env`, and any retired key still present in the host `config.toml` (`DEPRECATED_CONFIG_KEYS` in `src/config.ts`), warns on EVERY startup rather than once per process: the failure mode is silent — an operator edits a setting and nothing changes — and a daemon that started before they opened the file would otherwise have already spent its one chance to say so. Rollback for the units is manual and documented: re-add the two `EnvironmentFile=-%h/...` lines, or install an older build; the files are still there. **The vault is a SECRETS store, so the import DROPS the settings that config.toml now owns.** A pre-#452 `~/.env` also carries the `PHANTOMBOT_*_MODEL` / `_BIN` / `_CHAIN` mirrors the old wizards wrote, and importing those would not preserve them, it would PROMOTE them: a vaulted key is injected into `process.env` at every startup and `harnessEnv(...) ?? asString(toml…)` resolves env FIRST, so a dead mirror would become a permanent override of the only store `/model` still writes — `/model claude sonnet` appears to work, then reverts on the next spawn, forever, with the stamp preventing the old re-import loop from ever healing it (the `_<PERSONA>` variants are worse: they outrank even the persona's own file). `CONFIG_OWNED_ENV_MIRRORS` / `isConfigOwnedEnvMirror` (`src/config.ts`) name them and `vaultMigrate.importableEntries` drops them at import, loudly; a file of nothing but mirrors is still stamped so it is not retried forever. **A secret read for a persona that is not the startup persona must come from THAT persona's vault.** One daemon serves several personas but `loadVaultIntoEnv()` only ever injected the startup one's secrets into the shared `process.env`, so in-process consumers that used to read a single shared plaintext file now have to resolve per persona or they silently get the wrong persona's key or none: the audio path (`voiceApiKey` in `lib/audio.ts`, which is why `sttSupport`/`ttsSupport`/`synthesize`/`transcribe` are async) and tick's `--secret` env (`buildCommandEnv`, per `task.persona`). Two rules there: never write a resolved key back into `process.env` (two persona listeners can be mid-turn at once), and when falling back to the ambient env, exclude names this process injected FROM a vault (`isVaultInjectedEnvKey`) — an ambient shell/systemd export is host-wide and safe, another persona's vault value standing in is a cross-persona credential leak. That exclusion is scoped to the leak it exists for: a key injected from THIS persona's own vault is still honoured (`ambientEnvKeyAllowed` in `lib/vaultSecrets.ts`, the one gate both resolvers share), because `loadVaultIntoEnv` deliberately leaves injected secrets in place when the SAME persona's vault fails to open transiently — refusing them there would mute a persona over its own credential, and would have the two paths disagree about what a transient blip means. Vault READS are open-existing-only (`getPersonaSecretStrict` guards on the vault file, same rule as `readAllVaultValues`, #262): a pure read must never mint an identity + nsec for a persona nobody provisioned. **Deprecation warnings cover the PERSONA layer too**, not just the host file (`DEPRECATED_CONFIG_KEYS` / `warnDeprecatedConfigKeys`, checked before `stripHostOnlyKeys`) — since #441 a persona `config.toml` sets the same keys, and that is exactly where a silent edit hides. Note "retired" is not "ignored": `turn_timeout_s` is still honoured as an alias, and each entry's `advice` says which it is. Out of scope and still open: Telegram tokens and Gemini embedding keys living in `config.toml`.

33. **A turn wedged mid-flight is RESUMED with context, not dropped — and the trade that buys is stated, not hidden (issue #459).** `orchestrator/resume.ts` + the attempt loop in `fallback.ts`: when a harness is killed by the IDLE watchdog *after* it had already streamed output, the orchestrator respawns that same harness ONCE, in the same chain slot, handing it a preamble built from the killed attempt's chunk log — the narration the user can already see, plus the `progress` titles of the tool calls that were in flight. Before this, that case had no recovery path anywhere: pi's coder ladder is gated on `!producedOutput` precisely so it never replays a side effect, and a single-entry chain (`chain = ["pi"]`, how every pi-only persona is configured) has no next harness, so the turn was dropped and the user got an apology bubble. Six such kills on one persona in a week. Load-bearing, each with a failure mode if "tidied": **the branch keys on the STRUCTURED `killCause` on the error chunk, never on the message text** — `killCauseToErrorChunk` sets it for all five causes and there is a test pinning each, because recovering the distinction by matching on the prose is one rename away from silently disabling the whole feature. **Only `idle` qualifies.** A hard-cap `timeout` is the one timer that must stay final (resuming it multiplies a 60-minute cap), `startup` means no output at all and the ordinary fall-through already covers it more cheaply, `aborted` is `/stop`, `policy` is a tripwire. **Only after output.** With nothing produced there is nothing to resume WITH, and the plain chain is both safer and faster. **One resume per harness per turn** (`MAX_RESUME_ATTEMPTS`): a second wedge is not transient and each attempt costs a full idle window of the user's patience. **The preamble must not claim the tool failed.** The stall may have happened AFTER a tool completed perfectly; the honest — and the only safe — instruction is that each call *may or may not have applied* and current state must be VERIFIED before anything is redone. Weaken that wording into "retry the call" and this becomes the blind replay it was designed to avoid. **The resume is preferred over falling through even when a next harness exists**, because the harness that was making progress holds the context a cold hand-off to a different model does not. **No config flag, deliberately** (Andrew, 2026-08-27): an opt-in fix for a user-visible failure is a fix nobody gets, and the guarantee being traded away ("never silently replay a side effect") is replaced by a better one ("never silently drop a turn") — with *silently* doing the work, since the recovery attempt is told exactly what is uncertain. The chunk log is per ATTEMPT, not per harness slot, or a second wedge would describe the first one's calls. **Only a structured `chunk.tool` counts as a started tool call** — the chunk contract allows bare `progress` for diagnostics and liveness lines, and letting one satisfy the output predicate would both steal the turn from the cheaper no-output fall-through and tell the model that a version warning may or may not have applied. **A resumed slot's terminal `done.finalText` is STITCHED across both attempts**, because that field is contracted to be the sum of the slot's text chunks: `runTurn` persists it, voice and other non-streaming channels deliver only it, and the Telegram/PhantomChat transports diff it against what they already sent to compute the remaining suffix — forwarding the recovery attempt's own `finalText` would drop the pre-kill text from history and from voice, and make the transports resend the tail. Tests: `tests/orchestrator-resume.test.ts`.
